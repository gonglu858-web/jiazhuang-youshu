## 2. 按严重程度与根因归并的返修

### R1 / P1：产物绑定与启动准入未形成同一条受控链

定位：[驱动v1](证据/CodexL2单根产物绑定与单次驱动v1-20261031.cjs)第12–40、46–75行。

1. `bind()`计算的是调用方提供Buffer的摘要，实际启动路径另由`boundary.productPath`提供，运行前后只核对两份源码，未核对该路径的产物。本机反例中不同目标路径仍ok=true，四次摘要查询均不涉及启动产物。
2. `createRunner()`只看`artifactBound===true`和一个真值属性，接受手造绑定对象。反例移除sources、改变cwd/参数、使用非摘要字符串后仍调用spawn并ok=true；此外绑定Buffer可原地改写，储存摘要与字节不一致也能继续。
3. 消费标志属于每个runner而非绑定：同一绑定新建两个runner，可各成功启动一次。来源漂移、既有回执两类反例也均先调用spawn一次，最后才由assess拒绝，未实现写前/启动前停止。
4. PE检查仅看若干标记和非零CLR RVA。零节、OptionalHeaderSize=0、CLR实际内容缺失的1KB合成头也被标为`clrHeaderPresent:true`并可绑定。合成头适合作为替身，不能因此宣称有效受管产物的静态检查已闭合。

**修复要求：** 优先复用受审静态检查/能力边界。固定配置、来源、受审编译后检查记录、产物路径与摘要必须绑定到同一不可伪造且不受调用方后续修改影响的内部状态；实际启动文件须在启动前按既定持有/复核契约检查，不能以任意Buffer的哈希替代。测试注入与将来真实固定能力明确隔离，固定参数/环境/路径及限额在能力内确定。伪造绑定、无产物、错摘要/路径、来源变化、既有回执均零启动；同一绑定跨runner仍只能消费一次，并保留既有回执排他防重复要求。PE/CLR目录、长度和映射须有实质静态核验，不能只检测非零数字。以上只实现和替身验证，不读取候选系统文件或实际启动产物。

### R2 / P1：异常收尾与回执没有绑定实际观测

定位：驱动v1第61–109行。

1. `onData()`只累计长度，实际回执来自独立`boundary.receipt()`。反例让stdout为空或仅为`wrong`，另给合法回执，仍ok=true。原自测把根Node输出`L2_ROOT_ONLY`作为helper外层stdout，再单独制造JSON回执，未覆盖真实helper的输出接线。
2. spawn后的订阅或等待抛错直接逃逸，无统一finally；两例均无kill、无附着facts。超限仅置failure，不停止；超时只kill，不再有界等待关闭，killAccepted也未入报告。
3. spawn异常直接写`closed=true`，未获得关闭观测。底层在部分建立后抛错的替身反例中，实际无等待/终止却记录关闭；至少应保持未知，并由能力契约负责可观测收尾，不能推断关闭。
4. `attempts:1`、`unexpected:0`为字面常量，不是实际尝试与守卫汇总。“无公共模块import”也不等于外部boundary不会执行额外能力。

**修复要求：** 明确定义可实际接线的有界异步/事件接口，统一失败与finally收尾，保留第一失败和真实启动/关闭状态；订阅、等待、读取、解析及收尾异常都带净化事实返回。超限/意外stderr即时停止，终止后有界回收与关闭确认，未确认保持失败。回执必须来自本次实际收集的受限helper输出（或同等严格绑定的单次通道），空/错/额外/畸形输出不能由另一路合法对象补成成功。次数、守卫、终止与关闭事实均取实际记录；测试要覆盖实际最终出口，不能只算wouldFail。不得放宽受审回执schema或将根进程输出与helper回执混为一层。
