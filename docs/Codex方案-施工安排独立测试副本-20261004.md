## 2. 为什么不继续原来的 D 方案

现有客户端 schedule-client.js 调用 memberAccess；只换项目ID不会隔离后台。新 service.js 的成员批准、指定管家和移出守卫会作用到 A/B/C，旧项目缺字段是已知事实。已有方案的“更新共享 memberAccess 再建 D”暂不恢复执行。

完全独立环境的隔离更强，但当前不能承诺直接可用或免费：CloudBase 官方创建环境说明支持多环境；官方 MCP manageEnvs 参数说明同时提示该创建路径不创建 NoSQL 实例。当前实现依赖 wx-server-sdk 文档数据库，不能为了新环境改成 PostgreSQL，也不能购买后才发现不能运行。

来源：2026-10-04 通过 CloudBase 官方知识库 searchDocs/readDoc 读取 [创建环境](https://docs.cloudbase.net/quick-start/create-env) 和 [MCP工具说明](https://docs.cloudbase.net/ai/cloudbase-ai-toolkit/mcp-tools) 的 manageEnvs 参数。普通网页抓取超时，未据此判文档不存在。**工具创建路径的限制不能推广为所有微信控制台路径都不支持 NoSQL**；账号实际资格、可选后端和第二环境价格均未核实。因此本稿推荐先审查现有 NoSQL 环境内的独立副本，不新增环境、不假定免费。

## 4. 本地实现的必要保护（已确认，由WorkBuddy负责）

### 4.1 复用已验收业务实现，不建立第二套业务规则

原 service.js/schedule-service.js 已通过本地验收，本轮不重新设计事务算法。新函数打包时从指定验收源码生成副本并记录哈希，禁止手工维护逐渐分叉的业务副本。原入口不改；生成的新产物不能混入原 memberAccess 部署目录。
