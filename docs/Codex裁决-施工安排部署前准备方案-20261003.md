## 二、S1：纠正当前状态、权限及上线顺序

### 事实核对

1. 本地 `setMaintenanceMode`（schedule-service.js:658）进入 maintenance 时重验账号/管家/项目，但**没有调用 assertProjectWritable**，缺 schema/epoch 并不会按文档所称直接抛 PROJECT_NOT_WRITABLE。它可把缺 epoch 写为 1，但不会补 schema。方案 §0.1 将该入口列为缺三字段必拒绝，是错误的。
2. 当前维护入口要求活跃管家；app admin 身份本身不满足。§2.2“管家或 app admin 已实现”不成立。
3. 本轮只读核对先前保存的已部署包 `memberAccess-before-schedule.zip`：SHA-256 为 `af337224c177c8c5ea9327e437c22d14fea4e81d4f0cc1b3b2ee8a15442f5163`，与前置证据一致。包内 service.js 有批准/指定/移出路由，**没有 scheduleWriteMode**。这是先前部署包证据，不是本轮重新读取的云端当前状态；B0 须刷新云端包指纹。

因此，不能声称 W1 前后 A/B/C 都已经不可写，更不能假设给旧库写 maintenance 就能阻断尚未认识该字段的旧函数。旧代码仍可修改成员而不递增新 epoch，连续三次 epoch 相同无法发现这种操作。

### 必须修订

- 用三列表明确区分“最后已核验旧部署”“待部署本地实现”“拟建运维工具”。所有当前云端结论必须有新的 B0 来源。
- 补上线顺序与写入者覆盖：在依赖 epoch 保护扫描/修复前，所有能修改相关数据的服务端写入者必须已经遵守维护与 epoch 协议，或已用可验证方式停用并排空在途请求。人工停发预览只能作为辅助措施，不能证明旧云调用全部停止。
- 不把 B1→B4→B5 当成已经可执行的安全顺序：B1/B2 可能需要新集合及运维入口，B5 才部署的新函数又是维护保护的前提。修订稿必须列出 bootstrap/维护能力、资源准备、在途排空、核验、切换、恢复的依赖图和中断状态；具体载体由 B0 事实决定。
- 本方案聚焦安排与三类成员变更，不要声称 maintenance 阻断“一切业务写”。列明仍可写且与核验相关的邀请、身份等入口及其影响。

## 三、S2：首用初始化不能当旧目录修复；异常不等于幂等成功

`initDir`（schedule-service.js:307）固定写 guard generation/version/fence=1，并将成员锚点 generation 写为 1。把它用于 generation=5 且 guard 丢失的 F3，会降低代际，违反既有契约。F3 还包括 guard 已存在但错代际/重复 ID，调用 initDir 会直接拒绝。

“抛已存在就跳过”也不成立：该异常可能是损坏目录，不能当作本轮修复已完成。§1.3 说“全部新增字段”，但修复错值必然涉及覆盖；F4 update 覆盖也与“不请求覆盖”相矛盾。

裁决：

- 首批只设计**已证实无安排、无 guard、无历史非零代际的补缺字段路径**；保持非零代际和已合法值，不无条件写 epoch=0 或覆盖 schema。
- F3/F4 修复另行设计，不直接导出 initDir 当维修接口。重建必须有明确单调代际/围栏策略、CAS 前置条件、原记录指纹和修复后验证；不得把 generation/fence 重置为 1。
- 幂等重跑依据持久化的修复轮次/操作 ID、输入摘要、结果及当前状态匹配；无法证明时拒绝或重新取证，不按通用错误码/错误文案判定成功。
- 同一操作再次执行必须验证目标状态仍与原结果一致。“已 ready 就 changed:false”也不能绕过身份、轮次和当前就绪证据。
- 修复记录与业务审计分开；不得伪造过去遗漏的业务批准/安排审计。确需新增维修审计，写入范围要显式列入授权。

## 四、S3：只读完整性与就绪证明需要重设计

### 分类和全量发现

- F1–F6 不是互斥枚举。F5 是项目层标签，可与成员 F3/F4 和桶 F6 同时存在；缺锚点单列，不把“有安排但 generation=0”归为“F1 确无安排”。
- 所有成员都须查 guard，包括无锚点/generation=0，避免漏掉孤立目录。
- 项目级 active 安排须完整枚举，再按 worker 分组；只对现存成员逐个扫描会漏掉根本不存在成员记录的 workerUserId。成员存在但 left/禁用、缺师傅角色/工种同样不能视为就绪，应报告人工核对，不自动改业务身份。
- `_id` 升序 + skip 仅保证固定数据集下稳定分页，不自动提供并发快照。扫描前后要核对覆盖所有写入者的围栏；缺字段的旧部署阶段只能给“观测报告”，不能输出可执行修复证明。查询失败、集合不可读、分页不完整不得记为零数据。
- 容量/字节超限继续停止，禁止截断修复；以实际完整性区分 EMPTY / NONEMPTY / INCOMPLETE / ERROR。

### 占用完整性

仅枚举 active 安排推导的月份主键，找不到其他月份残留、错误工种、旧逐日键及未知键。因此不能据此声称 R8/R10 检查了“全部桶”。必须有项目占用记录的完整、可证明扫描（以及旧记录归属规则），否则标未知并停止恢复。

最终应精确比较“从所有有效 active 安排的实际施工日推导出的占用映射”和“数据库中该项目的实际占用映射”：项目、工种、年月、日期、scheduleId 均一致，无缺项/多项/休息日残留。同一天同工种有两个 active 安排时停下，不能靠遍历顺序选胜者。日期指向某个 active 安排不代表日期属于该安排。

### 恢复的有限事务

§2.7 要求在恢复事务里完整复检 R3–R10，可能需要枚举全项目 schedules/成员/桶，既没有上限，也未满足当前“事务内只允许主键操作、每 attempt ≤80”的设计约束。10 分钟时效和三次 epoch 稳定都不能代替并发证明。

改为明确的分阶段方案：完整只读核验生成可信、绑定 env/project/维护轮次/schema/epoch/数据摘要的核验结果；最终小事务重验执行人、维护状态、轮次、epoch、核验结果的来源/时效及预算，原子恢复并推进 epoch。只有当所有相关写入与维修都更新同一围栏、检查期无旁路写时，这种证书式方案才成立。不得接受客户端自报“ready:true”或只校验报告日期。若无法证明写入者覆盖，维持阻断，另行设计有限分批核验。

schema 就绪检查应精确匹配当前支持版本 1；未知高版本不擅自解释。generation=0 且实际为空、guard 不存在是合法首用状态，R6 应明确该分支，不能一概要求 guard 存在。

## 五、S4：B0 去掉循环前置；索引与资源按事实处理

- B0 只需要目标身份/环境明确、只读能力可用、取证范围受控。不能以 G2 写入授权、G7 写入干跑或整套修复设计通过作为 B0 前置；它本来就是决定是否需要这些写入的依据。
- B0 读取已存在资源，缺失五集合如经可信元数据查询确认不存在，可记录 NOT_EXISTS；不创建集合来完成取证。
- “兼容修复不新增任何索引”当前只能是目标，不能是结论。扫描实际需要的索引应从最终查询及现存索引回读比对。已有方案不自动证明某索引已存在或就绪。
- 支持等效覆盖索引时可以记录依据，不机械要求字段清单逐字相同；确需新增索引要说明查询、方向和范围，不能通过不完整主键枚举规避全量检测。
- 平台不支持事务 where 并不是本方案必然失败：只要最终写事务确实仅主键访问即可。函数 Timeout 与数据库事务时限分开记录，P3 不混称。
- 核验项按阶段分配：B0 不依赖尚未部署的 D 写入测试；生产兼容写、D 小范围验证、容量/故障专项分别明确门槛，避免“必须先实测 D 才能准备部署 D”的循环。

## 六、S5：重写写入清单与授权说明

当前 §0.2 禁止改占用/审计，§2.5 又要求重建占用；W1/W4/W5 被称为新增字段，但对已存在字段/guard 的纠错是更新；B1/B4 被称为唯二改状态，B2 同样会修改数据。W2“可删”也不代表删后保持可用。

修订为逐动作清单，至少区分：

1. 只读观测、离线干跑：沿用授权，无云端写入。
2. 已证实空数据的补缺元数据：精确 projectId/memberId、缺失字段与预期旧值、写后值、epoch 初始化/推进、可用性影响。
3. 已有目录/桶修复：原记录指纹、更新/新增/保留策略、是否涉及旧键清理、修复审计/幂等记录；当前暂不实施。不能一面承诺不删改占用，一面计划消除旧桶残留。
4. 恢复 ready：不是 W5 的自然结果，是单独状态变化，必须有已审查核验机制。
5. 新执行载体/资源：明确访问控制、打包依赖、凭据来源、默认禁用、退出机制；独立云函数不会天然隔离共享数据库写入风险。

Codex 可以裁定技术方案和执行已授权操作，不能代替用户批准新增范围。先形成干跑后的完整变更包，再提出一次有具体内容的授权请求；此次不要求用户逐条批准假设中的 F3/F4/F6，也不让用户确认“永久不可写”。
