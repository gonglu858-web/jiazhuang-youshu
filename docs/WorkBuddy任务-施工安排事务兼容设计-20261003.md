## 1. P1：事务内条件查询不符合官方支持范围

官方来源：https://docs.cloudbase.net/database/transaction （Codex 于 2026-10-03 用 CloudBase 官方知识库 readDoc 读取）。限制明确：事务仅支持 doc，不支持 where；最多 100 个操作，最长 30 秒。

现有 schedule-service.js：

- find 使用 source.collection(name).where(where)，可接收 tx。
- fetchAll/paginatedFetch 在传 source=tx 时执行 where/orderBy/skip/limit。
- rebuildGuardCount 在缺失 guard 时依赖事务内完整查询。
- hasActiveSchedules 在每次实际移出路由中依赖事务内完整查询。

影响：不仅新施工安排操作，新版 removeMember 也会引入此依赖。当前真实部署包 wx-server-sdk=3.0.1、@cloudbase/database=1.4.1；SDK 暴露 Query 并携带 transactionId 发送请求，不代表平台支持该查询。尚未在云端调用复现错误，不得把文档兼容风险写成已测得某具体错误码。

需要给出仅依赖已支持事务操作的方案，覆盖：

1. guard 正常、缺失、损坏、与实际安排计数不符时如何保证安全。
2. 如何防止事务外扫描期间创建/取消/改派引起集合变化，以及缺失 guard 的首次并发创建。
3. 创建/改派/取消/移出如何共享冲突点；同一事务重试如何重新校验所有依赖。
4. 如何完整校验超过 100 条安排；是否需要版本戳、确定性目录文档或其他可证明的结构。
5. 既有项目无新集合记录时如何兼容；有数据但缺结构时如何拒绝/修复，不自动按零计数放行。

**不可接受的快捷修改**：把 where 移到事务外后直接使用旧结果；仅信任计数并删除 GUARD_INCONSISTENT 检查；捕获错误后假定没有任务；改弱测试断言以通过。若提出事务外扫描+版本围栏，须说明从扫描前到提交之间每一种写路径如何更新围栏、初始化与重试如何处理；单纯在事务末尾读一个 guard 不足以证明扫描有效。

## 2. P2：365 天安排超过单事务操作预算

当前每个实际施工日保存独立 occupancy 文档。允许 365 天且无休息日时，仅 365 个占用写入已超 100 次；调整还会释放旧日/获取新日，另有权限读、成员读、receipt、guard、schedule、revision、audit 操作。

请提交每个动作最坏情况操作预算，计入读写和辅助结构：create/update/reassign/cancel/removeMember，以及缺失结构恢复分支。说明怎样在事务开始/首个写入前判断超预算，且失败不留下半份安排。

比较并推荐可实现方案：

- 改变占用结构，例如确定性分桶文档，保留每一天的冲突判定与原子释放/获取；需说明文档大小/热点/跨桶事务上限和迁移影响。
- 或明确限制首次试验的范围，并在服务端强制预算及客户端一致提示；不能悄悄把 365 改成 7，也不能只靠文档要求用户别选长日期。若改变既定产品能力，明确列为待确认变更。

不能通过拆成多个独立提交事务却继续宣称整条安排原子成功。必要的集合/字段/索引变化必须列清，当前获准五集合的方案不能被隐式扩大。

## 3. 运行配置与测试契约

- 当前 memberAccess：Nodejs16.13、256 MB、Timeout=3 秒；事务平台 30 秒上限不是函数可执行 30 秒。说明短期用例能否在 3 秒内完成及所需配置建议；不要自行修改云配置。
- 保留完整 requestId/版本/载荷回执约束、可信微信身份及项目权限、只允许管家写、日志脱敏。
- 设计新增“平台限制夹具”：事务内 where/query 即报错；记录并约束事务操作预算，不能继续用无限能力 mock 代替平台。

- 指定实际 SDK 版本，区分实际 SDK 请求形状测试、模拟事务测试与真实云端测试；不要把 SDK 路径可加载称作云端事务通过。
