## 2. S3-b：失败关闭与槽位关联仍未完整成立

### 2.1 临时读失败会回写进行中（P2，已实测）

定位：`miniapp/miniprogram/utils/sandbox-test-driver.js:1223`。

当前 `persistSlot` 首先读取已有状态；读取不成功时用 `inFlight` 兜底，然后调用 `setCaseState`。后者会再次读取存储。第一次临时失败、第二次恢复正常时，兜底值会实际写入。

独立反例 `late-first-read-fails-once`：

1. 两个请求均超时，正常返回 stopped，持久记录也是 stopped。
2. 只让下一次 getStorageSync 抛错一次，其后正常。
3. 第二笔晚到成功，触发补存。
4. **持久状态变成 inFlight，而先前返回的报告仍为 stopped。**

这是既有“补存失败不回写状态”的遗漏分支，不涉及新业务。当前仍有防重，不把本次发现夸大为已发生重复云请求。

最小修正：无法确认当前记录和状态时停止本次补存，不默认任何状态、不继续写回。已有记录保持原样；内存可以记录补存失败，但不能把失败当作保存成功。增加“仅首读失败、随后读取恢复”的测试，核对原存储字节不变、无补发、仍被持久防重阻断。正常保存路径保留。

### 2.2 内存槽位未带入持久证据（P2，已实测）

定位：`sandbox-test-driver.js:1214`、`:1263`。内存有 `slot.index`，但写入 `lateArrivals` 时只复制 row，再将各槽位的数组展平，未保留该 index。

反例 `same-id-two-timeouts-second-slot-late`：两笔同 requestId，发送时间精度内完全相同，均超时；只让第二笔晚到成功。持久 lateArrivals 只有一条，无 index/slotIndex；仅凭这份记录无法确定它属于两个 timeout 中的哪一个。数组第 0 项也不能代表第 0 槽，因为本例只有第 1 槽产生补充记录。

本轮已有测试仅验证“一个超时、另一个已成功，最终有一条指定内容”，没有验证持久化关联键。不能据此声称所有同号场景都可区分。

最小修正：将稳定槽位编号写入主响应与晚到响应，或使用保留槽位索引的持久结构；不使用 requestId 或时间戳代替槽位身份。补“两笔同号均超时，第二笔先晚到，第一笔随后晚到”的断言，验证两条补充证据各自关联正确，主 timeout/停止状态不变。

## 3. E1：重跑入口需简化，不继续扩大回退机制

### 3.1 所有 spawn 错误都回退，可能实际执行两次（P2）

定位：`docs/证据/WorkBuddy安全重跑与S3ab复现-20261006.cjs:127–136`。

`run.error` 并不等于进程从未启动；其中也可能是 ETIMEDOUT。代码对所有错误无差别 require 隔离副本，因此子进程已经执行过一部分并超时后，会再执行一遍。

对实际 `safeRerun` 函数进行合成进程/文件系统注入，ETIMEDOUT 样本计数为 **2 次执行启动**，结果仍为 `reran:true / awaited:true`。这是函数控制流的故障注入，不是声称本机真实出现了该超时。

### 3.2 文件出现/暂时稳定不等于异步任务已完成（P2）

同函数通过 require 启动自执行异步脚本，没有取得其完成 Promise，只轮询输出文件大小与 mtime。之后只要文件存在就设 `awaited:true`；轮询结束也没有以稳定计数作为最终拒绝条件。

EBUSY 注入样本模拟任务已经写出 JSON、但任务尚未结束，函数仍返回 `awaited:true`。因此本轮“进程内回退也实际 await 完成”的表述过强。这里的 await 等待的是轮询函数，不是被测脚本的生命周期。

**固定采用更小修法**：下一版入口不做进程内自动回退。子进程成功退出后才读取本次结果；任何启动错误、超时、非零退出或无新结果均记未完成，并保留实际错误。不能因为运行环境受限就延长轮询、自动再执行或用旧结果补齐。需要 shell 独立核对时另存证据并注明，不把它填充成自动重跑完成。

### 3.3 整体编排与封堵结论

- 外层入口 `:521` 先执行 34 条，再在 `:522` 执行 18 条；18 条脚本 `WorkBuddy返修S1S5复现-20261006.cjs:798` 内部又执行 34 条。故整个入口实际有两次 34 条执行，不能笼统写“34 条只跑一次”。这一结论来自两层实际调用链静态核对；本次没有为了证明重复而直接执行这条会覆盖既有重跑输出的路径。
- `:560` 使用 `reruns.some(r => r.reran === true)`：只有一份重跑完成也可能 `e1.sealed=true`。该结果最多说明一部分已完成，不代表要求的 34/18 两份都已复跑。最终应分别记录未完成项，完整结论要求两份本次结果均完成且符合各自期望；不能只检查出现了一个 summary。
- 隔离文件名只含固定 label，下一轮会覆盖同名 cjs 并删除同名 JSON。这可以作为明确声明的临时工作区，但不能同时称其中每份均为永久的新证据。下一版用独立运行标识保留每次输出，避免覆盖上一轮交付路径；无需新增签名系统。

最小方案：**只新增一个重跑入口**，由它统一执行 34 条和 18 条断言各一次，输出本次独立路径。必要时对运行副本的编排部分做明确、可核对的调整来禁止嵌套重跑，原断言保留；不能把“调整过编排”宣称为与原脚本逐字节相同。失败明确未完成，不开发通用执行平台。

本轮明确修改了 `WorkBuddy返修S1S5复现-20261006.cjs`：上一轮 36977 B、d26906f6…，本轮 41117 B、09f23d61…。因此“Codex 与历轮全部历史证据未改”不准确，也不符合上轮要求另建入口、旧脚本不改。
