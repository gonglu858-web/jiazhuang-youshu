## 2. R1【P1】读取必须区分缺字段与成功空，并核对返回记录主键

定位：`miniapp/scripts/lib/sandbox-primary-sdk-adapter.cjs:125–154, 309, 381`。

- 事务 `data === undefined` 被第138行当作无记录。独立复现让用户记录正常，primary与审计返回 `{requestId:'fake'}` 或 `{data:undefined}`：真实P4核心仍返回 `initialized/granted=true`，调用2次set、1次commit。
- `readOnlyGet(primary)` 返回单条 `_id:'wrong-key'` 被接受。任务明确要求0/1条且记录主键匹配，目前normalizeDoc没有接收期望key。
- 事务数组、普通读取对象也被当作兼容格式接受，超出本次真实包核实的形状，说明中“形状错误拒绝”过强。

最小修法：锁定当前SDK已核实契约：事务成功空仅显式 `data:null`；普通成功空仅 `data:[]`。缺data、undefined、非预期结构拒绝；非空记录必须有匹配查询key的 `_id`。若未来需其它版本形状，单独有依据地适配，不本轮猜测。含code继续拒绝。

验收：异常primary/审计读取与真实核心串联后**零set、零commit**；错/缺主键分别覆盖事务与普通读。保留正常null/[]及正确主键的正向例。

## 3. R2【P1】set成功判定与当前SDK返回契约不符

定位：同文件 `159–176, 399–401`。

当前只要求 updated/upsert_id/updatedCount 三者之一存在，仅检查updated是否number。`{updatedCount:false}`、`{updated:0}`都通过；独立串联核心，两种均得到initialized、2写1提交。这些回执不能证明写入成功。

当前真实包事务set转换后返回 **updated、upserted数组、requestId**，不是平台底层的upsert_id；第160行注释混淆了层级。已有测试的正确SDK样本靠updated字段侥幸通过，未检查upserted。

最小修法：以已核实的SDK最终返回形状判断成功，校验计数有限/非负/整数及单文档语义，校验插入结果的主键与目标一致；updated=0且没有合法目标插入结果不得通过。不接受未核实的updatedCount或底层upsert_id作为替代成功凭据。传入期望主键供校验，不改变核心已存在记录不覆盖规则。

验收：错误类型、NaN/负数、零更新无插入、错误插入主键、缺字段/含code均使核心不commit；保留实际SDK合成成功返回的正向串联，不能只验证空用户导致提前停止。

## 4. R3【P1】先核验调用者字段，再净化输出，不能取消核心拒绝条件

定位：同文件 `316–343`；对照已验收核心 `sandbox-primary-bootstrap.cjs:393–410`。

核验结果只检查allowed/envId，随后返回固定 `{allowed:true,envId}`，丢弃appId和trusted。

实测核验方分别返回：

- `{allowed:true,envId:固定环境,appId:'wrong-app'}`；
- `{allowed:true,envId:固定环境,trusted:true}`，核心未设置allowTrustedForTest。

两种均进入事务并initialized（2写1提交）。核心本来会拒绝错appId或测试trusted标记，适配层净化把其拒绝依据删除了。这不是要求本轮实现生产IAM，而是不能弱化已有契约。

最小修法：在输出白名单净化前拒绝核验结果的错appId与trusted:true；保留错envId/未通过/异常拒绝。生产核验者依然未接通，不制造新的凭据体系或假allowed。

验收：与核心串联上述两例，**零begin、零读写、零commit**。通过结果仍不得透传其它自由字段。

## 5. R4【P2】提交未知后的rollback不能依赖公开标志判断归属

定位：同文件 `249–267, 360–365, 427–444`。

rollback把 `__commitUnknown` 当作不在openTransactions中也可放行的依据，但未保留归属核验。独立复现：

- A适配器事务commit失败后，将其句柄交给B.rollback，B成功调用了A的底层rollback；
- 伪造 `{__commitUnknown:true,__tx:{rollback}}`，底层自定义回调也被调用。

现有外来/跨适配器测试仅覆盖普通活动句柄，没有覆盖unknown分支。

最小修法：归属及active/commitUnknown/finished状态放在适配器私有登记中，全部方法先核对归属。仅本实例真实登记的commitUnknown可rollback；外来标志不能授权。返回句柄不应允许更换底层事务引用。无需新架构，一个私有WeakMap等即可。

另：第360行称“不改真实句柄”，362–364行实际重绑了真实对象的方法；一并消除该不一致，避免污染宿主SDK对象。

验收：A/B交叉unknown、伪造unknown、已结束句柄均零底层调用；本实例合法unknown可回滚一次，之后拒绝复用。

## 6. R5【P2】异常净化不能保留任意name或信任可构造的AdapterError

定位：同文件 `68–74` 及各SDK调用catch。

- 传输异常name可以是任意字符串；设置为合成敏感标记后，标记进入适配层公开的originalErrorName。
- 若SDK/注入依赖抛出本模块导出的AdapterError，其message被sanitizeFailure直接信任；与真实核心串联，合成标记进入RESULT_UNKNOWN的detail.cause。直接JSON.stringify(Error)可能看不到非枚举message，但不代表核心后续String(error.message)安全。

最小修法：依赖边界抛出的任意异常只映射为本层固定码/固定文案；异常类型若保留，只允许固定白名单名称，否则统一Error。不能仅凭instanceof信任自由message/code。适配层自己生成的固定错误与依赖异常分开处理，不扩大为通用脱敏系统。

验收：marker分别放入message/name/code及外部构造AdapterError；检查直接错误的message、枚举字段及核心最终detail，均不得含marker。保留准确的失败类别与停止语义。
