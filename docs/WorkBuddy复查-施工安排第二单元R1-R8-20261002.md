## 3. 阻塞项与针对性修复要求

### F1 / P1：真实路由返回嵌套对象，列表和历史页直接报错（R2、R6）

定位：`miniapp/cloudfunctions/memberAccess/service.js:310`、`:318`；`schedule-service.js:195`、`:249`；`pages/project/project.js:30`、`pages/schedule-detail/schedule-detail.js:149`。

子服务现返回 `{ schedules: [], pagination: {} }` / `{ revisions: [], pagination: {} }`，路由却仍返回 `{ schedules: await ... }` / `{ revisions: await ... }`。通过实际 service.execute 接页面的离线复现得到：

- 项目页：`(body.schedules || []).map is not a function`；
- 详情页：`(revBody.revisions || []).map is not a function`。

路由同时没有转交 cursor/limit。要求统一最终公开响应，贯通路由—客户端—页面；分页不能仅存在于子服务。新增端到端离线契约测试，使用实际路由返回值，不再让页面 mock 自行伪造正确的数组掩盖问题。

### F2 / P1：缺失 guard 后取消一份安排，会放行仍有另一份安排的成员移出（R4）

定位：`schedule-service.js:73–98`，尤其 `Math.max(0, delta)`；`service.js:293–296`。

已复现具体顺序：建立同一师傅两份不重叠 active 安排 → 删除该师傅 guard（模拟损坏）→ 取消其中一份 → upsertGuard 以 delta=-1 创建 count=0 → removeMember 读取存在的零计数 guard，不查剩余安排 → 成员变 left，仍有 1 份 active 安排。

这是已通过实际 removeMember 路由复现的状态错误，不是仅猜测并发。缺失 guard 后新增也只从 1 起算，改派/取消同样存在低估风险。

要求：对所有 guard 写入路径制定一致的初始化/损坏处理规则。缺失时停止并报告，或在事务内可靠重建完整计数；不能根据本次 delta 创建零或一再当作权威基线。保留未启用旧项目的受控兼容方案，不用任意零值放行。增加两份及以上安排、缺失 guard 后取消/新增/改派、计数不一致、最终移出断言。

共同 guard 写入已加入，但仍须补创建/改派与移出的双向交错、事务冲突重试、各写入点失败回滚测试；现有串行测试不构成这些证明。

### F3 / P1：分页仍基于数据库第一页，产生假“没有更多”（R6）

定位：`schedule-service.js:29`、`:173`、`:205–229`、`:255–267`，以及 project/detail 的一次读取。

`find` 依然只有 `.where(...).get()`，随后内存排序/切片。超过 SDK 单次返回上限的数据从未取到，增加返回字段 pagination 不能解决。模拟数据库每次只返回 100 条，种入 101 条安排后，结果为 100 条、hasMore=false、nextCursor=null。

日期过滤在数据库截断后进行，也可能把后续页当天实际有安排误判为空。历史、可指派师傅集合亦存在同类风险。页面不处理 hasMore 或 nextCursor。

要求：使用稳定排序的数据库级分页或可靠完整获取策略；日期筛选与分页语义要兼容，不能漏掉当天数据；无效 cursor 不得默默回到首页导致循环或重复。路由透传分页，页面提供加载后续页或受控取全。测试必须在数据库替身中真实限制单页，再验证超过一页的成员/安排/历史均可到达。

### F4 / P1：执行人停用及回执重放的事务内权限缺口（R5、R7）

定位：`schedule-service.js:373–382` 及其他三个写接口相同开头；`service.js:50–83`。

师傅 users.status 已核验，但执行人账号只在事务前 identify 校验，事务里只查成员；已模拟外层鉴权通过后、事务开始前将管家 users.status 改为 disabled，实际 createSchedule 仍成功。

另外四种写操作均先 checkIdempotency、找到回执立即 return，然后才重新查项目/成员。已模拟外层鉴权后将管家成员变 left，同请求仍返回成功回执。外层校验不能代替承诺的事务内校验。

要求：先在事务里复核执行人当前账号、项目和成员权限，再决定回执重放或新写入；回执可跳过重复业务写入，但不能跳过当前权限。覆盖新增/调整/改派/取消及成功回执的角色撤销、成员移出、账号停用、项目失效。使用真实 index 离线入口验证业务码，不仅断言内部 error.code。

### F5 / P1：取消重试换号，表单实质改动反而不换号（R5）

定位：`pages/schedule-detail/schedule-detail.js:164–181`；`pages/schedule/schedule.js:32`、`:155–172`、`:204`；`utils/schedule-client.js` 写方法；`schedule-service.js` 回执负载。

- 详情页 cancel 调用未传 options.requestId，仍由客户端每次生成新号。模拟响应丢失后同原因重试，捕获两次不同 requestId；已经取消的首次成功将不能被第二次作为幂等成功识别。
- 新增/调整页面只在 onLoad 创建一次 requestId。内容或原因实质变更也不更新；首次成功但响应丢失后编辑内容会一直携带旧编号得到负载冲突。
- 当前 sanitizeForm 未 trim 内容、规范休息日顺序/去重，回执也未明确 expectedVersion、expectedConfirmed 的绑定语义。

要求：按一个确定业务负载维持操作状态，同负载、结果未知保留编号；明确失败可修改内容重新提交；若上次结果未知，先只读核对结果，避免换号制造重复安排。实质变更后才为新操作分配新号。取消也应保留输入、编号并防重入。使用字段白名单及真正的规范化规则，明确版本/确认条件。

必补实际页面重试测试：提交成功但响应丢失、相同内容重试、修改内容再操作、重复点击、取消重试。仅测试客户端“支持传参”不足。

### F6 / P2：云端页面仍显示本机说明、遗漏内容和只读导航（R2）

定位：`pages/project/project.js:30–44` 与 `project.wxml:4–25`，`pages/schedule/schedule.js:94–128`、`schedule.wxml:3`，详情页 cancel。

即使修正 F1 响应结构，project.js 映射也丢弃 content（已离线复现），施工内容在列表为空。project.wxml 仍无条件显示“本地虚构示例”“权限只作本地交互演示”、零值更新统计、现场记录标签及本机成员入口；不符合所称云端路径隔离。

普通项目成员的详情/历史按钮仍受 canManage 限制；反过来直接打开云端新增/编辑页时，代码忽略 ctx.isManager，非管家仍看到编辑表单。服务端拒绝写入不代表页面交互合格。表单错误/加载状态也未禁用保存。

本机详情页显示“取消安排”但一律调用云端 cancelSchedule，默认关闭时必然失败；本机编辑的“原因必填并入历史”文案并未对应保存逻辑。

要求：云端仅显示本轮已有的真实能力和字段；本机示例说明、记录/统计/成员路径按 mode 区分。开放合法成员的只读详情历史，只有管家展示编辑/取消入口；错误和加载时不可保存。云端工种/阶段选择器 index 与实际值保持一致。对于本机未实现操作，不显示可点击但必败的入口，也不能显示未实现的保存承诺。补真实页面数据和模板条件测试。

### F7 / P2：历史仍旧值错标新版本，阶段顺序和确认状态有遗漏（R8）

定位：`schedule-service.js:7`、`:440`、`:487`、`:526`；`utils/seed.js:4`；`schedule.js:163`；`schedule-detail.wxml` 历史区；实现说明第 2.2 节。

独立复现首次更新后的历史为 `(version=1,snapshot.version=1)`、`(version=2,snapshot.version=1)`，后者仍旧内容。交付说明“version 保存旧快照版本”没有落实。实现说明先说 version 是旧快照版本，随后举例却仍新号配旧快照，文字自身也矛盾。

要求定义不混淆的变更版本/快照版本语义（可以明确 beforeVersion/afterVersion 或保存每版完整状态），页面标注与实际内容相符，并避免重复版本键；历史必须能看施工内容和预计完成日期，目前模板未显示二者。

两处 STAGES 都把“竣工验收与交付”放在“保洁”之前，应恢复已确认顺序：保洁在前、竣工验收与交付最后。预计日期不一致勾选确认后再修改日期，目前保留旧 true；涉及日期变化应重置确认，使用户确认实际提交日期。restDays 中非字符串被过滤而非拒绝，需统一严格输入约定并测试。
