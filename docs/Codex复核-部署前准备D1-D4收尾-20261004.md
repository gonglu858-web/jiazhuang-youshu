## 3. 定点收尾 E1–E3

### E1（P1）：按实际存储字段修正取证白名单

位置：方案第 285、598–608 行，§6.2 S-3、§9.6.3–9.6.4；关联 §7.3。

1. `schedules` 没有持久化 `workingDays`。实际写入 `startDate/endDate/restDays`（`schedule-service.js:1058–1065`），施工日由 `workingDays(startDate,endDate,restDays)` 计算。当前白名单既取不到 `workingDays`，又禁止读取起止日期，无法构造占用映射 D。改为读取实际字段并明确推导步骤；不得把缺字段解释成零施工日。
2. `member_task_guard` 白名单漏 `projectId/userId/activeScheduleCount/version`。结构校验依赖计数/版本且需核对归属；`readGuardDoc` 明确检查计数与目录长度（`:194–207`）。写明真实集合名、完整必需投影及主键/字段归属交叉验证。占用集合写明 `schedule_occupancy`。
3. `app_admins` 不能写成泛指“绑定用户字段”：应为 `_id/userId/status`，primary 记录本身 active 与关联 users active 都须核对（`service.js:94–95`、`:113–114`）。邀请若需要申请人字段，应使用 `applicantUserId`，不是不存在的 `inviteeUserId`（`:265`）。
4. 审计仅 `_id/projectId/action/createdAt` 不能支撑历史代际判断。明确按既有 B0 最小投影取必要的主体 ID 与 before/after 锚点/项目元数据子字段；禁止读取完整 before/after，未发现证据不得提升成历史完整。
5. “任何 OPENID 派生值不得保存”与允许 userId 自相矛盾：现有 `u_…` 正是散列生成（`service.js:75`）。改为：原始 openid、令牌、绑定编号/摘要和签名链接不得取存；项目内关联必需的内部 userId/memberId 可在受控本地证据中最小化保留，不等于允许公开传播。删除含糊的“请求体 actorId 原值以外的任何凭据”例外；客户端 actorId 不构成可信身份。

只修字段说明和一致引用，不修改产品实现，不对历史证据执行删除或重写。

### E2（P2）：统一查询范围、计数范围和成员级首用判断

位置：第 284–289、357、628–630 行，S-2/S-3、R-6、§9.6.6，以及 MC-3。

- S-2 按项目过滤，却用“平台元数据计数”校验：A/B/C 当前分别 4/1/3 名成员，集合总计 8。不得将过滤结果与集合总数比较；只允许相同过滤条件的计数相互比较，记录观察时间，非原子结果差异标为待核对/INCOMPLETE，不推断数据损坏。
- S-3 是项目级全量扫描，不能写“命中 201 即停止”。项目合计 201 条可分布在多个均未超限的成员下。全量发现与每成员容量分开；按 workerUserId 分组后才应用 200/201 规则。若操作自身需资源上限，单列为取证未完成，不能伪装成成员容量超限。
- R-6 的 EMPTY 是“当前成员在已完整扫描结果中的 active 安排分组为空”，不是整个项目 S-3 都为空。否则项目中一名师傅有任务会误阻断其他成员的合法首用。
- 与 `scanActiveSchedules` 相同的只有分页大小/排序方式；它实际还过滤 `workerUserId`（`:283–290`），不能称项目级扫描“同参”。
- 独立读项继续；这类清单修正不要求重跑已完成的 A/B/C 记录查询。
