## 3. 定点修正清单

### D1：不要把业务查询路由当成零写取证入口（P1，影响 B0 工具选择）

位置：方案 §1.3（约第 56 行）；实现 service.js:72、:134。

`execute` 除 checkTransaction 特例外先调用 `identity`；identity 在首次见到账号时会写 users 和 registerIdentity 审计。因此 identify/listMyProjects 的业务查询主体虽是读取，完整入口并非无条件只读。requestBindingNumber 也写 users 和审计，不能列作 B0 的零写手段。

修正：
- 围栏表标明“查询主体只读，身份初始化可能写 users/audit_events”，区分公共前置逻辑。
- **B0 使用受控的管理端数据库只读查询，不调用这些业务路由取得身份或数据，不为核对而取号。**
- 账号状态/主管理员资格必须重验；证书涉及 active 安排责任账号的有效性时，不能仅因 users 未放入摘要就忽略账号状态的稳定性。

本轮未调用上述路由，不存在此次取证已产生注册写入的问题。

### D2：删除 M-b 下沿用新代码拒绝行为的旧句（P2）

位置：§2.2，约第 77 行：

> 且缺字段状态下无任何业务路由可写，本就无需维护态

该句仍把本地新代码的拒绝条件套到旧部署，并与 §10“不能把新代码缺字段拒绝当云端现状”冲突。

改为：
> 当前不执行补缺：云端旧部署未建立新围栏，且具体变更包尚未批准。旧部署可用性不能由本地新代码的缺字段校验推断。

另将 §3.1“多次 epoch 相等能证明新代码写路由无写入”改为“只观测采样值未变；只有在已证明全部相关写入遵守单调递增且无旁路回写的条件下，才支持期间无相关提交的判断”。不以此单独证明排空。

### D3：恢复可定位的完整 S/R/B0 清单（P2，执行说明缺失）

位置：§6.2、§7.2、§9.6 及 MR-2/MR-5。

当前只写“沿用上稿 S-1…S-7”“沿用上稿 B0-1…B0-8”，但同一路径已经被本稿覆盖；正文继续引用 R-6、R-1…R-12、S-5，却未保留对应完整表。§9.7 是状态表，不能替代范围/分页/投影/输出/停止条件的执行规范。

修正：
- 在当前方案恢复 S/R/B0 的具体表，或链接到真实存在、不可变且包含原表的版本；不能只链接同一已覆盖文件。
- B0 至少明确目标 A/B/C ID、集合与字段白名单、分页/结束条件、错误标记、敏感字段剔除、证据输出、只读调用方式。

这不阻止 Codex 按既有授权与受控查询推进 B0；但不应将压缩后的本文交给实现者称为完整执行规范。

### D4：小范围歧义及标题勘误（P2/P3）

1. §5.2 漏列 epoch=0。现实现 schedule-service.js:636 接受非负整数，service.js:52 也拒绝负数而非零。**已有合法 0 不应被误当缺失或擅自修成1**；缺失字段填入什么值及哪个事务负责递增，放入 B0 后的具体变更包，不在本轮执行。“不把正整数改回0”继续保留。
2. §6.5 第二行处于“不满足时”列却写“不阻断”，会被理解为目录损坏也放行。明确改成：“角色/退出状态本身不阻断；锚点/目录一致性失败仍阻断恢复。”
3. §8.4 明确成功回执重试分支：先核验当前身份/权限，再识别同轮次同输入已提交结果；不在回执返回前强制要求 maintenance/未消费/旧 epoch。首次恢复分支才要求这些前置，避免成功后合法重试被自己的 ready 和已消费状态拒绝。MX-5 表述为“拒绝二次执行或消费”；合法同输入重试按 MX-6 返回原结果，两者不矛盾。
4. §11.6 标题“7项”改成“10项”；“全部在内存合成数据上运行”改成“拟在内存合成数据上运行，尚未执行”。实际唯一用例数53正确。
5. §7.2 写明 monthOf(date) 与桶 month 一致；保留空桶规则不放宽错月/非字符串 holder 的校验。

以上是明确文字与执行分支的定点收尾，不要求设计新的业务功能或重做已关闭代码测试。
