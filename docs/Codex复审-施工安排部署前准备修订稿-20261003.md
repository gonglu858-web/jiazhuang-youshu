## 2. 必须修正的具体内容

### P1：补缺顺序与维护进入行为仍有冲突（§2、§3、§5）

当前维护入口缺 epoch 会写为 1，但 A-1 将 schema 缺失与 epoch 缺失/0 捆绑，会把“成功进入维护、schema 仍缺失”的项目排除在补缺路径外。

裁决：
- schema、epoch、成员锚点分别分类；schema 缺失但 epoch 已为合法正整数，不因 epoch 已存在就跳过 schema 缺失核对。
- 保留所有合法现值，不把 epoch 改回 0，不降低代际；非法值、部分锚点、无法证明历史非零代际不存在，转人工。
- 补缺仍只针对已证实无安排、无 guard、无历史非零代际的目标；不得据本规则自动处理非空或未知状态。
- 将“修复前观测报告”与“最终恢复证书”分开。所有计划内元数据写入完成后，才签发对应最终 epoch 的恢复证书；后续任意相关写入使旧证书失效。
- initDir 的合法首用路径要先有合法 generation=0 锚点；“锚点和 guard 都不存在即可直接 initDir”不能写成操作说明。
- 只改设计，本轮不补字段、不改变维护状态。

### P1：成员异常判定必须限于其业务关系（§6 R-12、MR-3）

项目本来就包含管家、负责人、主业主及历史退出成员。不能因为所有成员中有人没有师傅角色/工种、已经 left，就全项目禁止恢复。

裁决：
- 对 active 安排实际引用的责任成员，检查成员/账号有效、师傅角色与安排工种匹配；不满足则阻断。
- 对无 active 安排的非师傅或历史成员，检查其锚点与目录的一致性，不把角色或退出状态本身当损坏。
- 孤立 guard、错误代际、非空残留目录仍须检出；不因此自动改成员身份。
- 增加“无任务的管家/主业主/left 成员不误报”正向例，以及“active 安排引用 left 成员必须阻断”反例。
- 200 条容量按责任成员目录计算；项目全量扫描不能在全项目第 201 条就认定某一成员超限。

### P1：占用比对需允许当前实现保留的合法空月桶（§7、MO-*）

当前 writeBuckets 明确保留空桶（days={}）。取消或改派后，实际桶键集合可能多于 active 安排推导出的非空桶键集合。直接要求两者桶键集合完全相等，会把正常操作产生的数据判坏。

裁决：
- 全量枚举并验证所有桶的 schema、主键、项目、工种、月份与日期归属。
- 对合法桶展开非空日期占用，按 (projectId, trade, date) → scheduleId 与全部 active 安排推导映射严格相等。
- 结构合法且 days={} 的保留桶单列，不形成多余占用，不删除。
- 错工种/旧逐日键/未知键/无效结构不能仅因“空”而被豁免；重复占用、错误日期归属、孤立非空占用继续阻断。
- 增加取消后保留空桶、跨月调整留下空桶的正向例。

### P1：恢复证书方向接受，但必须明确可信来源、覆盖内容和使用协议（§8）

仅有报告日期或客户端传入证书字段仍不足以恢复。epoch 稳定只能覆盖确实参与同一围栏的写入者。

固定要求：
1. 证书由受信管理端核验流程生成，持久化在服务端可验证的记录中；客户端只引用证据 ID，不能自报通过。记录载体尚未实现，不据此新增资源。
2. 绑定环境、项目、维护轮次、当前 epoch、精确 schema 版本、核验规则版本、完整性结果、写入者覆盖证据；摘要覆盖项目/成员/锚点/目录/安排/占用核验输入，不仅占用映射。
3. 有效期固定为签发后最多 10 分钟，使用服务端时间，未来签发时间拒绝。时效是附加条件，不替代 epoch/轮次/完整性。
4. 最终有界事务核对当前可信执行人、管理员资格与账号启用、项目允许范围、maintenance、轮次、epoch、证书通过/完整/未失效/未使用和预算；原子记录恢复结果及证书消费，更新 ready 与 epoch。
5. 重试仍核验当前身份权限；同轮次同输入只能返回已记录原结果，不二次推进 epoch。不同输入不能复用旧结果。
6. 分阶段/分成员证据必须最终聚合为完整项目证书。写入者覆盖不明时，不得退化成“只核验部分成员就恢复整个项目”。
7. 邀请创建/申请仍可写的事实保留。明确哪些邀请字段属于就绪证据依赖；若依赖它们，必须另有稳定性依据，不能声称所有集合均被 maintenance 冻结。

### P2：消除剩余事实与流程表述矛盾（§1、§3、§9）

- §1 将 createInvitation/applyInvitation 写成改 project_members，应与 §3.4 统一：这两个动作涉及邀请及其审计，不直接新增成员；批准才改变成员。
- “新代码所有写入都递增 epoch”改为逐路由覆盖表，区分安排/成员受围栏动作、仍允许的邀请动作、账号与管理员状态变更、控制台/脚本等旁路。
- 多次 epoch 相等、停发预览或固定等待时间都不能单独证明旧请求已排空；这些只能作为观测。最终恢复必须有明确的写入者约束。
- B0 不以这些写入设计补充或新授权为前置；独立读项可继续。数据非空意味着停止自动迁移，不意味着停止其余只读取证。
- 查询失败不得报零；集合不存在是单独事实。旧部署观察不能提升为稳定迁移基线。
