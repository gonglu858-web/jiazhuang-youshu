## 4. 读取与结果契约

全部前置门槛通过后，应用层至多一次固定collection/doc/get读取，字段最小化为_id、openid、status；不能list/where全表、读原users、app_admins、项目、审计、绑定码、邀请或存储。不调用transaction/add/set/update/remove，也不能为了留核验证据写云端审计。云平台自身调用日志/计费不等于业务零副作用；不宣称零费用或平台零日志。

读后和成功返回前重读时钟，过期或无效即不可确认；异步read必须await。数据库错误/权限错误/超时/异常形状不得当作不存在。已发读取的事实保留，不能因为返回失败报告零调用。SDK可能内部重试，应用层一次get不等于平台请求恰一次。

建议净化输出固定schema、核验轮次、服务端时间、内部userId及：
- identityConfirmed：可信上下文/目标/口令/时间门槛是否满足；失败时不携带可采信的身份结论。
- registrationState：仅ACTIVE、ABSENT、DISABLED、MISMATCH、UNKNOWN。
- recordMatched：对实际记录主键与openid和当前上下文是否一致给出布尔/未核实语义，禁止回传原值。
- readAttempted：仅实际进入get调用后为true；错误不冒充零读取。

ACTIVE须恰一条、主键及openid精确匹配、status=active。明确无记录才ABSENT；受支持SDK确切“文档不存在”形状需要单独验证，未知异常/未知status/多条/字段缺失统一UNKNOWN。DISABLED只接受明确已支持的停用状态且身份一致；openid/主键不符归MISMATCH。读失败可保留已可信取得的身份事实，但registrationState必须UNKNOWN，不能当作登记或P准入成功。整个响应逐字段投影，不透传原始SDK异常、环境变量或请求。

本轮记录不以business-test-participant-record/1直接伪装P证据。未来真实核验、人工本人对应、必要登记与回读完成后，再形成明确来源的新P参与者记录，保留原核验轮次和来源关系。内部userId是标识而非密码，仍只在核验参与者/受控执行资料中使用；公开交接展示尾号。
