## 2. H1 / P1：未知结果仍可直接清除；响应异常被误判明确失败

定位：`miniapp/miniprogram/pages/schedule/schedule.js:231、298、336`；`schedule-detail.js:222、230`；`utils/schedule-client.js:34`。

独立复现实际页面 save() → 实际服务创建成功 → 模拟网络响应丢失。页面进入 unknown 后，点击“我已核对”只执行 discardPending：清空状态并换 requestId，没有读取、没有恢复已创建安排。随后修改日期并保存，数据库出现两份安排。这条路径使用页面公开事件，不是直接绕过页面校验调用内部保存。

另一个复现：服务端已提交后抛出客户端现有的“云端响应异常，请稍后重试。”，页面将其置为 failed；仅含 errMsg 的 SDK 异常也不受当前 message 正则可靠覆盖。不能用“未匹配超时字样”推断服务端没有提交。

要求：

- 去掉无证据清除 unknown 的出口，或真正核对并恢复到已有安排结果；仅点击“我已核对”不构成程序核对。取消页同样处理。最小方案可保留锁定及原请求重试，不新增云接口。
- 区分本地发送前校验、可信明确业务拒绝、传输/响应未知。客户端传递可靠错误类别；不依赖文案正则把其余一律当业务失败。响应缺失/畸形、无 code 的拒绝、errMsg 对象均需覆盖。
- 保留完整提交快照（项目、安排 ID、版本、requestId、表单/原因），重试不再取易变页面字段；在途时不允许清除状态或开启第二次不同操作。
- 页面—客户端—实际 service 离线联测：服务端已成功但响应丢失，原号重试只留一份安排；取消同理。覆盖任何提供给用户的恢复按钮，不能只检查 requestId 字符串相同。

## 3. H2 / P2：明确失败后修改表单仍无法保存

定位：`schedule.js:190、254、301`，`schedule.wxml:35`。

独立复现：本次施工内容留空提交，收到“请填写本次施工内容”；通过 input 填入有效内容后，error 没有清除。save() 遇 error 直接返回，保存按钮也被 error 禁用，实际请求次数仍为 1。与“业务错误后允许编辑新操作”的交付说明不符。编辑原因校验也有相同风险；取消明确失败后同样需检查可恢复路径。

要求将初始化/权限等阻断错误与可纠正表单/提交错误分开。明确失败后允许纠正并重新校验提交，同时保留 H1 的 unknown 锁定；不能简单把所有 error 清空而解除身份或初始化失败限制。补通过实际 save() 和输入事件的回归，不能直接调用 saveCloud() 绕开门槛。
