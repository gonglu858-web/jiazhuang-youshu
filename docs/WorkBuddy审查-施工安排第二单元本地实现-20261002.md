## 二、返修项

### R1 / P1：详情页 WXML 不能编译

定位：`miniapp/miniprogram/pages/schedule-detail/schedule-detail.wxml:12`。

`(schedule.restDays || []).length` 与模板内 `join()` 表达式不应留给 WXML 执行；当前编译器直接报错。页面已注册到 app.json，即使功能入口禁用，也不能以此绕过打包编译问题。

要求：在 JS 中计算是否有休息日及显示文本，模板只绑定可编译字段。修复后完整执行 wcc/wcsc，记录 8 个路由的实际模板和样式编译结果，不能用 JS 语法或文件存在检查替代。

### R2 / P1：云端页面依赖本机身份，且存在回退本机保存与旧入口回归

定位：`pages/schedule/schedule.js:17`、`:99`，`pages/project/project.js:10`、`:36`，`pages/schedule-detail/schedule-detail.js:15` 及对应模板。

实际问题：

1. 页面先读取 store 并调用本机 `context(state, projectId)`。真实云项目不在示例种子中时，在任何云请求前就报“当前示例账号无法访问此项目”。云端新增安排也未独立取得完整云端上下文；权限、师傅名单、切换工种仍受本机数据影响。
2. `save()` 根据提交瞬间的入口开关选择云端或本机，而非保持页面数据来源。已复现 `mode=cloud` 时关闭开关，点击保存却写入本机并提示“已保存到本机”。
3. project 的新增按钮与编辑按钮都指向详情页；新增实际生成 `schedule-detail?...&id=`，无法进入新增表单。旧本机安排没有 status 字段，而详情操作要求 status 为 active，已有编辑流程受损。
4. 项目模板仍使用本机通知、日期字段、更新统计与记录入口；云端返回字段不匹配。只读成员缺少可用详情/历史入口，详情权限使用本机身份而非云端上下文。重新读取失败或权限丢失时，旧详情与历史未清除。
5. 本机历史和云端 history.snapshot 的结构不同，需分别转换为明确的页面模型。

要求：固定且明确的 local/cloud 数据来源；真实云项目不依赖示例身份；每次请求仍校验入口与权限，但云路径受限只能停止，不能切换成本机保存。新增、详情、调整、改派、取消、只读历史均形成完整导航。云端页面不得显示本机统计或把示例记录混入。保留原本机试用流程，并修复失权后的旧数据展示。

必补测试：非种子真实形态项目 ID、云端与本机身份不一致、工种切换筛选云端师傅、提交前门控变化零写入、非管家只读入口、失权清理、本机新增/编辑/历史完整回归。

### R3 / P1：更新安排携带 _id，真实 SDK 拒绝

定位：`schedule-service.js:76`、`:386`、`:431`、`:470`。

调整、改派、取消将包含 `_id` 的 current 展开到 updated，随后送入 `doc(id).update({data: updated})`。本机现有 SDK 的 DocumentReference.update 在发送网络请求前即拒绝此参数：`INVALID_PARAM / 不能更新_id的值`。当前内存假数据库允许此操作，掩盖了问题。

要求：采用允许字段组成的更新补丁，排除 `_id` 及不应重写的创建字段。新增 SDK 契约测试，假数据库也必须拒绝更新 `_id`。覆盖调整、改派、取消，不能只验证新增。

### R4 / P1：成员任务保护记录缺失时放行；共同事务冲突协议不完整

定位：`schedule-service.js:109–123`，`memberAccess/service.js:293–295`。

已用实际 createService.execute 路由复现：先建立 active 安排，再令对应 guard 缺失，removeMember 仍将成员改为 left，安排保持 active。当前缺失即视为无任务，负计数被 Math.max(0, ...) 掩盖，计数类型及完整性无校验。

安排创建/改派写 guard，而移出只读取 guard 并写成员，不写共同保护记录。现有测试没有证明所需并发序列及事务重试，本轮不据此声称真实 CloudBase 已发生竞态，但不能把任务要求的共同保护协议记为完成。

要求：明确未启用项目兼容与 guard 初始化条件；已有任务但 guard 缺失/损坏必须停止或经过可靠一致性核验，不能直接当零。建立创建、改派、取消、成员移出共享的事务冲突保护；计数必须是合法非负整数且与状态变化一致，不能截断负数掩盖错误。关闭客户端入口不能撤销已有任务的移出保护。

必补测试：实际 removeMember 路由、有/无/多份安排、最后一份改派或取消、缺失/负数/非数值 guard、创建与移出及改派与移出的两种交错顺序、冲突重试、任意写入失败全部回滚。需证明最终不会留下“在席任务指向已移出成员”。

### R5 / P1：客户端重试不复用提交编号，回执身份边界与参数门控不完整

定位：`utils/schedule-client.js:20–35`、`:55–77`；`schedule-service.js:84–102` 及各写接口。

1. 每次调用写方法都生成新 requestId；网络结果未知后的同内容重试不能找到原回执。
2. 回执键只依赖 requestId，负载不含执行人。已复现第二位管家使用相同编号/内容得到第一位管家的回执；事务内回执返回早于最新项目/成员权限核验。原始 form 直接参与摘要，也未形成明确的规范化及 expectedVersion 绑定语义。
3. `listSchedules` 的 filters 可以覆盖 projectId，内部 call 的 data 又可覆盖 action。离线已捕获允许项目检查后实际发出另一个项目的 removeMember 请求。此为客户端入口限制失效，不等于已经绕过服务端权限。

要求：同一操作的相同提交负载在结果未知时保留稳定提交编号；不同内容/新操作显式换号。服务端回执绑定账号、项目、动作及规范化有效负载，明确版本条件，重放前核对当前访问权限。过滤参数使用白名单，action/projectId 不可被调用参数覆盖，最终发送边界再核验目标。

必补测试：响应丢失后重试只写一次、不同账号同编号隔离、同编号不同内容拒绝、权限撤销后重放、非允许项目/动作覆盖零请求。

### R6 / P1：日期查询返回私有结构，分页缺失可残留占用

定位：`schedule-service.js:198–225`、`:261–265`，`service.js:305–315`。

带 date 的 listSchedules 直接返回数据库文档，未调用 publicSchedule；不带 date 返回 id，带 date 只有 _id。页面实际使用日期过滤，因此安排 ID 与导航不可靠，并暴露额外内部字段。

任务/契约中的 cursor、limit 未形成接口实现；成员、安排、历史、占用均假设一次 where.get 取全。本机 SDK Query.get 默认 limit=100。取消按单页查询删除占用，不能覆盖允许的最长 365 天。离线将每页限制为 1，取消 3 天安排后仍剩 2 条占用；这是人为分页复现，并非测量云端限制。

要求：所有返回分支统一公开字段；实现稳定排序、分页契约与页面加载行为。释放占用优先按旧安排确定的施工日逐个确定性 ID 核对并释放，或采用经过证明的完整获取方案；不得将查询首页当完整集合参与保护或释放。说明最大范围的事务资源限制及本地校验边界。

必补测试：超过一页成员/安排/历史/占用，日期查询字段一致，取消/调整完整释放，失败回滚后无部分占用残留。

### R7 / P1：业务错误穿过云函数入口后丢失，事务身份核验不完整

定位：`schedule-service.js:13–18`、`:252`、`:365–367`，`memberAccess/index.js:12–15`，`service.js` schedule 路由。

安排模块抛普通 Error 并附 code，云函数入口只识别 AppError。用真实入口函数配合离线数据库已复现 VERSION_MISMATCH 被转换成 SERVER_ERROR，用户无法得到契约定义的冲突提示。

内容调整仅在责任人或工种改变时核验师傅；已复现师傅工种被撤销后仍能调整安排。目标用户 users.status 不检查，已停用账号仍可被安排。操作人状态也需在写事务内复核，不能仅依赖事务前 identify。getScheduleContext 的负责人分支绕过原 projectAccess 范围检查，模块自身只验证项目 active，需统一项目读取边界。

要求：共享受控业务错误类型或明确白名单映射，不透传任意底层异常；按操作语义在事务内核验当前项目、执行人、责任师傅账号/成员/工种。取消或将任务从失效师傅改派出去应有正确解困路径，不把重新核验变成无法撤销任务。统一所有读取接口的项目范围权限。

必补测试：走 service 路由及真实 index 返回结构验证 VERSION_MISMATCH、SCHEDULE_CONFLICT、WORKER_INVALID、NO_ACCESS；停用账号、撤销角色/工种、事务前后状态变化、负责人访问非目标范围项目。

### R8 / P2：阶段、日期确认、历史版本和输入契约尚未闭合

定位：`schedule-service.js:7`、`:228–248`、`:280` 及各 writeRevision 调用、表单页面。

- STAGES 仅 10 项，遗漏已确认的“竣工验收与交付”，需与 11 阶段主规则一致；本轮不新增该阶段验收业务。
- expectedConfirmed 的判断方向不对，调用始终传 false，页面也无对应确认。已复现预计完成日期不同于结束日期仍直接保存，未满足已确认的二次确认要求。
- 变更历史外层 version 使用新版本，snapshot 却保存旧版本；页面显示“第 2 版”可能展示第 1 版内容。应定义前后版本及快照语义，保留旧版本全部有效字段，并一致显示当前和历史。
- form=null、restDays 非数组、未知字段等未形成严格输入规则；日期范围在展开日列表之后才检查上限，应提前拒绝；日期计算与北京时间业务日期规则需明确。

要求：同步技术契约与实现，增加相应输入、版本与确认测试；不能仅改文档把未达成的已确认规则取消。

更新实现说明的集合字段、确定性键、索引草案、接口分页、错误映射、幂等、历史及事务保护协议。补齐新集合客户端直连拒绝规则的本地草案和未来启用前置检查，保持未应用状态。对本轮尚未实测的真实事务容量/冲突语义明确标为后续验证，不能写成已验证。
