## 2. U1 · P1：业务码不能证明原未知提交未发生

位置：`miniapp/miniprogram/utils/schedule-sandbox-client.js:139–160`、`:825–829`。

现有注释称业务拒绝均在回执核验之后，因此可清除原 envelope；与实际 service 不符。`schedule-service.js` 的 `tryReceiptReplay` 先执行 `verifyActorInTransaction` 和 `assertProjectWritable`，再读回执；外层 `identity` 也先于回执。故 NO_ACCESS、IDENTITY_DISABLED、PROJECT_NOT_WRITABLE 等可以在未读原回执时返回。

**已复现真实 main 路径：**施工新增已成功提交但响应丢失；之后将合成项目转 maintenance；`resumePending` 返回 PROJECT_NOT_WRITABLE，被标为 definite 并清空未决记录，数据库里原安排仍为 1。窗口拒绝 SANDBOX_EXPIRED 测试通过不能代替此分支。

**修复：**区分首次已知拒绝与“原结果未知后的重试拒绝”。后者不因业务码名称清掉原结果；只有足以确认原请求结果的证据才结束未决状态。最小安全实现可让重试的非成功响应继续保留原 envelope，明确本次拒绝与原提交仍未知，不修改 vendor 权限顺序。

**验收：**真实已提交回执后响应丢失，再维护/失权/停用，保留原编号与快照且不放开新写；恢复权限后同号返回原结果；首次确定的日期冲突仍可修正。

## 3. U2 · P1：历史 identify 缓存不能当作当前会话的可信账号

位置：`utils/schedule-sandbox-client.js:327–355`、`:627–653`、`:716–735`；页面 onLoad/onShow。

恢复只读取本地 `account:<env>:<round>` 字符串，没有向当前会话核实身份。`envelope.accountId === accountId` 是两个缓存值的比较。现有 T2.4 测试直接把缓存改成另一个账号，再断言看不到原请求；这验证了分键，未验证实际账号变化如何被发现。

**已复现：**在共享存储的合成场景中，甲留下待恢复请求；重进页面的传输端身份将返回乙，页面却没有调用 identify，直接发送甲的 createSchedule 原编号/载荷。这里没有实测微信跨账号缓存方式，不能据此声称已发生真实越权；缺口是代码和测试没有建立“缓存绑定仍是当前执行人”的依据，不能把该边界写成已验证。

**修复：**在当前会话恢复前建立可核验的身份前置，身份未确认或变化时保留旧 envelope、拒绝恢复；不要相信表单 actorId。身份刷新应能独立完成，不能被旧未决记录锁死，也不能把新 identify envelope 写入账号键时覆盖旧未决记录。若采用平台隔离作为前提，需要明确证据和适用边界，不能只手工更改缓存模拟“可信切换”。

同时更正 READ_ONLY 中 identify“不会产生写入”的说明：真实 `service.identity()` 首次见账号会写 users 和 registerIdentity 审计。其重复调用是否有安全保障应依据该实际逻辑说明，不能称零写；本轮仍只做本地模拟。

**验收：**传输层实际返回不同身份，业务恢复零发送；同身份重进可恢复；身份请求失败保留原记录；身份绑定存储部分失败时不能混用旧身份；刷新不会覆盖任何已有未决记录。无需新建通用登录系统。

## 4. U3 · P1：目标为空仍可恢复，envelope 内部关系未校验

位置：`utils/schedule-sandbox-client.js:358–383`、`:466–478`、`:740–750`。

**已复现两例：**

1. 原请求目标为 p_sbx_target；当前配置将目标清空，开关仍开启。`:741` 只有两者都非空才比较，恢复仍把原项目写请求发出。普通提交会因未登记项目拒绝，恢复却绕过这项门槛。
2. 将有效 envelope 顶层 action 从 createSchedule 改为同类的 cancelSchedule，snapshot 仍是原 createSchedule 且摘要有效。结构校验接受，恢复覆盖 action 后实际发送 cancelSchedule。单键存储解决了半写拼接，但没有自动保证顶层与快照一致。

**修复：**按动作执行恢复前置；项目必需动作当前登记为空必须停止，非空也须与原目标严格一致。明确身份/建项目等无项目动作的例外，不把当前目标补进原本无目标的提交。

校验 envelope 的 action/projectId/accountId/键归属/round/env 与快照关系、已知动作和字段类型；写后读回核对完整关键绑定，而非只查 requestId 与快照摘要。损坏即停止，不覆盖/修补成另一请求。该校验用于损坏检测，不把本地摘要宣称为防恶意篡改的安全签名。

**验收：**目标从非空变为空时零请求；同目标恢复正常；动作/项目/账号与快照或存储键不一致时均零请求；非项目动作正常。保留本轮单键与半清理测试。

## 5. U4 · P2：未收到事务成功返回，不等于事务未提交

位置：`cloudfunctions/scheduleSandbox/project-guard.js:214`、`:244–246`、`:280–284`。

`committed` 只在 `await runCreate` 正常返回后设真。SDK 可能已完成提交、但提交响应未被调用方收到；这时 Promise 拒绝而 committed 仍为 false。

**本地故障注入：**真实创建事务正常提交后，让 SDK 替身抛出响应丢失错误；项目与回执各为 1，返回文案却是“事务未提交，未留下半套状态”。本例仅模拟该故障边界，不冒称 CloudBase 已实测。

**修复：**没有明确回滚证据时只报告“未确认结果/需按原编号核对”，不要从本地布尔值推断未提交。已确认提交后读取失败的文案保持正确。无需修改创建协议或业务算法。

**验收：**提交后读失败、提交确认响应丢失、事务写入明确失败分别说明事实；同号重试能取回已提交结果、不多建项目，历史证据保留。
