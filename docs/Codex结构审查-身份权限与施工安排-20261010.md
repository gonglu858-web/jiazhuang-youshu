## 2. 已具备的结构及其边界

| 主题 | 本地代码证据 | 能得出的结论与限制 |
|---|---|---|
| 身份来源 | `memberAccess/index.js` 的 `cloud.getWXContext()`；`service.js:72` 的 `identity` | 身份由云端上下文取得，不能靠请求体填角色冒充。首次身份解析会写 users 和登记审计，不能把所有名称似查询的业务路由当作纯只读。管理端取证仍应走独立只读路径 |
| 项目与操作权限 | `service.js:97/106/112` 的 projectAccess/managerAccess/requireAdmin；`schedule-service.js:611` | 项目访问与管家写权限分开；负责人身份不自动替代管家。安排写事务内重验账号、项目、成员。不能据此称每一条成员管理路由都采取相同事务内账号复核策略 |
| 写入完整性 | `schedule-service.js:1030/1082/1169/1218` 四写 | 安排、目录、占用、修订、审计、回执通过同一个事务流程维护；调整/改派/取消检查版本，避免静默覆盖旧编辑。平台事务行为与实际冲突重试仍须验证 |
| 重复提交 | `schedule-service.js:911` 及四写中的 checkIdempotency/saveReceipt | 服务端回执绑定账号、项目、动作与输入；同号重发不是再建一条。客户端必须保留原编号和原输入，见 A1；非幂等成员动作不能照搬安排重试策略 |
| 移出成员 | `service.js:319` removeMember + lockDirForRemoval | 通过成员目录、安排扫描和项目版本核对未完成安排；有任务则拒绝。未来加入整改/验收等任务后，须相应扩展“未完成任务”判定，现阶段不能称已覆盖全部业务任务 |
| 维护状态 | 项目 scheduleEpoch、目录 fence 与事务内校验 | 相关安排/成员写入形成冲突约束。身份登记、取号、部分邀请路径仍可能写库；维护不是全环境停写。旁路控制台/脚本不能由这些守卫自动约束 |
| 测试隔离 | `scheduleSandbox/index.js`、`collection-map.js` | 固定映射11个前缀集合，入口先校验再取数据库，事务也走映射。仍是同一 CloudBase 环境内的代码隔离，不是平台管理员权限隔离 |
| 前端职责 | 普通 schedule 页 + schedule-client；独立 schedule-sandbox 页/客户端 | 页面负责交互、客户端组包，后台负责权限与业务。普通页面还兼容本机示例；独立副本是测试工具，不能作为正式团队页面已经接通的证据 |

服务层通过注入 db/时钟便于本地验证；这提供了验证接缝，也要求测试替身忠实于真实 SDK，不能只凭测试数量验收。此前反复出现的夹具和协议接线问题，应通过真实页面/入口到服务的贯穿样本控制。

## 3. 必须在相应入口放行前解决

### A1：普通施工页重进后丢失未知提交（正式施工入口前；不阻断仅登记制品准备）

位置：`miniapp/miniprogram/pages/schedule/schedule.js:46/51/284/340/349`。

当前 pendingRequest 只在 Page.data；onLoad 新建 requestId。同页超时重试会保留原编号，但退出重进没有读取持久未决记录的逻辑。

独立证据加载真实普通页面与真实 schedule-client，仅将 wx、入口配置和时间/随机环境作为合成夹具：

- 第一次 createSchedule 超时，页面 pendingRequest=unknown。
- 同页 retryPending 发出原编号（保护成立）。
- 创建新的页面实例后 pendingRequest=null，同样内容能以新编号发送。
- 全程页面持久存储写入为0；合成请求共3次，未加载真实 SDK。

这证明跨页面未决保护缺失，**不证明已经发生云端重复数据**。安排占用、版本等服务端保护仍可能拒绝第二次请求，但新编号已不能作为第一次请求的回执恢复，不能据此推断第一次没有提交。

处置：普通源入口保持关闭；将正式页面的跨重进未决恢复单独列为后续任务，沿用已验证的账号/项目/原编号/原输入绑定原则，未知时停止、核对，不提供清缓存绕过。不得直接复制全部测试驱动到业务页面。本报告不下发实现，也不重开独立副本已验收的持久 envelope。

### A2：恢复与停用能力是正式试用门槛（既有缺口）

现有 ready 恢复被明确阻止；本次未验证独立数据与影像备份恢复。正式项目仍需达到已确认的“最多补录最近1小时、24小时恢复核心访问”目标，并通过隔离演练。Git 只保存代码，不能证明业务数据已可恢复。

关前端不等于关服务端；部署包回读、关闭包、在途请求处理须列入实际执行包。登记、管理员初始化、施工测试分步确认，不以本报告作为写入授权。

## 4. 可以后续改善，但扩大使用前应核验

### B1：对外分页不等于后台工作量有界

`schedule-service.js:448/505/554` 的列表及历史列表先 paginatedFetch 取齐，再内存切页。独立合成250条记录，limit=1 时仍查询3页（100/100/50）；请求下一页再次查询3页。

这不是本次发现的数据错误，也没有实测平台超时或金额；它证明查询成本随历史量增长，客户端小页不能限制后台读取量。每成员 active 上限200也不限制项目历史安排总量。

先用计划中的试点数据量核验耗时/读取量，再决定是否改为数据库侧游标分页及日期筛选索引。不在本轮引入新缓存或搜索系统。超预算应明确停止，不能静默截断成“全部数据”。

`service.js:32` 通用 find 是单次 get，项目/成员/邀请列表没有完整分页契约；须在试点规模表内注明并在扩容前验证，不能从当前少量样本推出永远完整。

### B2：规则重复与文件规模

原型 business.js、云端 service/schedule-service、测试副本 vendor 存在不同用途的规则副本。vendor 有受审来源哈希是优点；后续修改须保持来源与制品一致。无需为了目录好看立即拆文件；只在新增业务时明确一份云端权威规则、页面显示契约及必要测试，避免三处独立维护同一业务结论。

### B3：权限变化期间的保证范围

安排写事务内重验 users 状态；成员管理的 managerAccess/requireAdmin 分别重验成员或 primary，不统一重验操作者 users。现有业务未提供统一停用账号入口，本次没有复现外部停用竞态。

未来若提供账号停用、管理员切换等控制，须明确在途写如何与权限变化互斥并添加同事务核验，不能把首次 identity 检查当作整个请求期间持续有效。本项是静态边界说明，不宣称已发生越权，也不把未提供的停用功能加入本轮开发。

## 5. 需要真实环境验证的项目

1. 微信身份与角色：受审目标本人登记、管理员另行初始化；不同账号验证项目隔离、师傅不能写管家操作、移出后不能再取项目资料。
2. 最小施工链：管家创建一条安排，师傅查看，管家修改、改派、取消；手机显示、返回结果和管理端记录一致。
3. 失败与并发：响应丢失后按原编号核对、同号两笔、不同号冲突、版本冲突、安排与移出成员竞争；合成事务测试不能代替真实并发。
4. 平台与部署：实际 SDK/依赖、事务回执/回滚/重试、索引查询、时间及大小限制、IAM、当前额度费用；历史只读成功不代表写权限和事务已验证。
5. 停止与恢复：两端关闭、未知写结果留证、独立备份恢复。前缀集合与生产原集合共用环境，执行包必须保持明确目标。

此前已有资源/只读查询证据的事项继续保留，本报告不改称“项目从未验证”。本次未联网复核其当前状态，亦未新增相关通过结论。
