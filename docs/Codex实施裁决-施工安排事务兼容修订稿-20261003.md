## 2. 实施必须修正的安全路径

### 2.1 完整锚点配对和状态机

- guard 增加 taskDirSchemaVersion/taskDirGeneration（或含义相同的 schemaVersion/generation），与成员锚点精确匹配。两侧类型、范围、项目/成员标识错误均拒绝；不得把 undefined、NaN、负数或零版本宽松转换为正常。
- generation=0 且 guard 缺失的首次路径单独处理：实际扫描必须为空，事务内重读仍是同一未初始化状态，才能原子建立 generation=1 的 guard 和锚点。没有 guard 时不可读取 fenceVersion+1；明确以首次 fence 值建档。
- generation>=1 且 guard 缺失拒绝；历史缺锚点成员拒绝自动初始化。guard 属于旧代际/错误成员，即使数组自洽也拒绝。
- 新成员批准加入、重新加入、负责人创建项目、指定管家产生的成员记录分别列影响。重新加入保留已有代际及目录；缺历史字段走维护准备，不通过重新加入顺便清空任务状态。
- 正常业务不重置代际；受控修复若重建目录，代际必须增加、围栏不倒退，原子更新两侧。不能在后续维护中把所有成员重新写成 generation=0。维护脚本须幂等且可接续。

### 2.2 先判断快照是否过期，再判断一致性

修订稿 §3.2 第(4)步在验证围栏未变前，将扫描与旧目录差异直接报 GUARD_INCONSISTENT，会把正常并发创建/取消误判成损坏。

实施顺序：

1. 通过可信身份和项目权限初检，读取项目模式/schema/epoch、相关锚点和 guard 的前置状态。
2. 在事务外扫描相关成员实际 active 安排，记录ID集合；重扫必须重新读取所有前置状态，不能只重查 schedules。
3. 开始事务，重新校验身份/项目/成员、锚点/guard配对与围栏。先确认前置版本仍相同；版本变化作为 STALE_SCAN，退出事务，在外层预算内重扫。
4. **仅当围栏确认未变时**，才对实际集合、目录唯一ID集合和计数判定一致性。稳定快照仍不一致才报 GUARD_INCONSISTENT。
5. 写路径共同更新 guard 围栏/目录、项目冲突版本、业务文档并提交。事务内不能出现条件查询或外部扫描。

外部管理员不遵循服务同时篡改多个文档不纳入正常并发保证；但明确可见的误删、错代际、自洽但错误目录等必须拒绝。若为提前拒绝结构错误而在外层读取，避免将两个不同时刻的快照混合后当成确定的损坏；权威判断仍以事务内复核为准。

### 2.3 把重扫、SDK重试和请求重放分清

- 两轮扫描是本次逻辑请求的总上限，不能给旧/新责任人或每次 SDK 回调各自重新计一次。
- SDK 自动回调重试不能绕开外层限制。若重新进入回调发现前置围栏不符，立即抛出不会被误当作事务冲突自动重试的业务停止码，结束当前 runTransaction，再外层重扫。
- 所有动作均有明确总尝试上限；采用已有 SDK 实际可支持的重试配置，记录语义及回调次数，不凭参数名字推断。不得叠加一个无界自定义循环。
- 第二轮仍过期返回明确业务拒绝 STALE_SCAN，不归为成功；事务/传输结果无法确定则走 unknown，保留原 requestId/快照。
- 成功回执重放须在当前权限与维护策略允许后优先核验，不能被首轮请求已改变目录、达到200容量或旧 expectedVersion 拦下而失去原结果。回执返回不能绕过当前权限核对。
- 同请求重试不换 requestId；SDK内部尝试、外层重扫、人工原号重试分别记录。客户端业务错误映射需补全新增码，未知传输错误仍阻塞编辑。

### 2.4 维护切换必须与在途业务写冲突

只在事务里读 projects.scheduleWriteMode，不足以证明维护开关生效后旧快照写事务不能提交。采用本轮明确方案：

- create/update/reassign/cancel/removeMember 都在同一业务事务写项目 scheduleEpoch+1；维护切换也写同一项目文档，形成冲突。增量写真实字段，不能用无变化写或依赖“读会自动锁住”。
- 在维护切换先提交的交错中，旧业务尝试必须回滚/重试后看到非ready并拒绝；业务先提交的交错中，维护命令须在进入维护后再采集最终数据。
- 初扫捕获项目epoch，事务校验；项目级串行化适合本轮低频测试，是明确代价。不能声称无额外冲突或不影响其他成员操作。
- 维护期间会增删成员/锚点的入口（至少 approveInvitation、assignManager、removeMember 相关分支）也须遵循同一维护策略与冲突约定。逐项列出，不留可绕过初始化的旧成员写入口。
- 维护修复每个事务仍受80/100预算；“不占业务事务预算”只是单独请求，不能表示维护操作不受平台限制。修复到一半失败，项目维持maintenance；按checkpoint接续并复核后才切ready。
- projects字段缺失视为未就绪；**这会阻止未准备的A/B/C项目移出成员等操作，必须在说明书明确，不能声称旧项目完全不受影响。** 当前禁止改A/B/C云记录；部署前需由Codex补充兼容/准备方案及影响裁决，不能靠静默给旧项目填ready解决。先完成本地实现和用例，不把这个部署事项混作已完成。

## 3. 预算与容量的具体口径

### 3.1 算术和计数纠正

修订稿 §5.4 列出的算式自身并不等于结果：create 依其所列加数合计40而非33；最大update合计69而非约66；reassign合计17而非约13；cancel合计41而非约35。它还存在锚点读是否与validateWorker重复、首次锚点写遗漏等问题。以上只是指出算术差异，**不是最终预算认证**。

实现需生成操作表：每一类文档的读、写次数，命中/缺失/首用/改责任人/改工种/旧新日期不相交各分支；计入新增项目冲突写、双方锚点读写与回执/审计。同一文档复用已读结果可减少次数，但只能在同一次事务尝试内复用。

旧新桶并集最多26个，桶数据操作最多52次；其余开销可用28次预算。最终以平台限制夹具测到的尝试峰值为准。测试至少覆盖365天跨13个月及旧新26桶，同时换责任人/工种；超80必须在首个数据写之前预检拒绝，另设逐次计数防意外第81次操作。两层检查不能混为一谈。

### 3.2 扫描和字节上限

- 目录ID唯一、稳定排序、类型/长度合法；同时以UTF-8实际序列化长度执行本轮保守技术上限32 KiB。生成最大合法200条样本验证能装下，不根据字符串字符数估算字节。
- 扫描采用固定排序和有界读取，正常最多200项，读取第201项作为超容量哨兵。到扫描上限不能把截断数组当作完整集合；遇到超量明确拒绝并转受控维护。
- 若底层单页100条，200整页需要额外空页或201哨兵确认结束；测试必须覆盖0/99/100/101/199/200/201以及页间变更。
- 正常可达的200条目录允许不增条目更新、取消、改派走出；转入已满目录拒绝。历史已超200属于维护事项，不宣称当前正常接口保证能处理无限旧数据。
- 200不是允许假取消的理由。提示使用“当前测试容量已达上限，请联系管理员核对”，不要求取消仍有施工任务的安排。

## 4. 月桶规则与索引

- 旧active安排释放时，桶或原日期键缺失同样属于占用不一致；不能只检查“有别人的ID”而默许缺失。空桶保留的选择接受。

## 5. 本轮交付与验证

WorkBuddy 在既有五集合设计内本地实现上述方案，允许修改施工服务/相关成员路由、客户端新增错误码映射、测试夹具/测试、数据契约与进展记录。固定入口保持 enabled=false/allowedProjectIds=[]/冻结；不改旧凭据、旧探针或env-gate。若必须扩大云资源/业务能力，列出差异交Codex，不自行落地云端。

必测：

1. 平台受限夹具跑所有写路由，事务内零where，第81/101次操作前拒绝；逐动作精确计数。
2. 四种成员移出/创建/改派交错，七集合加projects完整快照（现共8类集合），失败整体不变，审计/回执恰好一次。
3. generation=0首用竞争、guard误删、旧代际、错误ID自洽目录、重复ID、重新加入不重置。
4. 扫描期间变更先判STALE_SCAN而非数据损坏；有界重扫后成功/拒绝；双方同时变化；事务回调重入不复用过期扫描。
5. 维护与已启动写事务的两个提交顺序；成员批准/管家指定与维护交错；修复失败保持maintenance；修复重入不重置代际。
6. 同号回放在目录已变/已满/安排版本已升后返回原成功，失权仍拒绝；新增业务码恢复与unknown保留快照。
7. 长日期月桶、26桶最坏更新、月末/闰年/休息日、同月不同日并发、缺失/异主占用拒绝。
8. 容量200边界、201哨兵、32KiB字节保护、到上限不增容量动作可用。
9. 未就绪旧项目有明确拒绝语义；文档和测试如实记录影响，不把兼容拒绝算成旧行为完全一致。
