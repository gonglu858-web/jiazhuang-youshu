## 2. S1 · P1：正常准备链仍然走不通

位置：`cloudfunctions/scheduleSandbox/gate.js:209`（准备期所有带 ID 请求拒绝）、阶段清单；`index.js:108`。

实际 main 顺序：负责人成功建项目 → 管家成功取号 → 负责人用刚返回的项目 ID 指定管家，返回 **SANDBOX_PROJECT_NOT_READY**。改为 execute 阶段又返回 **SANDBOX_ACTION_NOT_ALLOWED_IN_PHASE**。邀请/批准同样属于必须准备、却没有可走通路径的动作。`getMembers/listInvitations/getScheduleContext` 等准备/表单必要读接口也未形成完整可用路径。

**修复要求**：创建后用受控登记或本轮持久记录确定唯一项目；该项目的正常指定/邀请/申请/批准和必要查询在准备期可用，其他项目仍拒绝。不要用“禁止所有项目”代替范围控制，也不要把准备动作移到执行期而绕开准备验证。身份和管理员初始化边界不变。

**验收**：从未创建项目开始，真实客户端 → main 完成建项目、本人取号、指定管家、邀请、申请、批准、成员/申请核对；随后受控切换 execute，执行施工四写及查询。不允许直接 vendor 写成员来跳过任何准备步骤。main 可返回随机绑定编号给本地测试下一步使用，无需因此绕过入口；不得将该合成编号写入证据。

## 3. S2 · P1：回执失败仍遗留半套状态，同号并发仍有 SERVER_ERROR

位置：`cloudfunctions/scheduleSandbox/project-guard.js:155–171`、`:44`。

回执仍在业务创建事务**提交之后**单独 add。注入该 add 失败，实际得到：第一次 SERVER_ERROR，数据库已有 1 项目、1 初始成员、1 创建审计、**0 回执**；同号重试成为 SANDBOX_PROJECT_STATE_CONFLICT。这不是“失败无半套状态”，只是检测到半套状态后停住。

两份同号同载荷经独立 main 并发调用，本机复现为一成功、一 SERVER_ERROR；测试仅要求“至少一个成功”，没有完成原要求的幂等回放。把平台并发列为未验证不能代替本地协议修复。

此外唯一键仍含 actorUserId；当前测试只覆盖一个 primary。若本轮 primary 绑定变化，另一允许账号仍可能得到另一轮次项目 ID。须将“一个轮次只允许一个创建执行人/项目”的可信约束持久化，不依赖当前 primary 永远不变的未声明假设。

**修复要求**：在新副本、限定 createProject 的包装范围内，将唯一性状态、项目创建结果和回执组成一致提交与冲突重试协议。保留原 vendor 算法和原函数不动；不能以源码注释声称一致提交。若拟用事务适配包装，必须保持单层真实事务、原业务权限检查、失败整体回滚和操作预算；实现不可行时报告具体边界，不自行把标准降为“留下半套但报错”。

**验收**：真实回执写故障注入，而非成功后手动删回执；同号/不同号同载荷并发都取得同一原业务结果且不重复落库；不同载荷明确拒绝；主管理员更换或失权不产生本轮第二项目；原结果回放重验当前权限。保留对已损坏状态的停止逻辑，但它不能作为正常故障恢复的替代。

## 4. S3 · P1：请求项目 ID 可覆盖邀请真实归属，列表仍返回其他轮次

位置：`cloudfunctions/scheduleSandbox/gate.js:240–243`、`index.js:130`、`:158`。

- `assertRecordOwnership` 优先使用请求 projectId，仅在其为空时取解析值。发送 **projectId=p_allowed + 属于 p_other 的邀请码**，门控通过，vendor 使用真实邀请码对 p_other 写入申请和审计。本机复现邀请变 requested、2 次写入。
- prepare 根本不执行邀请码归属检查，省略 projectId 即可申请另一轮次邀请。
- 实际 `listMyProjects` 在 execute 仍返回 p_allowed 和 p_other；原业务负责人能看全部项目，包装层没有限制本轮结果。测试 R4.8 的标题说列表，实际调用的是 getSchedule，未验证列表。

**修复要求**：始终解析记录真实归属并与本轮唯一项目比较；请求 ID 如存在必须再与解析值一致，不能优先覆盖。两阶段均有归属约束，邀请码规范化须与 vendor 的 trim/uppercase 一致。按真实数据核对邀请、安排、成员归属，保留原服务权限。列表结果也只限本轮目标；未建立目标时应有明确空结果/拒绝语义。

**验收**：跨项目邀请码分别带允许 ID、不带 ID、带错 ID、大小写/空格变体；prepare/execute 都测；拒绝零写入。种入另一个合法测试项目，实际调用 listMyProjects 并断言返回 ID 集合；不能用另一个接口代替。

## 5. S4 · P1：客户端未决状态与项目校验仍不完整

位置：`utils/schedule-sandbox-client.js:117–145`、`:193–232`。

已实际复现：

1. 配置目标为 p_allowed，但传 p_other 仍发云请求；配置无项目时传任意 projectId 也可绕过“未登记”限制。未知动作测试还主动接受发请求，与 R2 原要求相反。
2. 未决请求仅比较 requestId；同号把 createSchedule 改为 cancelSchedule 仍发送，并覆盖原 snapshot。相同编号不等于相同提交。
3. BAD_INPUT 明确拒绝后 pending 未清理，下一次不同号被 SANDBOX_PENDING_UNRESOLVED 阻断。交付说业务拒绝清理，但代码只清成功和两个 LOCAL_ENTRY_CODES；R5.11 只测成功。
4. getStorageSync 抛错被解释为“没有未决”，随后 set 成功即可发新请求；不能证明旧请求不存在。两个 key 分次写也须覆盖中途失败/不一致，不能默认为空。
5. 直接持久化整个 body，applicantNumber、bindingNumber、invitationCode 会随超时保留，没有到期清理/最小化策略，与“凭据不写长期缓存”不符。证据只记录布尔值，未保存原始编号。

**修复要求**：按动作/阶段核验固定目标；未知动作零请求。使用可校验的未决记录绑定动作、项目、requestId 和完整非敏感提交快照/摘要；同号不同内容拒绝，重试从已保存快照重建，不由当前表单覆写。存储读取失败或记录不一致拒绝发送；对明确业务拒绝、明确成功、网络/服务端未知分别处理，不能把所有错误一律清除。存储记录按环境、测试轮次及可信账号隔离，避免另一轮/账号误恢复。

敏感凭据不能原样进入长期 snapshot/报告；选择本地范围内的最小策略，例如仅内存保存敏感部分，重进后明确要求核对并恢复必要凭据，校验与原请求绑定后再继续。不能静默生成新的编号或申请。对尚无服务端幂等保障的取号/邀请动作，不把“同 requestId”宣传为已实现安全重试。

**验收**：同号不同动作/项目/载荷、真实 BAD_INPUT 后继续、SERVER_ERROR/超时保留状态、读失败、半写失败、账号/轮次切换、报告/存储不泄露敏感值。既有正常字段传递和环境版本门控测试保留。
