## 已确认范围：先做施工安排本身

1. 管家新增安排：项目、阶段、工种、主要上传责任人、起止日期（含当天）、预计完成日期、本次施工内容、休息/停工日。
2. 管家调整日期、责任人、施工内容，填写调整原因并保存新版本；原版本保留，旧记录关联当时版本，不被新内容覆盖。
3. 管家取消安排须填原因，保留安排及其历史；取消不是施工完成或阶段验收通过。
4. 同项目成员查看正式安排及调整历史；师傅/设计师/主业主/家庭成员不能修改安排。负责人保留已有查看范围，只有同时获得该项目管家角色时才使用安排写入权限。
5. 有效师傅且具备对应工种，才能被设为主要上传责任人。日期内排除休息/停工日后得到实际施工日；这里只显示施工计划，不伪造现场记录或“今日已更新”。
6. 移出保护同步接入：师傅名下存在未取消安排时须先改派；确实不再施工的安排可由管家填原因取消。不能靠预计完成日期已过就当作任务完成，不能通过取消冒充验收。正式施工完成关闭条件留待阶段验收单元衔接。

### 本轮已确认的具体规则

- **同一项目、同一工种、同一实际施工日最多一份有效安排**；新增重复安排提示已有安排并引导调整。不同工种可以同日施工；多个工种可授予同一师傅，各自成安排。此规则由用户在本轮新确认。
- 起止日期包含首尾，施工日排除休息/停工日；若排除后没有施工日则提示调整。预计完成日期不得早于开始日期；与安排结束日期不一致时提示确认，不默默改写。
- 调整、改派、取消均填写原因并保留历史。取消只改变计划，不删除历史或将施工标记完成。

## 分阶段实施

### 第一步：本地实现与审查（已授权）

WorkBuddy提出具体数据/接口契约后实施服务层及离线回归，复用现有页面；保留本机示例可辨识，云端失败不得回退为“已保存到本机”并假装云保存成功。不得让首页试用身份或请求传入role决定云端权限。

数据设计建议：schedules保存当前安排、版本和状态；独立安排修订记录保存不可变历史；复用audit_events记录真实操作者与当时角色。具体集合/索引/函数名称在技术任务中定稿；不在本轮创建。

服务端在同一变更中核对身份、当前项目/成员/工种、提交版本，写入安排、历史与审计。相同提交重试只产生一份安排和一条审计；旧版本修改被拒绝，保留未提交表单便于重新载入。

成员移出与安排创建/改派必须协调并发：两边事务共同读取/更新可冲突的成员任务保护记录或等价机制，不能仅各自先查询再写入，否则可能移出后又成为责任人。按同工种实际施工日做冲突保护，不能仅前端查重。失败不得留下半条安排或丢失审计。

新增集合默认客户端直接读写拒绝；列表/详情/历史均按可信微信身份和项目权限裁剪。禁止直接迁移本机示例数据，禁止将OPENID或凭据暴露给页面。

## 验收标准

| 场景 | 必须得到的结果 |
| --- | --- |
| 管家新增与多端刷新 | 正确项目的安排云保存后，师傅和主业主可见相同内容；重新进入仍存在 |
| 日期范围/休息日/同日多工种 | 实际施工日准确；休息日无施工要求，不同工种可并行；同工种冲突按确认规则拒绝 |
| 权限与跨项目 | 非管家写入拒绝；非成员读取/写入拒绝；伪造角色/账号无效；当前成员退出立即失权 |
| 责任师傅有效性 | 非成员、已退出、无师傅角色或缺工种者不可指派；提交前发生权限变更也拒绝 |
| 调整与历史 | 版本递增；旧版内容/署名/时间保留；旧版本提交提示刷新，不能静默覆盖 |
| 重复提交与并发 | 同请求重试只保存一次；同时编辑不会互相覆盖；同工种同日不重复占用 |
| 失败回滚 | 安排、历史、审计任何一步失败整体不生效；输入仍可保留，不能显示成功 |
| 责任人移出 | 有未取消安排先拒绝移出；完成改派后按既有规则可移出；并发移出/指派不得产生失效责任人 |
| 本地示例与云端 | 两种来源清晰，云端身份不接受本地角色切换；历史身份与并发检查回归保持 |
