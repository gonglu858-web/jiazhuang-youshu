|---|---|

## 1. V06 小并发 —— 关键限制

### 1.1 现状核实结论（已按复查更正）

| 编号 | 意图 | 当前页面的实际可达性 | 结论 |
|---|---|---|---|
| V06-a | 相同 requestId 两次新增 | 未决锁拦下第二次，第二次**零发送**（本地返回，非服务端幂等） | 真实串行回放**未验证**；见 §1.3 |
| V06-b | 不同 requestId 同日同工种 | 第二次被未决锁拦下（`SANDBOX_PENDING_UNRESOLVED`） | **当前不可达** |
| V06-c | 相同版本两次调整 | 同上 | **当前不可达** |

**「两个 `Promise.all(callSandbox(...))` 会在本地就拦下第二个请求」是事实**，不是风险推测。任何把 V06 描述为「已实现真实并发」的记录都是错的。

### 1.2 人工核对标记不是解锁工具（复查更正）

页面的 `resolvePendingAfterExternalCheck` 会**保留原 envelope 并标记 `writeLocked: true`**。它**不是**「解除后就能发送第二个请求」的工具：

- 标记后本轮仍**锁写**，新写动作不会自动放开；
- 该路径**不清除** envelope，未决证据仍在；
- 它的用途是「已在管理端核对完该编号，允许后续按原号恢复」，不是并发工具。

因此**不得**用「先标记核对，再发第二个请求」来实现并发。

### 1.3 三个用例的准确口径

**V06-a 相同 requestId 两次新增（幂等回放，串行）**
- 前提：**第一次请求已有确定结果**（成功或明确失败）。首次**明确失败**不能作为「两次成功结果相同」的前提。
- 事前：记录 requestId `R`、完整 form、发送前载荷快照与摘要。
- 第一次：`createSchedule`，form 含 stage/trade/workerUserId/startDate/endDate/expectedDate/restDays/content、requestId=`R`。
- 第二次：确认第一次结果后，**用原 requestId 与原载荷**再次发送。
- 通过依据：两次返回同一结果；数据库只有一份安排、一条历史、一条审计、一条回执。
- **可达性限制**：当前 Page **没有任意 requestId 输入框**（requestId 由客户端自动生成）。因此「按原号重发」**没有现成的可点击路径**；须由受审驱动按 §2 草案提供，或记为**未验证**。不得写成已有可点击回放路径。
- 如实记录：**串行幂等回放样本，不是并发**。

**V06-b 不同 requestId 同日同工种（占用冲突）—— 真正并发当前不可达**
- 阻断原因：第一次请求留下未决记录后，第二次被本地锁拦下，零发送。
- §1.2 的人工核对标记**不解锁**。标记不是「解除锁的路径」，也不构成并发手段。
- 需要区分两件事：**真正并发**（两个请求同时在途）当前不可达；但一笔请求已有确定结果后，按正常客户端流程可以再发下一笔**串行**请求。已明确成功的请求会按客户端流程处理 envelope；已明确的首次拒绝同样不构成无限重发理由。
- 结论：**本轮 V06-b 记未验证**。不通过换 requestId、清缓存或解锁页面来「完成」。

**V06-c 相同版本两次调整（乐观并发）—— 真正并发当前不可达**
- 同 V06-b：第二次被本地锁拦下。
- 结论：**本轮记未验证**。

### 1.4 请求同时发出 ≠ 服务端发生事务冲突

即使未来某个驱动能同时发出两个请求，也**不能**据此声称验证了事务重入：平台文档说事务回调会被冲突重入重试，但「两个请求同时到达」与「同一事务被重入」是两件事。只有记录到**真实 SDK 的 attempt/请求序列**（同一事务内回调被调用多次）才能描述真实重入。没有平台重入证据时，只报告实际响应与最终状态。

## 3. V07 移出成员

### 3.1 页面现状（复查更正，删除了「已核实可选」结论）

**当前 `schedule-sandbox` 页面无法移出成员。** 已核实：

- Page 的 `ACTIONS` 共 17 项（identify、requestBindingNumber、createProject、assignManager、createInvitation、applyInvitation、approveInvitation、getMembers、listInvitations、createSchedule、updateSchedule、reassignSchedule、cancelSchedule、listSchedules、getSchedule、listScheduleRevisions、getScheduleContext）——**不含 `removeMember`**。
- 虽然 `buildPayload` 有 `action === 'removeMember'` 分支、WXML 也有「成员账号（移出用）」输入框，但**动作选择器里选不到该动作**，输入框不会被使用。
- 客户端 `callSandbox` 仍登记 `removeMember`（属 `NON_IDEMPOTENT_ACTIONS`），**客户端方法可供后续受审驱动调用**。

**本轮不为满足操作稿而修改页面。** 结论：

| 路径 | 状态 |
|---|---|
| 页面点击移出 | **不可达**（动作不可选） |
| 现有导出客户端方法单次移出 | 客户端具备 `removeMember` 能力，但**无 UI 入口**；调用需受审驱动承载（载体未成立，见 §2） |
| 「点击移出即可」 | **错误表述，已删除** |

### 3.2 公开返回契约（复查更正）

`getScheduleContext`（vendor `schedule-service.js`）**只返回** `project`（id/name/status）、`isManager`、`trades`、`workers`。

**不返回** `activeScheduleIds`、目录条目、锚点或围栏字段（`fenceVersion` / `generation` 等）。因此：

- **不得**依赖页面核对 guard 计数、目录长度或锚点配对；
- 这些改为**受控管理端只读核对**（直接读前缀集合），**不新增公开字段**；
- **历史查询须由仍有权限者执行**（管家或负责人）；**被移出的账号用于验证「失去访问后的拒绝」**，不是用来查历史。

### 3.3 两种前置条件下的操作与判定

这是**两个不同前置的测试动作**，不是「整轮只能发一次却要求两个结果」：

**动作 A：有任务在身 → 一次拒绝尝试**
- 事前：记录被移出人 `userId`、当前项目；**受控管理端只读**记录其 `activeScheduleCount` 与 `activeScheduleIds`（不在页面核对）。
- 操作：`removeMember` + 目标 `userId`（受审驱动调用；完整 userId，不是尾号/昵称/手抄 OPENID）。
- 通过依据：返回明确拒绝（目录非空）；被移出人**仍在** `project_members` 且 `status` 未变。
- 管理端事后只读核对：在身安排、`member_task_guard` 目录与代际、月桶映射全部不变。
- **只发这一次**；结果未知即停止，不重发。

**动作 B：目录清空后 → 一次成功移出**
- 前提：先通过正常业务（取消/改派）把该人的安排清空，管理端只读确认 `activeScheduleCount` 为 0。
- 操作：`removeMember` + 同一 `userId`。
- 通过依据：返回成功；`getMembers` 不再含该人；该人再次调用项目内查询被拒（失去访问）。
- 管理端事后只读核对：成员 `status` / `leftAt` 已更新；`member_task_guard` 锚点与代际配对正常；**历史版本仍可查**（由管家/负责人执行 `listScheduleRevisions`）；月桶中已取消/改派的映射一致。
- **同样只发一次**；结果未知属不安全重发，停止并只读核对。

### 3.4 规模与对象限制

- 最多对**候选师傅乙（尾号 f182f4）**做动作 A 与动作 B 各一次；其不能参与时**保持未验证**，不自动换人、不把 A/B/C 成员拉进副本。
- 移出只在本轮唯一项目内做，**绝不在 A/B/C 项目测试**。
- `removeMember` 非幂等：同一次操作不重发。

## 4. 首次 primary 初始化（P4）

### 4.1 先后关系（复查更正：解除循环依赖）

原 §4.2 要求「项目 ID 已登记」才可初始化 primary，但建项目在 P5、且 vendor `createProject` 又要求管理员资格 —— 构成循环。**更正为：**

1. 已核实环境 / AppID；
2. 已登记轮次与两小时窗口；
3. 指定账号**本人微信**完成 `identify`；
4. 目标前缀 `users` 中该账号 `active`；
5. `app_admins.primary` **确认不存在**（只读）。

**此时项目尚未建立。** 初始化审计可按当前模型记录 `projectId: null`，并关联受控轮次与执行证据。项目归属与 ready marker 的读回属于**后续 P5/P6**，不得偷换为「预先已有事实」。

### 4.3 技术方向（Codex 裁决，照录）

- primary 选择**受控一次性、原子条件写**的技术方向；**不接受**独立「读 → 写 → 回读」作为等价替代。
- 同一受控事务内：核实用户与 primary 不存在 → 新增 primary → 写可关联审计。普通回读不能防止竞态，也不能消除无审计的中间状态。
- 结果未知：**先只读确认**再决定下一步。
- 同输入已提交的确认**不等于**重复授权。

### 4.4 执行方法就绪性（如实记录）

> **执行方法未就绪。**

- 载体能力**未核实**：管理 SDK 是否提供本地受控事务命令、其登录方式与实际事务接口均**未核对**；本轮不安装、不实现、不执行，也不新增云函数。

### 4.5 同输入重试与失败后确认

- 同一输入（同一 `primary`、同一 userId）重试：必须仍走「不存在才新增」；命中已存在即停止并报告，**不做 upsert**。

- `primary` 存在但 userId 与名单不符 → 判定状态冲突，停止并提交差异，**不「修正」为名单值**。

| `allowedUserIds` | `[]` | **执行当日已核实完整 userId 名单** | 同 prepare | 管理端只读核实的完整 userId；不接受尾号/昵称 |
