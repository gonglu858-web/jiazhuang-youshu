## 3. 真实包离线核对结论（本机实测）

先复跑 `docs/证据/Codex首次初始化SDK离线形状核对-20261006.cjs`：**8 项通过，networkAttempts = 0**。据此实现的转换规则：

| # | 真实包实测结论 | 适配层对应做法 |
|---|---|---|
| 1 | 实际入口是 `./transaction/index`，不是旁边的旧 `transaction.js` | 不按未加载的残留实现写适配层 |
| 2 | `db.startTransaction()` → `tx.collection(n).doc(id).get()/set()` → `tx.commit()/rollback()` | `beginTransaction` 返回**冻结空壳句柄**；底层引用只存私有登记，**不改写宿主 SDK 对象** |
| 3 | 合成成功空列表：事务读 `{data:null}`、非事务读 `{data:[]}` | `normalizeDoc` 按 mode 归一为 `null`；**仅这两种**算成功空，其余形状（含缺 `data`）拒绝；非空记录须 `_id` 匹配 |
| 4 | `set(fields)` 用**裸字段对象**。要求是**本适配层不得再多嵌套一层** `{data: fields}` —— SDK 可能把它当作业务字段保存，并不必然替我们拦截 | `reconcileId` 核对 `_id` 一致后**复制剔除**，不改核心对象；不额外包 `data` |
| 5 | 真实 SDK 的 `set({_id:...})` 在发到传输层前就拒绝（实测结论；但这不意味着「错误嵌套写法」也会被 SDK 拦截，见第 4 条） | 适配层负责转换，不改 P4 业务数据结构 |
| 6 | 文档方法可能返回**含 code 的错误对象** | `normalizeDoc` 遇 `code` 抛 `READ_REJECTED_BY_SERVER`，**绝不**归一为「不存在」 |
| 7 | 事务 set 转换后的最终返回为 `updated` / `upserted` / `requestId`；commit 的含 code 错误会抛出；rollback 走 `abortTransaction` | `assertSetSuccess` 按该形状判定（计数须有限非负整数且 ≤1，零更新须有主键匹配的插入）；`commit` 净化为 `COMMIT_UNKNOWN`；`rollback` 失败抛 `ROLLBACK_FAILED` |
| 8 | 手动事务路径可匹配核心 | 保持手动事务，不改成自动重试 `runTransaction` |

**本轮新增的两条实测约束**：

1. `Db.reqClass` 的替换**必须在 `sdk.init(...).database()` 之后**。若先替换再 init，`startTransaction` 不会走合成传输，而会尝试真实连接并被网络拦截拦下（`OFFLINE_ONLY`）。
2. 合成传输返回的文档**必须是 BSON 扩展 JSON（EJSON）序列化后的字符串**。SDK 的 `DocumentReference.get` 会对每个返回项调用 `bson.EJSON.parse`，而该函数要求参数是**字符串**（内部走 `JSON.parse`）。直接返回普通对象会在 SDK 内部抛 `SyntaxError: "[object Object]" is not valid JSON` —— 这是 SDK 的既有行为，**不是适配层的问题**，但会让人误判为适配层缺陷。测试脚手架用 SDK 自带的 `EJSON.serialize` 生成，已固定。

## 5. 缺失读取与响应错误的处理

这是本适配层最要紧的语义，逐条列明：

| 情形 | 真实包表现 | 适配层处理 | 错误码 |
|---|---|---|---|
| 事务读成功空 | `{data:null}` | 归一为 `null`（确认无记录） | — |
| 非事务读成功空 | `{data:[]}` | 归一为 `null`（确认无记录） | — |
| 读被拒绝（权限等） | `{code:..., data:undefined}` | **拒绝**，绝不归一为「不存在」 | `READ_REJECTED_BY_SERVER` |
| 读**缺 data 字段** / `data:undefined` | `{requestId:...}` / `{data:undefined}` | **拒绝**（R1：不得与「显式 null」混同） | `READ_SHAPE_INVALID` |
| 读传输异常 | 抛异常 | 拒绝，只保留白名单内的类型名 | `READ_TRANSPORT_FAILED` |
| 读形状未核实 | 事务返回数组 / 普通读返回裸对象 | **拒绝**（R1：不做兼容性猜测） | `READ_SHAPE_INVALID` |
| 读到的记录 `_id` 缺失 / 与查询 key 不符 | — | **拒绝**（R1：不能把别的记录当本计划记录） | `READ_KEY_MISSING` / `READ_KEY_MISMATCH` |
| 写被拒绝 | 含 code | 拒绝，核心不会继续 commit | `SET_REJECTED_BY_SERVER` |
| 写回执计数异常 | `NaN` / 负数 / 非整数 / `>1` | 拒绝，核心不会继续 commit | `SET_SHAPE_INVALID` |
| 写零更新且无合法插入 | `{updated:0}` | 拒绝 | `SET_SHAPE_INVALID` |
| 写零更新但插入主键不符 | `{updated:0, upserted:[{_id:'其它'}]}` | 拒绝 | `SET_KEY_MISMATCH` |
| 写回执只有未核实字段 | `{updatedCount:false}` / 只有底层 `upsert_id` | **拒绝**（R2：不作替代成功凭据） | `SET_SHAPE_INVALID` |
| 写传输异常 | 抛异常 | 拒绝，不提交 | `SET_TRANSPORT_FAILED` |
| commit 失败 | 抛出 | 净化传播，**不重试**、不谎报已回滚；状态转 `commitUnknown` | `COMMIT_UNKNOWN` |
| rollback 失败 | 抛出 | 如实报失败并提示人工核对 | `ROLLBACK_FAILED` |
| 跨实例 / 伪造事务句柄 | — | **拒绝**，零底层调用（R4：归属在私有登记） | `TX_NOT_OWNED` |

**「含 code」与「不存在」严格区分**是本层的核心义务：`result.data || null` 这类写法会把拒绝变成「记录不存在」，本层不采用。

## 6. 事务句柄状态机（R4 修正）

```
（本实例私有登记）──► 读写/提交 ──┬─ 提交成功 ──► finished（不可复用）
                                ├─ 提交失败 ──► commitUnknown（不可读写/再提交；**允许回滚一次**）
                                ├─ 回滚成功 ──► finished（不可复用）
                                └─ 回滚失败 ──► finished（不可复用）
```

**归属与状态全部放在适配器实例私有的 `WeakMap` 里，句柄对象本身是一个冻结的空壳**（`Object.freeze({})`）：

- 底层 SDK 事务引用只存在登记项中，**外部读不到、也换不了**；
- 旧实现把 `__commitUnknown` 放在句柄上，rollback 又拿它当放行依据，会导致
  ①跨适配器句柄能回滚别的事务、②伪造 `{__commitUnknown:true,__tx}` 即可授权任意底层回调；
  现已全部改为先核对私有登记，未登记即拒绝；
- 同时**不再重绑真实 SDK 对象的方法**（旧实现为拿绑定函数而改写了宿主事务对象，属污染）。

提交结果未知后仍**允许回滚一次** —— 回滚是既有的恢复动作，不是新写入；核心据此区分
「回滚成功 → `RESULT_UNKNOWN`」与「回滚也失败 → `ROLLBACK_FAILED`」。
