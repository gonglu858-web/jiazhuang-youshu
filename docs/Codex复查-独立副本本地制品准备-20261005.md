## 2. R1（P1）：校验必须覆盖 manifest，缺基线不得继续；生成前完成可预知检查

位置：`miniapp/scripts/package-sandbox.cjs:203`（基线读取失败），`:282`（check 分支），`:306`（逐个写入），`:335`（额外文件），`:558`（先打包后核对资源）。

已复现：

- 临时包 manifest 替换成 `NOT JSON`，`buildPackage({checkOnly:true})` 仍返回 check；目前只判断 manifest 存在，完全未解析或核对。
- 指定不存在的 baselinePath，默认核验开启仍生成包，返回 `baseline.checked:false`。
- 预放 `package/unexpected.txt`，生成模式成功并写 manifest，extraFiles 只是报告数组，没有拒绝。
- 预放不同内容的第二个文件 gate.js，生成失败前已经创建第一个 index.js；与头注释“失败时不写任何新产物”不符。主入口还在包写完之后才检验候选清单。

限定修复：

1. 默认/CLI 缺失、不可解析或字段不完整的基线一律停止；测试专用显式跳过必须隔离且不伪装已核验。
2. check 与生成复用同一事实校验：manifest 可解析，schema/白名单/文件路径唯一且完整，字节数/哈希/来源与实际源及包体一致；不得只相信其自报 true。无需给 manifest 添加自哈希。
3. 写入前完成源、基线、候选清单、既有文件冲突、额外文件与既有 manifest 的预检。预先能发现的失败须零新文件；生成与检查模式均拒额外文件。检查整个制品目录允许项，不仅 package 子目录。
4. 不要求实现通用文件系统事务。中途真实 I/O 故障可能留部分新文件时如实说明未完成，保留可核对状态，不声称任何失败均零写；不递归删除用户目录。

补测：manifest 无效 JSON/文件条目哈希错/漏项或重复项；缺/坏基线；生成前额外文件；晚序文件冲突及候选清单错误时零新增文件。

## 3. R2（P1）：校验受信根路径，而不只校验根目录下面的相对文件

位置：`package-sandbox.cjs:101–139`、`:253–280` 以及 manifest 读写位置。

`resolveInside` 从 baseResolved 下面开始 lstat，不检查 base 本身与祖先。realBase 又是已经跟随链接的根，比较其下真实路径无法发现根被替换。

实测：使用 `fs.symlinkSync(actual, alias, 'junction')`，确认 `lstat(alias).isSymbolicLink()===true`；把 alias 作为 outDir，仍生成成功，manifest 实际写入 actual。没有修改真实交付目录；只在新建临时目录复现。

限定修复：对 outDir、package 根、源根及沿途祖先、manifest 自身做一致的链接与真实包含检查；CLI 输出限定仓库中独立制品目录，禁止源目录重叠，不能把调用方给的任意目录直接当受信根。测试临时输出可以有显式受控根，但不能削弱 CLI。检查路径后才 mkdir/read/write，不必扩展为通用安全文件库。

补测真实 Windows junction：输出根、package 根、manifest 链接、祖先目录链接；验证拒绝发生在写入前，目标目录不变。不能只测 `a/../../../x.js`；它验证的是字符串过滤，不是根联接。

## 4. R3（P1）：资源清单校验当前只验类型，未锁住批准候选

位置：`package-sandbox.cjs:443–448`、`:489–524`。

当前清单本身正确，以下对内存副本的单项变异均被工具接受：I04 keys 反序、I07 createdAt 从 desc 改 asc、I05 unique 改 false、I01 编号改 I99、删除 function.runtime。

限定修复：按已审查 I01–I13 规格逐条严格匹配 ID/集合/字段有序序列/方向/unique/TTL；候选规格必填且精确匹配，created/executable/containsPlatformApiRequest 等就绪标记必须是明确 false。保留对集合双向核对、额外函数和触发器的现有检查。不要把待验证候选改成新规格，不新增索引。

测试必须调用真正的校验器并证明每种变异失败；只读当前 JSON 断言它恰好正确，不能证明校验器会拦住后续变更。

## 5. R4（P2）：操作稿须恢复实际可达路径与公开返回契约

位置：`docs/独立副本有限测试操作稿-20261005.md` §1.1–1.3、§3、§5；源依据如下。

- Page 的 ACTIONS（`schedule-sandbox.js:26–44`）没有 removeMember。虽有 `buildPayload` 分支和“成员账号（移出用）”输入框，**不代表 picker 可以选到该动作**。删除“已核实可选”结论，标注页面不可达、客户端方法可供后续受审驱动调用；本轮不为了满足操作稿改页面。
- `getScheduleContext`（vendor `schedule-service.js:410–429`）仅返回 project/isManager/trades/workers，没有 activeScheduleIds。guard/锚点/安排完整性改为受控管理端只读核对，不新增公开字段。历史查询须由仍有权限者执行，被移出账号用于验证拒绝。
- `resolvePendingAfterExternalCheck`（client `:1056–1090`）保留原 envelope 并标记 writeLocked；不是解除后就能发送第二个请求。已知成功路径可按正常客户端处理，但未知请求人工核对标记不是解锁工具。
- 一次请求被本地锁挡下只是防重样本，不是服务端幂等回放证据。真正串行回放须确认第一请求成功并用原 requestId/载荷再次发送；首次明确失败不能作为“两次成功结果相同”的前提。Page 没有任意 requestId 输入时，不写成已有可点击回放路径。
- 区分“有任务的一次拒绝尝试”与“任务清空后的一次成功移出”，不是整轮只能发一次 removeMember 却要求两个结果；两次属于不同前置的测试动作，任一结果未知均不得自动重发。
- 补任务明确要求的 prepare/execute/closed 差异表，依据 gate/project-guard，列字段来源、项目创建前后、切换前在途核对；保持真实值空，不生成启用包。

只更正操作稿/交接，并补相称的源码契约断言（动作列表、公开字段）即可，不扩写已关闭业务测试。

## 6. R5（P2）：primary 前置与专用驱动载体需要定点澄清

### P4 的先后关系

操作稿 §4.2 要求“项目 ID 已登记”才可初始化 primary。但执行包 P4 在 P5 建项目之前，vendor `service.js` createProject 又要求管理员资格。这形成循环。

P4 应先有已核实环境/AppID、轮次/窗口、指定账号本人登记、目标前缀 users active 与 primary 缺失。**此时无需已创建项目 ID**，初始化审计可按模型记录 projectId:null，并关联受控轮次/执行证据；项目及 ready marker 的项目归属读回属于后续 P5/P6，不能偷换为预先已有事实。本轮只修字段/顺序说明。

### Codex 技术裁决

1. **primary 选择受控一次性、原子条件写的技术方向，不接受独立“读→写→回读”作为等价替代。** 同一受控事务内核实用户和 primary 不存在，新增 primary 与可关联审计；结果未知先只读确认。同输入已提交的确认不等于重复授权。普通回读不能防止竞态或消除无审计的中间状态。
2. “一次性管理命令必然需要新增云函数”不成立；管理 SDK 的本地受控事务命令也可能成为载体，但必须先核对已有 SDK、登录方式与实际事务接口。本轮不安装、不实现、不执行该命令，也不新增函数；能力未核实仍标未就绪。后续由 Codex 形成单独最小实现任务，不把付款意愿当授权写库。
3. **暂不批准 §2 的两个 Node 测试文件作为可执行真机并发驱动。** Node 测试文件没有小程序 wx.cloud 的真实登录上下文；getWXContext 是服务器 API。可保留纯协调逻辑的离线设计，但需说明未来在小程序运行时如何取得受信 identify 结果和发出固定函数请求，不能注入 OPENID/actorId。
4. “独立存储键”只解决覆盖，未解决与普通页面同时提交。后续驱动需先拒绝已有普通未决记录，再保存自身测试批次；批次未决时不得启动下一例/页面写操作。不能要求用新独立键绕开原未决状态。
5. “同轮次只发一对”至多覆盖一个并发用例。保留一对限制时明确 V06 另两例未验证；若以后实现三对，使用同一业务 roundId 下固定 testCaseId 的三对有界计划，每对只发一次、串行核对后再下一对，不能更换业务轮次规避防重。当前只修草案，不实现。
