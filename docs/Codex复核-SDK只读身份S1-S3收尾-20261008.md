## 2. T1 [P2] 两处 !== false 尚未改成约定的严格 true

位置：`miniapp/scripts/lib/cloudbase-sdk-readonly-observer.cjs:1024`、`:1032`。

实际仍是：

```js
out.userIdShapeValid = out.userId !== null && rec.userIdShapeValid !== false;
out.statusValid = out.status !== null && rec.statusValid !== false;
```

这与交付说明、函数注释的“必须严格true、不再混用!==false”不一致。通过真实 `interpretWorkerOutput → interpretPrimary/interpretTargetUser` 复现：

- primary.userIdShapeValid、primary.statusValid、users.statusValid 分别给缺失/null/0/空串，合计12例仍得OBSERVED。
- false的3例被拒；true的3例通过，证明问题是把“不是false”误当成“明确通过”。

这些样本是**损坏的worker输出协议**；当前正常worker会输出布尔值，本次不声称真实云记录已经被误认，也不声称取得任何写权限。它仍是上轮明确要求且本轮声称完成的收紧，不能只改交付文字掩盖。

最小修复：两处使用 `=== true`；userIdPattern=null 的users仍保持“不适用”，不增加users.userId要求，不要求worker没有提供的docIdMatches标记。补测上述缺失/null/0/空串/false/true，走完整解释链。保留本轮正常记录正向通过。

## 3. T2 [P2] 两条时效测试没有验证标题对应阶段

位置：`miniapp/tests/cloudbase-sdk-readonly-observer.test.cjs:1961`（S3-5）、`:1992`（S3-6）。

- S3-5 的子进程全部exit 1，断言允许 stoppedAt=sameBatchCredential或cliAssociation；甚至注释明确“CLI阶段就会…停止”。该例不能证明worker返回后复核。局部snap没有送入编排。
- S3-6 没有明确的worker响应分支，断言只要求有errorCode/incomplete，未证明worker已调用、已返回以及最终过期说明来自父进程返回后的检查。
- WorkBuddy独立证据S3-5确实到达worker失败返回，覆盖了失败后复核；但其按now调用次数校准，不代表上述两条单测已覆盖。

**Codex已补证实现正确，不要求重写S3实现**：新增脚本以worker输出即将close为事件屏障推进时钟，并断言四个阶段实际经过。

| 场景 | 结果 |
| --- | --- |
| 正常返回、未过期 | 两条记录OBSERVED；整体仅因合成链proven=false而INCOMPLETE；无过期说明 |
| 正常返回、父进程收尾前过期 | 两条部分观测保留；整体INCOMPLETE；明确返回后发现过期 |
| SDK_UNAVAILABLE返回、父进程收尾前过期 | 原始错误保留、FAILED；另有过期说明，无再次获取凭据 |

最小修复：重写现有S3-5/S3-6，不增加架构。以事件屏障驱动时钟；断言确实启动并完成worker、正确保留结果或错误，并含父进程过期说明。补未过期对照；删除未使用snap和“提前失败也算通过”的兜底断言。不要再只用now调用次数猜阶段。
