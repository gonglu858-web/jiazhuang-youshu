## 2. S1（P1）：校验的批准/计划与实际送入 worker 的内容仍可不同

位置：host `issueControlledApproval` 196–224、`verifyControlledApproval` 253–293、`executeOnce` 543–545、687–722。

### 证据

1. `verifyControlledApproval` 校验 `approvalSource.approval`，但 721 行传给 worker 的是独立的 `o.approval`。保持签发句柄不变，只把后者 `approvedBy` 改成 `SYNTH_DIFFERENT_REVIEWER`，完整链仍两写一提交；实际审计的批准人变成这个未绑定值，最终 `resultPersisted=true`。
2. 句柄只顶层 `Object.freeze`，嵌套 `approval` 可改。签发后修改 `source.approval.approvedBy`，验证仍 `ok:true`。注释“批准人与签发时一致”实际只检查字符串类型。WeakSet 证明对象由本模块发出，不能保证对象内部未被改动。
3. `o.plan` 在获取凭据前检查一次，随后跨多次 await 继续使用原可变对象。在 `persistRoundStarted` 回调中改 `operatorRef`，仍成功提交，审计记录了修改后的值。P4 六字段摘要不覆盖该字段，不能代替完整批准绑定。

样本：`approval-not-bound-to-worker`、`signed-handle-nested-mutation`、`plan-change-after-started`。

### 最小收尾与验收

- 受控句柄内部保存独立、不可变的批准和完整计划；真实 worker 载荷取自已经核验的同一快照。不要核验一份、执行另一份。
- 不需要新增签名服务或批准数据库。可以用现有私有存储保留快照，或递归冻结安全副本；嵌套指纹也不能由外部改写。
- 在异步边界之后使用绑定快照；若保留调用方计划/批准参数，差异须明确拒绝，不能静默替换审计身份。启动 worker 前复核当前期限及实际实施文件绑定。
- 三条反例须“拒绝”或“执行原绑定快照”，不得让改动值落库；正常成功链保留。

这是受审管理进程自身的数据一致性问题，不是在要求防御能任意改本机代码的人。

## 3. S2（P1）：事务中途过期仍两写一提交，且报告成功

位置：worker 334–335、380–387、404–425、440–455；host 704–724。

worker 虽有实时 `now()`，给 P4 的 `nowMs` 仍是 `payload.fixedNowMs` 常量。P4 自己的“首写前再核验”因此一直看到起点时间。凭据期限只在入口检查、提交后统计；批准句柄自身的期限未传到 worker 做执行期检查。

独立样本在 **SDK 的 users 事务读取完成事件**推进合成时钟，不按 now() 次数猜测：

| 场景 | 实际结果 |
| --- | --- |
| 计划在第一条事务读取后过期 | primarySet=1、auditSet=1、commit=1、回读=2；`planExpiredDuringRun=true` 但 `ok=true` |
| 凭据在第一条事务读取后过期 | 同样两写一提交和两读；`credentialExpiredDuringRun=true` 但 `ok=true` |

样本：`plan-expires-after-tx-read`、`credential-expires-after-tx-read`。

### 最小收尾与验收

- `fixedNowMs` 如需保留，只作审计记录时间；P4 的计划有效期校验传实时函数，不能固定时间。
- 在新接线层检查凭据与批准期限，至少覆盖开启事务、首写前、后续写入/提交前等实际操作边界；截止后禁止继续授予。必要回滚只报告实际结果，不承诺本地计时器能撤销已经提交的平台事务。
- 读后过期两例必须零 set/commit，并验证取消事务的实际调用；再补首写后过期分支，不能继续第二写/commit 后才记“已过期”。不要改 P4/适配器来迁就接线。
- 回读只有同批凭据仍可用时进行；删除“过期仍照常核对”的注释与行为。凭据不可用明确留待只读接续，不补取第二批重写。
- 若提交已发生、随后才过期，保留提交事实并区分“核对未完成”，不能把成功提交抹成零写。

## 4. S3（P1）：worker 异常后没有完整的核对与留证路径

位置：host 687–690、731–751、852–909、917–949；测试 E-2 832 行起。

### 证据

1. worker 超时：报告虽 `RESULT_UNKNOWN`，但 `auditId=null`、无 `roundId`；started 回调保存的 `auditId` 也为 null。同批凭据仍有效，实际回读 0，结果保存回调 0。报告文字称“保留轮次与审计 ID”，实际未完整保留。
2. 子进程以 0 退出但 stdout 是坏 JSON：返回 `WORKER_FAILED/resultUnknown=false`。退出码 0 不证明写请求没发生，丢失输出应保守留作待核对。
3. worker 明确输出 `resultUnknown:true`（例如提交未知），父层 `projectWorkerOutput` 无条件用自己的 false 覆盖。父层进程正常不意味着数据库提交结果确定。

样本：`worker-timeout-loses-reconcile-keys`、`malformed-output-clean-exit`、`worker-declared-unknown-lost`。

E-2 名称声称“保留轮次与审计 ID”，断言却只查错误码、started、取凭据次数，**没有断言 ID 或两条回读**。R5-e 只覆盖 worker 仍能活着执行 catch/回读；不能代替父层处理 worker 消失的路径。

### 最小收尾与验收

- 在启动 worker 前由受控计划用 P4 算好确定性 auditId；started 与所有终态保存轮次、摘要、审计键，不依赖子进程输出才能取得这些值。
- 可能已执行但超时、信号、坏输出、缺输出时保持结果未知。合法 worker 的未知结论与父层进程事实作保守合并；不要用正常退出覆盖业务未知。
- 同批凭据仍有效时，父层安排**只读**的 primary + 本计划审计核对；不得再次进入 initializePrimary。子进程是否确已退出与数据库事务是否仍在途须分别记录；未确认终止时，一次“暂时没读到”也不能升级为确定未提交。
- 无法回读时明确原因与实际未核对事实；输出/持久化未知结果，不保存为成功。结果保存失败保留 started，不能自动重写。保存能力缺失应在外部动作前识别，不能提交后才发现缺少记录手段。
- stdin 发生错误也不能单凭该错误断言“载荷必未完整送达/零写”；应依据已观察的阶段保守判定。
- 将 E-2 的名称变为真正断言：审计键精确相等、轮次保留、有效凭据仅固定两读、无第二次初始化/凭据获取；补坏输出与提交未知的贯穿场景。

## 5. S4（P2）：父层只限定字段名，未限定字段值

位置：host `projectWorkerOutput/projectBootstrap/projectObserved` 917–990；另 594 行 `credentialFailureClass`。

worker 的正常输出已作部分净化，但父层仍直接接受以下任意字符串：`outcome`、`bootstrap.errorCode/inputDigest/requestIds`、`observed.state/primaryStatus/errorCode` 等。顶层 auditId 仅 startsWith 前缀，不是与本计划精确比较。

`known-field-projection-leak` 在这些**已知字段**内放入 `SYNTH_PRIVATE_MARKER`，父层全部保留；不是未知 extra 字段透传问题。当前 R3-g 只证明未知字段被丢弃，R5-c 只测 worker 层，不能证明父层严格投影。

最小修正：

- 复用/对齐现有有限状态与错误码、32 位 inputDigest、UUID 请求 ID 规则；不新增任意大写字符串放行规则。
- 父层持有预期 auditId/inputDigest 后逐项精确核对；不匹配不可升级为成功。
- 凭据失败类别使用实际固定错误码枚举，594 行大写正则不等于白名单。
- 补“合法字段内非法值”与正常值通过的测试，既不能泄漏任意外部文本，也不能把成功状态错误净化掉。

当前这是合成损坏输出协议验证，**不宣称实际平台曾泄漏秘密**。
