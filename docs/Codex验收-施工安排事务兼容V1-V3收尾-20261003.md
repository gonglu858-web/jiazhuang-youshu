## 1. a–g 逐项核验

| 项 | 验收结论 |
| --- | --- |
| a 屏障位置 | **通过**。`gateAfterBothFastReceiptChecks` 先 await 原始 `runTransaction` 成功结束，再核对 null 并等待另一方；达到两次后释放。两次快速检查都结束前不会进入实际写事务。外层 `gateAll()` 是冗余释放，正确性来自包装器自身。 |
| b 变异检出 | **本次故障模型通过**。编译内存副本，确认原有 4 处检查且删除后为 0，四动作均检出对应业务错误。文本变异可接受，且不会写磁盘。4/4 只证明“删除这四处检查”的已知缺陷被锁住，不证明所有语义变体和全部回归无缺口。 |
| c 双向交错 | **通过**。先启动待暂停方，命中提交前 barrier 后，另一条真实路由完整执行，再恢复；最终成员/锚点/编号/申请/审计与 epoch 3 或 2 一致。`attempts>=3` 单独不足以证明重试，结合该夹具启动顺序、写集和结果才成立。 |
| d 暂停目标 | **在本组夹具下正确**。每例只启动指定的一条路由，维护写 projects、不写 project_members，成员路由同时写两者；命中后移除 hook，再启动另一方，不会把它暂停。不能把该判别器直接当作任意未来事务的通用分类器。 |
| e 零写可信度 | **通过**。V3a 注入预算 18→90 后经真实 create 路由执行，`appBudget:null` 确实关闭夹具的 80 拦截，仅保留 100；写计数在底层写尝试时增加、回滚不清零。写调用 0 加执行前后全库 JSON 一致，有效证明本场景首写前拒绝。末尾自比快照断言冗余，但不影响前面有效断言。 |
| f 重入计数 | **通过所测累计错误场景**。冲突夹具使 SDK 回调模拟重入两次，每次底层执行 60 次，最终峰值 60；若两次累计则第二次不能完成。结合 U3a 产品 80 边界与 U3b 同实例交错共同证明当前要求。这里没有调用真实 SDK 的冲突机制。 |
| g 注释准确性 | **仍有少量非阻断问题**，详见第 3 节。真正双向交错和零写证据已由新增 V2/V3 覆盖，旧标题不再作为其证明。 |

## 2. 关闭范围

- V1：四动作同号同载荷均返回相同原结果；业务版本一次，回执/历史/审计各新增一次；不同载荷明确拒绝；删除写回调检查的变异可检出。
- V2：批准申请、指定管家与真实维护路由分别覆盖两种提交顺序；维护先提交时无目标成员、无对应审计且不消费编号；成员先提交时维护重试后成功，保留成员与锚点。
- V3：实际 create 超预算零写及全库不变、未注入时成功对照、回调重入量化计数均通过。正常 26 桶更新的既有回归保留。
- 不重做已关闭的 T1/T2/T5，不改业务代码。

## 3. 非阻断记录：随下次测试/文档维护清理

这些问题不削弱新增关键场景已有的有效断言，因此不阻断本地关闭，也不要求为它们再次重写实现。

1. `schedule-service.test.cjs:2973` 附近，U1a 的成员数量断言两边都取 `before.members`，恒真；“八类集合其余不变”也不准确，create 会改变 projects epoch、成员锚点和占用。应改为真正的前后期望，或删去该无效断言和过度注释。不能把现有断言描述为八集合逐字段验证完毕。
2. `:3735` 附近 V3a 的最后一条 `snapshotAll8(db) === snapshotAll8(db)` 是自比；可删除。前面的执行前后 JSON 比较已有效覆盖全库不变。
3. U2d 说明首句“两半都不是与真实维护路由并行”与第二半实际交错矛盾；第一半是直接改 epoch 后顺序调用维护，第二半确实是 removeMember 与真实维护交错。其标题 `(both orders)` 也应缩小。T4c 新标题与实际移出在途时被直接改维护状态的行为相符。
4. V2 helper 首句“把先提交方卡住”应为“把后提交/重试方卡住”；下方 first 注释和执行代码是正确的。断言消息“后完成的成员写/维护”也宜按真实先提交方表述。
5. U3d 旧标题仍宣称零写入，实际只是公式与成功路径；零写证明是 V3a。V3b 自身是 13 桶 create 对照，不是 26 桶 update，标题需避免混淆。后者在既有用例中已验证。
6. 交付文档“证明回归不再有覆盖缺口”应限为“检出本次 4 个删除检查变异”。“第 81 次在写入前拒绝”应为“第 81 次底层操作前拒绝”；逐操作拦截可能发生在前面已有暂存写入之后，失败原子回滚不同于首写前零调用。
7. `currentAttemptPeak()` 当前实现保留服务实例观测过的最大峰值，不总是“最近一次 attempt”。V3c 新实例两次均 60 的样本不受影响。U1 等待双方 null 的循环建议后续加有界失败与 finally 清理，避免未来夹具故障挂起整套测试。
