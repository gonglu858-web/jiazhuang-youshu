### 1.3 逐路由围栏覆盖表（消除 P2 表述矛盾）

上稿称"新代码所有写入都递增 epoch"过于笼统。修订为逐路由。**"递增 epoch"与"无写入"是两件事，必须分开标注**：查询主体只读的路由，其 `execute` 公共前置逻辑仍可能写库。

| 路由/动作 | 是否递增 `scheduleEpoch` | 维护态下 | 围栏可信性 |
|---|---|---|---|
| `createSchedule` / `updateSchedule` / `reassignSchedule` / `cancelSchedule` | **是**（`bumpProjectEpoch`） | 阻断 | 可信 |
| `removeMember` | **是**（显式 `update projects`） | 阻断 | 可信 |
| `approveInvitation` / `assignManager` | **是**（`guardAndBumpEpoch`） | 阻断 | 可信 |
| `setScheduleWriteMode` | **是** | — | 可信 |
| **`createInvitation`** | **否** | **仍可写** | **不参与围栏** |
| **`applyInvitation`** | **否** | **仍可写** | **不参与围栏** |
| `requestBindingNumber` | **否**；写 `users`（`bindingCodeHash`/`expiresAt`）+ `audit_events` | 仍可写 | 不改变核验对象，**但不是零写** |
| `identify` / `listMyProjects` | **否**；**查询主体只读，身份初始化可能写** `users` + `audit_events`（`registerIdentity`） | 可用 | — |
| 账号 `status` 变更、管理员记录变更 | **否** | 仍可写 | **不参与围栏** |
| 控制台 / 管理脚本 / 其它函数（`connectionCheck`） | **未知** | 未知 | **未确认覆盖** |

**D1 更正：业务查询路由不是无条件只读入口。** `execute`（`service.js:134`）除 `checkTransaction` 特例外**一律先调用 `identity`**（`service.js:143`）；`identity`（`service.js:72`）在**首次见到该账号**时会写 `users` 并追加 `registerIdentity` 审计。因此：

- 上表"只读"仅指**查询主体**，**不指完整入口**；`identify` / `listMyProjects` / `requestBindingNumber` **不得作为 B0 的零写取证手段**。
- 该副作用属于**公共前置逻辑**，与是否部署新代码无关（`identity` 在旧部署中同样存在）。

**由此产生的取证与证书约束：**

1. **B0 一律使用受控的管理端数据库只读查询**（§9.6 B0-0），**不调用这些业务路由**取得身份或数据，**不为核对而取号**（不新申领、不复用绑定编号、不走 `requestBindingNumber`）。
2. **账号状态与主管理员资格必须重验**，不能因为上一轮身份初始化已发生就假定账号稳定。
3. 若最终证书涉及 **active 安排责任账号的有效性**（§6.5 分流的第一类），**不得仅因 `users` 未进入摘要就忽略账号状态的稳定性**——须另有稳定性依据，或把 `users` 纳入摘要。

**更正上稿**：上稿 §1.2 把 `createInvitation` / `applyInvitation` 写成"改变 `project_members` 与 `invitations`"，**不准确**。这两个动作涉及**邀请记录及其审计**，**不直接新增成员**；只有 `approveInvitation` 才改变 `project_members`。

**结论**：围栏只覆盖上表前四行。**"所有写入都被维护态冻结并受围栏保护"这一说法不成立**，§3 与 §8 均据此收口。

## 3. 在途排空与写入者覆盖

### 3.1 旧部署阶段无法证明排空

旧部署（A 列）的 `service.js` 修改 `project_members` 时**不递增新 `epoch`**。因此：

| 观测手段 | 能证明 | 不能证明 |
|---|---|---|
| 多次 epoch 相等 | **只观测采样值未变** | **旧函数写入**（旧部署不递增新 epoch） |
| 停发预览 | 减少新入口 | 旧预览、直接云调用 |
| 通知参与者停止 | 减少人为操作 | 定时任务、重试中的请求 |
| 固定等待时间 | 心理预期 | 任何技术性质 |

**结论：多次 epoch 相等、停发预览、固定等待时间三者都不能单独证明旧请求已排空。** 它们只能作为**观测记录**。

**"epoch 采样值未变"的正确读法（不得拔高）**：只有在**已证明全部相关写入都遵守同一围栏的单调递增、且不存在旁路回写**的条件下，"采样值未变"才支持"期间无相关提交"的判断。M-b 下这两个前提**都不成立**（新代码未部署、旧函数不递增、旁路写入者未确认），因此**当前任何 epoch 采样都只能记为观测值，不作为排空证据**。

### 3.2 最终恢复必须有明确的写入者约束

按 §1.3，围栏不覆盖 `createInvitation` / `applyInvitation` / 账号状态变更 / 控制台与脚本。因此最终恢复必须附带：

## 4. `initDir` 的合法使用前提

`initDir`（`schedule-service.js:307`）固定写 `version/fence/generation = 1`，且要求 guard 不存在。

**它只能用于合法首用路径**，前提是：

1. 锚点**已存在**且 `taskDirSchemaVersion = 1`、`taskDirGeneration = 0`（**合法首用锚点**）；
2. guard 不存在；
3. 实际完整扫描为 `EMPTY`；
4. 无历史非零代际证据。

**"锚点和 guard 都不存在即可直接 `initDir`"不能写成操作说明**（P1 要求）。锚点缺失时必须先按 §5 补锚点，**不能跳过锚点直接建目录**。

上稿"首批只补 projects/project_members 缺失字段"的表述已按此收紧：**补锚点（A-3）是首用前置，不是可选项。**

## 5. 补缺路径（P1 修正）

### 5.1 上稿冲突

上稿 A-1 把"schema 缺失"与"epoch 缺失/0"捆绑为同一动作。但按 §1.2，维护入口在缺 epoch 时会**写入 1**。于是存在这一序列：

```
项目缺 schema、缺 epoch
  → 进入维护态（第 1 步）→ epoch 变为 1，schema 仍缺失
  → 上稿 A-1 的条件（"epoch 缺失或为 0"）不再满足 → 被排除在补缺路径外
```

**结果：成功进入维护、但 schema 仍缺失的项目无法补 schema。** 本稿修正。

### 5.2 三字段分别分类（P1 要求的修法）

`scheduleSchemaVersion`、`scheduleEpoch`、`project_members` 锚点**分别独立分类**，不互相捆绑：

| 字段 | 合法值 | 处理 |
|---|---|---|
| `scheduleSchemaVersion` | 缺失 | 列入补缺候选（A-1） |
| | 合法值（= 1） | **保留**，不覆盖、不改写 |
| | 非法值 / 高于支持版本 | **转人工**，不擅自解释 |
| `scheduleEpoch` | 缺失 | 列入补缺候选（A-2） |
| | **合法值 `0`** | **保留**——现状实现接受**非负整数**（`schedule-service.js:636` 的 `isNonNegativeInt`；`service.js:52` 亦只拒绝负数）。**已有合法的 `0` 既不得被误判为"缺失"，也不得被擅自改写成 1** |
| | 合法正整数（含维护进入后写入的 1） | **保留，绝不改回 0** |
| | 负数 / 非整数 / 类型不符 | **转人工** |
| 锚点两字段 | **都不存在** | 列入补缺候选（A-3，需 §11.2 四项条件全满足） |
| | **仅一个存在（部分锚点）** | **转人工** |
| | 合法 `generation=0` | 保留（合法首用态） |
| | 合法 `generation>=1` | 保留，**不降低代际** |
| | 非法值 | **转人工** |

**`epoch = 0` 的处置边界（本轮只记录，不执行）**：

- **本轮不执行补缺。** 缺失字段**填入什么值**、以及**由哪个事务负责递增**，放入 B0 事实齐备后的**具体变更包**决定，**不在本轮执行、不在本稿预设**。
- **"不把正整数改回 0"继续保留**（上表第三行），与本行"已有合法 0 保留"不冲突：前者禁止**下调已递增的代际**，后者禁止**把已存在的 0 当成缺失去改写**。
- 因此 A-2 的触发条件严格是"**字段不存在**"，**不是**"值小于某阈值"**（§5.3）。

**明确不因 epoch 已存在就跳过 schema 缺失核对**（P1 要求）。三字段各自独立取证、独立结论。

### 5.3 首批补缺动作（修订）

| 编号 | 动作 | 前置条件（全部满足） | 写入 |
|---|---|---|---|
| **A-1** | 补 `projects.scheduleSchemaVersion = 1` | 该字段**缺失**（非非法值） | `projects` 更新 |
| **A-2** | 补 `projects.scheduleEpoch` | 该字段**不存在**（**不是**"值为 0"；已有合法 `0` 或正整数则**不写**） | `projects` 更新 |
| **A-3** | 补 `project_members.taskDirSchemaVersion = 1` + `taskDirGeneration = 0` | 锚点两字段**都不存在**（非部分存在）+ 无 guard + 完整扫描 `EMPTY` + 无历史非零代际证据 | `project_members` 更新 |

**全部保持"不覆盖合法现值、不降低代际、不改回 0"。**

**首批范围不因本规则自动扩展**到非空或未知状态（P1 要求）：任何 `NONEMPTY` / `INCOMPLETE` / `ERROR` / 非法值 / 部分锚点，一律**转人工**，不进入 A-1…A-3。

### 5.4 首用路径的完整顺序

```
成员锚点两字段都不存在
  → B0 完整扫描 = EMPTY（必须是 EMPTY，不是 INCOMPLETE/ERROR）
  → 确认无 guard、无历史非零代际
  → A-3 补锚点（schema=1, generation=0）        ← 此后进入合法首用态
  → 该成员首次安排时，由产品的 initDir 建目录（generation=1）
```

**不得跳过 A-3 直接建目录。**

### 6.5 成员异常判定限于其业务关系（P1 核心修正）

上稿 R-12 / `MR-3` 要求"无 `MEMBER_INACTIVE` 成员"，这**过于宽泛**：项目本来就包含管家、负责人、主业主及历史退出成员，不能因为有人没有师傅角色或已 `left` 就全项目禁止恢复。

**修订为按"是否被 active 安排引用"分流**：

| 成员类别 | 检查项 | 不满足时 |
|---|---|---|
| **被 active 安排引用的责任成员** | ① 成员记录存在且 `status==='active'`；② 账号存在且启用；③ 具备 `师傅` 角色；④ 具备该安排 `trade` 的工种；⑤ 锚点与目录一致 | **阻断恢复**（`WORKER_INVALID` 类） |
| **无 active 安排引用的成员**（含管家、负责人、主业主、`left`、非师傅） | 仅检查**锚点与目录的一致性**（`generation` 配对、ID 唯一、目录与扫描一致） | 见下方分行判定 |

**第二行的"不满足时"必须按下表读，不得笼统理解为放行**：

| 不满足的具体项 | 判定 |
|---|---|
| **角色缺失**（无 `师傅` 角色）／ **工种不覆盖** | **不阻断**——该成员无 active 安排引用，角色/工种与就绪无关 |
| **已 `left` / 账号停用**（无 active 安排引用） | **不阻断**——退出状态本身不是损坏 |
| **锚点/目录一致性失败**（代际不配对、ID 重复、目录与扫描不符、孤立 guard、非空残留） | **阻断恢复** |

即：**角色与退出状态本身不阻断；锚点/目录一致性失败仍阻断恢复。** 原文"不阻断"写在"不满足时"列会被误读为"目录损坏也放行"，以此表为准。

**仍然检出的异常（不因"不阻断"而免检）**：

- 孤立 guard（有目录无对应锚点）
- 错误代际（锚点与 guard 不配对）
- 非空残留目录（目录条目与扫描不符）

## 7. 占用完整性：允许合法空月桶

### 7.1 上稿的判错

`writeBuckets` 明确**保留空桶**（`days = {}`）。取消或改派后，实际桶键集合可能**多于** active 安排推导出的非空桶键集合。上稿要求"键集合完全相等"，会把正常操作产生的数据判坏。

### 7.2 全量枚举与结构验证（不变）

对 S-5 全量枚举到的**每一条**桶记录验证：

| 项 | 要求 | 失败标签 |
|---|---|---|
| `schemaVersion` | 恰为 `2` | `SCHEMA_UNKNOWN` |
| 主键 | `_id = {projectId}:{trade}:{YYYYMM}` 可解析 | `ORPHAN_KEY` |
| 归属 | `bucket.projectId` / `trade` / `month` 与 `_id` 解析一致 | `FOREIGN_HOLDER` |
| `days` | 合法对象（非数组、非 null） | `DATE_INVALID` |
| **日期→月份归属** | **`monthOf(date) === bucket.month`**（日期键自身的年月必须等于该桶声明的 `YYYYMM`） | `DATE_INVALID` |
| 日期键 | 真实 `YYYY-MM-DD` 且 `parseDate` 有效 | `DATE_INVALID` |
| **非空 holder** | 若某日期键取值**非空**，该值必须是**有效非空字符串**（可解析的安排 ID）；**取值校验先于归属核对** | `FOREIGN_HOLDER` |

**顺序要求（先类型后归属）**：日期键必须先通过 `parseDate` 与 `monthOf` 校验，再对其 holder 做"是否为有效非空字符串"的判定，最后才做"该 holder 是否属于本项目/本工种/属于该日期所属月份"的归属核对。**不得在 holder 尚未确认为合法 ID 前就做归属比较**，也不得跳过 holder 类型检查直接比对。

**空桶不放宽以上任何一项**：合法空桶（`days = {}`）的**豁免仅限 §7.4 的"不形成多余占用"**，**不豁免** `schemaVersion`、`_id` 解析、`monthOf(date)` 一致性、`trade` 归属与 `days` 结构校验。**错月桶、非字符串 holder、无效结构一律阻断。**

### 7.3 非空日期占用严格比对（P1 核心修正）

比对对象是**非空日期占用**，不是桶键集合：

```
推导占用 D（从全部 active 安排计算，已扣 restDays）：
  (projectId, trade, 'YYYY-MM-DD') → scheduleId

实际占用 A（从全部合法桶的 days 中展开非空项）：
  (bucket.projectId, bucket.trade, date) → holder
```

**D 的推导步骤（E1 修正：不存在 `workingDays` 持久化字段）**

1. 对 S-3 枚举到的**每一条** active 安排，读取 `startDate` / `endDate` / `restDays`（**不是** `workingDays`——该字段不持久化，`schedule-service.js:1058–1065`）。
2. 按产品实现计算施工日：`workingDays(startDate, endDate, restDays)` = `startDate`…`endDate` **闭区间**逐日递增，**扣除** `restDays` 命中的 ISO 日期（`schedule-service.js:1343–1356`）。
3. 若 `parseDate` 失败或 `start > end`，该实现返回**空数组**。此时**必须标记该安排为"日期不可解析，推导不完整"并中止 D 的构造**，**不得**把它当作"零施工日"直接参与比对——否则会制造大量虚假"多余占用"。
4. 由 `workingDays` 得到的每个日期与该安排的 `trade` 一起组成 D 的键值对。

**要求**：`{(k, v) ∈ A}` 与 `{(k, v) ∈ D}` **完全相等**——无缺项、无多项、无归属错误。

### 7.4 合法空月桶单列（P1 要求）

| 类别 | 判定 | 处置 |
|---|---|---|
| 结构合法 + `days = {}` | `LEGACY_EMPTY_BUCKET` | **不形成多余占用**（不进入 A）、**不删除**、**不阻断** |
| 结构合法 + `days` 含 `''` 或 `null` 值 | `INVALID_EMPTY_ENTRIES` | **阻断**（不是合法空桶） |
| 结构非法（错 schema/错工种/旧逐日键/未知键）即使 `days={}` | 结构错误 | **阻断**，不因"空"豁免 |

### 7.5 继续阻断的情形

- 同日同工种两个 active 安排 → **停止**，不靠遍历顺序选胜者
- 重复占用（同一 key 映射到不同 scheduleId）→ 阻断
- 错误日期归属（日期指向某 active 安排但不属于该安排）→ 阻断
- 孤立非空占用（`days` 指向非 active 安排）→ `ORPHAN_KEY`，**不自动清理**

### 7.6 正向例（新增用例 `MO-8`、`MO-9`）

| 用例 | 场景 | 期望 |
|---|---|---|
| `MO-8` | 取消安排后留下 `days={}` 的月桶 | 判 `LEGACY_EMPTY_BUCKET`；**通过**，不要求删除 |
| `MO-9` | 跨月调整后原月桶变空 | 同上；新月份桶占用正确 |

| 字段 | 说明 |
|---|---|
| 环境 / AppID | 固定，不接受跨环境复用 |

| **核验规则版本** | 规则本身版本化，规则变更即使旧证书失效 |

| **写入者覆盖证据** | §3.2 的 W-1…W-4 满足证据 |

### 8.3 有效期、失效与时效的地位

**要求 3：有效期固定为签发后最多 10 分钟，使用服务端时间；未来签发时间拒绝。**

**证书失效条件**（任一即失效）：

| 失效条件 | 判定 |
|---|---|
| 超过 10 分钟 | 服务端时间比较 |
| `issuedAt` 晚于服务端当前时间 | 拒绝（未来签发） |
| epoch 变化 | 与证书绑定的 epoch 不一致 |
| 维护轮次变化 | `maintenanceRoundId` 不一致 |
| schema 版本变化 | 不再等于签发时的精确版本 |
| 核验规则版本变化 | 规则版本升级 |
| **任何相关写入** | 计划内元数据写入完成后才签发**对应最终 epoch** 的证书；此后**任意相关写入使旧证书失效**（P1 要求） |

**时效是附加条件，不替代 epoch / 轮次 / 完整性**（P1 明确）。

### 8.4 恢复事务与原子消费

**要求 4：最终有界事务核对**

事务内**仅主键操作**，核对：

1. 当前**可信执行人**（不接受请求体 `actorId`）；
2. **管理员资格**——对齐现有 `app_admins` **主管理员模型（`primary` 记录绑定的用户）**，执行时**重验可信身份与账号有效**；
3. **项目允许范围**（显式列表，不接受"当前所有项目"）；
4. `maintenance` 状态；
5. 维护轮次；
6. epoch；
7. 证书**通过 / 完整 / 未失效 / 未使用**；
8. 操作数预算。

然后**原子**完成：记录恢复结果 + **原子消费证书** + 更新 `ready` + 推进 epoch。

**要求 5：重试规则——必须区分"成功回执重试"与"首次恢复"两个分支（D4 澄清）**

上稿只写"同轮次同输入重试返回原结果"，但未说明该分支是否仍要通过 `maintenance` / 证书未消费 / 旧 epoch 等前置。若把首次恢复的前置一并套到重试上，**一次成功之后的合法重试会被自己造成的 `ready` 状态和已消费证书拒绝**。因此明确如下：

| 分支 | 判定顺序 | 前置要求 |
|---|---|---|
| **① 成功回执重试**（本轮次、同输入、已有成功记录） | ① 先**核验当前身份与权限**（可信执行人 + 主管理员资格 + 账号有效 + 项目在允许范围）；② 再**识别同轮次同输入的已提交结果**；③ 命中则返回**已记录的原结果** | **不要求** `maintenance` 仍成立、**不要求**证书未消费、**不要求** epoch 仍为签发时的旧值。**只做身份/权限核验 + 回执识别**，不二次推进 epoch、不二次消费证书 |
| **② 首次恢复**（无同轮次同输入成功记录） | 走上述"要求 4"的全部 8 项核对 | 全部满足方可恢复 |

**分支互斥判定顺序**：必须**先判分支①，命中即返回原结果并结束**；未命中才进入分支②的前置检查。**不得**在分支①命中前先执行 `maintenance` / 证书未消费 / 旧 epoch 检查。

**与用例的关系（不矛盾）**：`MX-5` 表述为"**拒绝二次执行或消费**"，指**不得对同一证书再执行一次恢复动作或再消费一次**；`MX-6` 表述为"合法同输入重试**按原结果返回**"。二者分别约束"证书不可被二次使用"与"合法重试应被受理"，**同时成立**。

**其余重试场景**：

| 场景 | 规则 |
|---|---|
| 同轮次**不同**输入 | **不得复用旧结果**，拒绝（回执识别必须含输入摘要比对） |
| 任何重试 | **仍核验当前身份与权限**——不因有记录而跳过 |

"已是 `ready` 就 `changed:false`"**不能绕过**身份、轮次与当前就绪证据检查；但若本轮次已有成功记录，则按上方分支①返回原结果，**不作为一次新的"已是 ready"判定**。

### 8.5 邀请类字段与就绪证据（P1 要求 7）

若证书摘要包含 `invitations`（因 §3.4 的 `createInvitation` / `applyInvitation` 维护态仍可写），则**必须另有稳定性依据**（例如写入者已停用、或该集合不进入摘要且不作为就绪判据）。

**不得声称"维护态冻结了所有集合"**——§1.3 已列出仍可写入口。

#### 9.6.6 分页与结束条件（统一规则）

- 统一 `_id` 升序 + `skip` 分页，**页大小 100**，避免漏读。**与 `scanActiveSchedules` 相同的只有分页大小与排序方式**；该函数额外按 `workerUserId` 过滤（`schedule-service.js:283–290`），因此 S-3 的项目级扫描**不是"同参"**（E2-3）。
- **结束条件**：返回条数 < 页大小即结束；**翻页中断** → `INCOMPLETE`，**不得记为零数据**。
- **计数比较范围（E2-1）**：只允许**相同过滤条件**的计数相互比较（例如"项目 A 的成员数"只能与"按 `projectId = A` 过滤的计数"比较），**禁止**与集合总计比较。已观测事实：A/B/C 成员数 **4 / 1 / 3**，`project_members` 集合总计 **8**，两者不同是正常结果，**不是数据损坏**。
- **非原子性**：多集合分别读取**不是原子快照**。同一过滤条件下两次读取的条数差异**标为"待核对"或 `INCOMPLETE`**，**不得据此推断数据损坏或被篡改**。

### 14.3 共享部署影响（M-b 下必须先讲清）

`memberAccess` 是**共享云函数**，一次代码更新影响所有调用该函数的项目。以下影响在**任何**变更包中都必须说明：

| 影响面 | 说明 |
|---|---|
| **共享代码面** | 一次部署影响 A/B/C **全部**项目及该函数承载的其它路由（身份、成员、邀请等），无法只对 A 生效 |
| **旧部署并存期** | 新代码未部署时，旧 `service.js` 修改成员**不递增新 epoch**；新旧行为并存期间围栏不成立 |
| **未就绪项目的受限范围（F3 更正）** | 按**当前未部署实现**：安排四个写动作与**批准/指定管家/移出成员**在未就绪项目会被新守卫拒绝；但 **`createInvitation`、`applyInvitation`、取号、身份初始化等仍可能写入**。`setMaintenanceMode` 有自己的鉴权与写入路径，也不是统一的缺字段拒绝。**与 §1.3 逐路由表一致——不写"所有写入都停止"** |
| **B 的连带影响** | 任何共享部署都会把新守卫校验带到 B；B 无管家，可能出现"A/C 可维护、B 直接被拒"的**不对称可用性** |
| **变更包必须评估的范围** | 完整变更包**必须评估 A/B/C 及其他调用方的影响**，并**列明每项目处置、在途请求约束、中断窗口、失败接续点与回退适用条件** |
| **数据不可逆约束（保留）** | guard 一旦建立**不能靠删除回到"无目录"**；锚点代际**只增不减**；`scheduleEpoch` **单调递增**、**不回退** |
| **回退适用性（不作断言）** | **不宣称"回退旧包必然安全"**——旧包可能绕过新围栏，**须结合实际已写数据判断**；**也不宣称"回退必然不安全"**。是否存在受控分阶段路径、兼容包或暂停窗口，**由未来具体方案证明** |

**结论（F3 修正）**：共享代码更新确实影响所有调用方，但**代码部署与数据库迁移并不因此成为一个原子事务**。因此**不据此推出**"必须一次性覆盖 A/B/C 补缺与 B 权限处置"，也**不据此推出**"部分项目不可写的中间态无法回退"。**这两类绝对结论都未经证明，本稿删除。** 后续变更包须按上表逐项给出**可审查的依据**。
