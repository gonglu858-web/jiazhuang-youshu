## 二、后续证据必须遵守的纠正口径（写入所有新证据/脚本/文档）

> 来源：验收文档第 5 节「不采纳为当前执行成功的表述」。任何新脚本、新 JSON、新报告都须遵守。

1. **EBUSY / spawn 受限**
   - 不得用 `catch` 后回填历史输出字符串充作「本次通过」。
   - 正确做法：记录为「未验证（spawn 受限 / EBUSY）」，并在结果中引用既有历史证据文件，
     明确区分「本次未执行」与「历史已核验」。
   - 输出文案示例：`[spawn 受限] 本次未执行，沿用 docs/证据/<历史文件> 中已核验结果。`

2. **标签正则 / 结构检查 ≠ 编译**
   - `/<checkbox(?!\-group)[^>]*\bbindchange="toggleDateConfirm"*/` 等正则只能证明结构匹配。
   - 不得把 `wxmlGroupCompiled=true` 解释为「编译成功」。
   - 真正的编译证据须来自真实微信编译器（`wcc`/`wcsc`）的实际运行输出。

3. **entry 元数据 ≠ 配置读取证据**
   - 脚本内 `entry` 常量（newEnabled=false 等）只是声明，不构成「已读取实际配置」的证据。
   - 若需证明配置冻结，须实际读取并比对导出配置，而非依赖常量。

4. **数组事件精确措辞**
   - U5 的判定精确为「非数组 或 不含 `date-confirm` 时未确认」。
   - 注意：`['date-confirm','other']` 实测**仍确认**（includes 不拒绝混合数组）。
     代码注释/文档中「含其它值一律未确认」表述过强，应改为「不含 date-confirm 时未确认」。
   - 当前 group 仅一个固定 checkbox，正常交互无混合值，故不提升为功能阻断。

5. **测试数量 ≠ 契约完整性**
   - 测试通过数量本身不能证明契约完整；未知结果动作须用真实 Page 单独补证。

6. **历史证据保留**
   - `docs/证据/` 下历史脚本与 JSON 一律保留原样，不改写、不覆盖。
   - 新结论用新文件承载（如 `独立测试副本U3U5-Codex验收-20261004.{cjs,json}`）。
