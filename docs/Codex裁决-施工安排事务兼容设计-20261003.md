# Codex 裁决：施工安排事务兼容设计（2026-10-03）

## 结论

已审阅 [WorkBuddy 兼容设计](WorkBuddy方案-施工安排事务兼容-20261003.md)。**月度分桶方向通过；目录安全设计尚未通过，先修订设计，不直接开始实现或云端操作。** 六项决策如下。用户已确认的云端方案授权继续有效，但兼容前提未满足，部署仍暂停。

## 六项裁决

| 项 | 裁决 | 执行口径 |
| --- | --- | --- |
| 1. 目录硬上限 200 | 可作为本轮隔离试验的服务端技术保护上限，不确认为正式业务永久上限 | 指每项目每成员 active 安排目录条目数；须同时控制实际序列化字节，重复 ID 不得通过。达到上限只拒绝增加条目的新操作，允许读取、减少条目的合法取消/改派；幂等成功回放不再次占容量。禁止提示用户为绕过容量而取消实际仍需施工的安排。不能将“成员一生最多 200 项”或“同时施工 200 项”混同于当前 active 状态定义。 |
| 2. 月度分桶 | 接受 | 复用 schedule_occupancy，不新增集合；保持 365 天及逐日冲突规则，完整变更仍在同一事务提交。按旧/新项目+工种+月份桶键的并集核算，每个桶读一次、合并后写一次；同月不重叠日期可先发生事务冲突，重试后应可各自成功。 |
| 3. 预算阈值 | 应用层每次事务尝试最多 80 次数据操作，平台限制夹具仍为 100 | 80 是工程余量，不是“重试共享 100 次额度”。每次尝试独立计数，重试另计累计耗时。80 包括权限、回执、结构锚点、目录、旧/新桶、安排、历史、审计全部 doc 读写。不能直接认可草案 38/64/15/10 的估算值。 |
| 4. 3 秒超时 | 本地设计阶段不改云端；不接受“10/15 次操作可以在 3 秒完成”的结论 | 函数的外层身份/鉴权、冷启动、重试与查询同样耗时。修订稿给出有限重试和超时行为，部署准备时单列建议 10 秒及客户端等待窗口供核对，不自动改资源配置。少量样本不能声称有可靠 p95。当前 3 秒尚未验证，不以文档延迟假设放行。 |
| 5. GUARD_INCONSISTENT | 不接受仅“计数=目录长度”替代与实际安排核对 | 保留拒绝损坏和不一致的语义；目录只能作为维护的派生索引，不能用“原子写所以永不损坏”排除误删/历史数据/漏写。只读诊断有用，但不能将一个本应阻止移出的检查悄悄降为旁路提示。修订方向见下节。 |
| 6. guard 字段角色标注 | 必须明确 | 不新增集合不等于不新增字段。记录 schemaVersion、目录/计数/冲突版本各自职责，以及独立初始化锚点所在文档和迁移规则；member_task_dir 只能是概念称呼，物理集合仍 member_task_guard。涉及 project_members/projects 新字段及写路径时必须逐项列入影响清单。 |

## 阻断一：初始化标记不能与被删除目录保存在同一处

草案 §2.2 使用“目录缺失且 initialized=true/false”区分首次使用与被删除，无法实现：目录不存在时两者都读不到 initialized。

反例：师傅有 active 安排 → guard 文档被删除 → 读取结果与从未建目录相同 → 按零初始化 → 移出可能错误放行。

修订必须做到：

- 使用独立于 guard 的持久初始化/模式锚点，例如已有成员文档中的任务目录模式或代际字段，字段具体定义由修订稿明确；目录缺失且锚点表示已初始化时一律拒绝。
- 对旧成员“无锚点、无目录”不能自动推断没有安排；必须有明确的初始化/迁移入口与就绪状态。当前五集合未创建是本次前置观察，不是运行时永远安全的证明。
- 说明新成员加入、成员离开后重新加入、首次安排、原目录被删除各分支；保持稳定成员 ID/历史关系，不能覆盖旧 active 目录。
- 若需要在 approveInvitation 或其他旧成员写路径补初始化字段，逐项说明兼容影响，不扩大到无关身份行为。
- 维护/回填时不能只依赖客户端 enabled=false 暂停写入；需要服务端可验证的就绪/维护条件，防旧预览及直接调用并发写。

## 阻断二：目录自洽不等于与安排一致

反例一：count=0、ids=[]，但 schedules 实际有 active 安排。反例二：count=1、ids=[错误ID]，但真实安排为另一个 ID。两者都满足数组长度检查，却不满足原安全要求。

推荐修订方向：在事务外按实际 schedules 完整扫描，配合从扫描之前建立的持久版本围栏；事务内仅 doc 核验围栏未变，随后共同修改保护记录，保留真实集合与目录的核对。**不是简单把 where 搬出去。** 修订稿须画出以下可执行顺序与竞争证明：

1. 先读稳定锚点/guard 的代际和版本，再扫描实际安排；不能扫描后才第一次取版本。
2. 明确所有改变安排归属/status/目录的业务路径均在同一事务更新相应版本；改派涉及双方。其他会影响核对结果的字段修改也要考虑。
3. 事务内重新读锚点与 guard，核对版本/代际和数据前置条件；不一致必须重新扫描或有界拒绝，不能在事务自动重试中反复使用失效扫描结果。
4. 用同一保护记录写冲突协调从校验到提交的窗口；解释首次并发初始化、目录缺失、重新加入和维护期间行为。
5. 明确管理员绕过服务直接同时篡改多文档不在正常业务一致性保证内；有可见缺失/自洽但与实际扫描不符仍须拒绝。不得声称能检测任何形式外部篡改。

若认为另一种确定性结构可以保留同等保证，可提交替代证明，但不能删去反例测试。事务外只读扫描不计事务内操作额度，仍须计算函数总耗时/分页限制，并防止分页期间业务写入导致漏读而未被版本检查察觉。

## 分桶与预算的实施约束

- 日期键统一为真实 YYYY-MM-DD（草案示例 202610-01 应纠正）；覆盖闰年、跨年、月末、365 天跨度、休息日及全休息日拒绝。
- 修改日期/工种时合并旧新桶操作，同桶先在内存中释放本安排再获取新日期；不得写回旧快照覆盖他人占用。
- 释放日期发现占用属于其他安排时应停止并报告不一致，不能静默继续取消/改期后留下错误占用。
- 空桶删除或保留须统一；add/update/set/remove 的存在/缺失分支全部纳入预算。
- 365 天最多跨 13 个自然月；改期/改工种旧新桶并集可能达 26 个，必须计算两方目录及额外锚点后的最坏路径，不固定使用“约 12”开销。
- update 的旧日期/工种/责任人须事务内读到权威版本后才能做准确预算；形状校验可提前做，最终预算必须在首个数据写之前确定。服务端为准，客户端预估只作体验辅助，不复制易漂移的权威规则。
- 测试夹具应在第 101 个操作执行前拒绝，另验证应用第 81 个操作不会发出；不是只在 commit 时事后报错。计数器每次重试重置，报告同时保留总尝试数。
- 桶“约 2 KB”仅估算。用实际最长允许项目ID、工种、安排ID和31个日期计算 UTF-8 序列化字节，记录数值及依据；文档大小真实平台限制执行前再核对。

## 报告需修正的事实

1. 摘要“不新增字段”与 §6.1 冲突，应写新增字段及结构语义变更，集合数不变。
2. 不得宣称目录与计数同事务写使“与实际不符不可能发生”或新语义“更严格”。
3. “不存在跨桶问题”改成多个桶在单一事务中协调、预算可控但仍要验证。
4. listSchedules 当前不按 workerUserId 过滤；草案 §6.2 称成员工种索引仍由此接口使用不准确。按修订后所有实际查询列索引，尤其事务外核对扫描仍可能需要该索引。
5. 集合未创建不是现存集合 Count=0，区分存在性与数量证据。
6. 缺目录并发初始化只要求初始化恰好一次；两个不同日期/合法容量的创建可在重试后都成功，不应断言业务只能成功一个。
7. 平台冲突重试不一定触发 VERSION_MISMATCH：若安排版本未变，仅 guard 变动，重新校验后可以成功。不要将 guard.version 与 schedule.expectedVersion 混同。
8. 不保证操作次数少就能在 3 秒内完成，删除无测量依据的 10–30 ms 数值。

Codex 收到修订稿后核对两项阻断是否闭合，再给出一轮明确实现任务。测试继续覆盖四种路由交错、七集合快照（含新增字段）、目录误删、自洽但错误目录、扫描期间变更、重试重新扫描、幂等、超预算首写前拒绝、同月不同日与同日竞争。
