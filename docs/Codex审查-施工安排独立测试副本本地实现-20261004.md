## 2. 必须修复

### R1 · P1：可信身份传递契约不一致，所有正常业务调用失败

位置：`miniapp/cloudfunctions/scheduleSandbox/index.js:44`、`:108`、`:115`；原 `memberAccess/service.js:73`、`:137`。

包装层生成 `appId/openid`，随后原样传给 `service.execute`；复用业务层读取的是 `APPID/OPENID`。配置合法、真实上下文完整的 identify 仍返回 `IDENTITY_UNAVAILABLE`。定点复现：数据库工厂被调用 1 次，业务数据库操作 0 次。

**返修**：包装层分别保存门控所需上下文与业务层所需的可信微信上下文，显式转换；不得从请求体补身份，不修改 vendor 或原业务源码。

**验收**：测试必须进入实际 `index.main`，覆盖启用后的正常身份登记、建项目、邀请及施工安排路径；错误/缺失 APPID、OPENID、环境、允许账号仍在可判定的最早阶段拒绝。

### R2 · P1：客户端白名单删除了真实业务必需字段

位置：`miniapp/miniprogram/utils/schedule-sandbox-client.js:55`、`:73`。

实际捕获发送内容：createProject 丢失 `name`；createInvitation 丢失 `role/trades`；approveInvitation 丢失 `invitationId/applicantNumber`；createSchedule 丢失 `form/expectedConfirmed`；cancelSchedule 丢失 `expectedVersion`。update 同样需要 `form/expectedVersion`，removeMember 实际使用 `userId`，当前白名单没有。这会在 R1 修复后继续导致正常操作失败；顶层 `content/version` 不能代替真实契约。

**返修**：按实际开放动作定义完整字段契约与嵌套 form 白名单，保留 restDays、日期确认、版本、原因等真实业务输入；继续禁止调用方改变目标环境、函数、集合或可信身份。不要简单改为整包透传。核对微信调用选项的环境指定方式，并在测试中检查真实发送参数。

**验收**：启用配置后的客户端 → actual main → vendor 链路走通；逐动作断言必需字段到达业务层、禁止字段未透传。未知动作不生成业务请求。

### R3 · P1：持久防重不保证“本轮唯一项目”，回放绕过当前权限

位置：`miniapp/cloudfunctions/scheduleSandbox/project-guard.js:29`、`:65`；`index.js:99–110`。

- 确定性 ID 包含 requestId；同一轮、同一负责人，仅换 requestId 即创建第二个项目，**无需并发**。定点复现项目数为 2。
- `projectReadyMarker` 只有非空字符串检查，没有读取或更新持久状态，不能充当“本轮项目已建立”事实。
- 已有项目命中后先返回，未核验用户 active/当前 primary、未核对输入摘要。复现同号改名称被接受，用户停用后同号仍返回成功。
- 回执写在创建事务之后，且读回回执函数并未被入口使用；丢响应、同号并发和回执失败没有形成原子且可恢复的协议。“窗口极窄、单人操作可接受”不属于已批准的放宽。

**返修**：在新包装层建立本轮唯一项目的持久约束，绑定轮次、可信执行人、输入摘要和原结果；换 requestId 不能增加第二个项目。成功回放必须先核验当前身份/权限，同号不同载荷明确拒绝。创建、唯一性状态和回执须具备一致提交/冲突重试及故障恢复语义；不能用项目存在即成功替代。保持原业务算法和生成副本不变，采用本地、限定 createProject 的包装机制；如无法在此边界完成，先说明确切冲突，不自行放宽标准或修改旧后台。

**验收**：顺序不同号、同号并发、不同号并发、同号不同载荷、失权/停用回放、提交后响应丢失、回执写失败。断言本轮一个项目、一套初始成员、一条创建审计和一致原结果；失败不得遗留半套状态。使用有重复主键拒绝及冲突检测的替身。

### R4 · P1：阶段与项目范围存在绕过

位置：`gate.js:51`、`:97–149`；`index.js:81–87`。

- 未识别 phase 被自动改为 prepare；只有动作黑名单，没有分阶段允许列表，准备期也放行施工写动作。
- 准备期 `assertProjectScope` 无条件返回；原 A/B/C 未被硬拒绝，若把这些 ID 配成允许目标，执行期比较也会放行。
- 入口仅在请求带非空 projectId 时检查范围。applyInvitation 用邀请码自行解析项目、不要求请求带 projectId，因此执行期可对另一测试项目提交申请；复现另一项目邀请变为 requested，产生 2 次写入。
- 未知动作进入 identity 后才报 BAD_INPUT；首次见账号会写 users 和注册审计，复现为 2 次写入。

**返修**：明确 prepare/execute 各自允许动作及无项目动作例外，缺失/未知阶段拒绝。项目创建后以受控登记/本轮持久记录限制准备期成员操作；执行期所有项目相关动作均限制唯一 ID。根据实际邀请/成员/安排记录核对归属，不能只信请求的 projectId；列表亦不可泄露其他轮次项目。显式拒绝 A/B/C，拒绝配置误指这些 ID。已知非法动作、配置和项目参数在数据库访问前拒绝；必须读记录才能判定的归属检查允许受限只读，但拒绝时零写入。范围保护不替代原服务权限。

**验收**：实际 main 的阶段矩阵、未知动作/阶段、缺 ID、A/B/C（包括误配）、跨项目邀请码/邀请/安排/成员、列表隔离；统计实际数据库访问和写入。不要仅单测 gate 函数。

### R5 · P1：没有可用测试页面，也没有结果未知时的持久状态

位置：`miniapp/miniprogram/config/schedule-sandbox-proof.js`；`utils/schedule-sandbox-client.js:74–103`；`app.json` 及 pages。

代码检索：**没有页面导入新客户端**，8 条路由没有独立测试页面。只新增配置与函数不满足方案 §4.3 的可见测试入口。`sandboxProjectId` 完全未被读取，启用后即使其为空也会发送项目操作。`cacheKey()` 只是拼字符串；没有保存请求快照、恢复未决请求或阻止二次提交的实现，调用方缺号时每次调用又新生成 requestId。返回错误里的原 requestId 不等于防重闭环。

**返修**：完成清晰标注“施工安排独立测试”的专用本地页面/受控入口；可以依赖注入复用界面，但必须确定调用新客户端。分阶段校验所需配置，项目动作缺目标/错目标零请求；无项目身份准备动作有明确例外。实现未知结果的请求编号及提交快照保存、同号重试、退出重进恢复、存储失败拒绝发送、未决期间防止改表单再次提交，缓存与旧页面隔离；凭据不写报告或长期缓存。原页面原路径、旧探针、旧入口开关、env-gate 行为不变。

**验收**：实际页面与启用客户端测试，不用“入口仍关闭”代替异常分支。包括 develop/trial、release/未知版本、缺项、错项目、网络未知、二次点击、退出重进、存储失败、无旧函数/本机回退。新增页面后才执行相应路由及 WXML/WXSS 编译。

### R6 · P2：集合白名单会接受原型属性，句柄并非不可改写

位置：`collection-map.js:34–59`、`:152–168`。

映射表是普通对象，查 `COLLECTION_MAP[name]` 只判真假。`constructor/__proto__/toString` 被当成已登记名称，将 function/object 传到下层 `collection`，本机 spy 确认 3 次调用，未在适配层立即拒绝。尚未证明能够访问旧集合，不作此扩大结论。代理只拦 set，`Object.defineProperty` 仍可改写句柄，违背交付中的不可改写承诺。

**返修**：无原型映射表或自有属性严格校验，限定返回值为已登记字符串；未知 API 同样避免继承属性穿透。保护集合、查询、文档及事务包装对象的可变性，不暴露原始句柄。

**验收**：原型名、空名、未登记名在事务外/内均零下层调用；defineProperty/delete/setPrototypeOf 不得改变方法；正常 SDK 方法仍可用。不要依靠下层 SDK 恰好报参数错误通过此项。

### R7 · P1：当前测试存在“没测到但通过”的关键缺口

位置：`schedule-sandbox-isolation.test.cjs:182`、`:291`、`:317`；`schedule-sandbox-frontend.test.cjs:96–122`；`helpers/sandbox-test-db.cjs`。

- 业务链直接用 vendor，绕过 index，未检出 R1；前端 6.5 查源码字符串，6.6 接受“默认关闭”作为网络异常通过条件。
- 移出保护用例先取消唯一安排，再传 `targetUserId`（实际字段为 `userId`），只断言任意异常；这不能证明 active 安排阻止移出。
- 重入测试由外部捕获后再次调用整个事务，不是 SDK 在同次 runTransaction 中重调回调。
- 变异构造了一个另写的 brokenDb，没有变异交付适配器并跑同一业务用例。
- 替身 add 覆盖同主键，不拒绝重复键；并发事务整表快照提交没有冲突检测，不足以支撑创建唯一性/幂等结论。

**返修**：把 R1–R6 的实际入口反例纳入回归；新增测试必须启用合成配置并断言实际到达预定分支。移出保护在正确参数和 active 安排下断言 `WORKER_HAS_ACTIVE_SCHEDULES`，取消/改派后另测合法移出。重入由模拟 SDK 调同一回调，变异实际事务映射后同一真实路径须失败。对创建并发使用可控屏障、重复键拒绝和冲突重试，检查写入/提交/回滚及结果；不要把简单隔离替身描述成平台事务模型。

**文档同步**：两份顶部接续说明标“返修中”，纠正“专用入口已完成”“未知结果防重已覆盖”“恶意名称全部拒绝”“只形成部署候选”等超出证据的结论。原 WB 交付历史保留，本轮审查是当前状态。区分原源码测试、包装层、页面、SDK 离线和真实平台五类证据。
