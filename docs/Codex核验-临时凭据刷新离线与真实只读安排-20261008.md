## 3. 需要保留的事实

1. 固定 CLI 的临时登录判定依赖 refreshToken；刷新函数返回 data，缓存替换和 resolveCredential 不会自动从旧状态补回缺失的 refreshToken。新夹具按该合同提供完整合成响应，不是自行宣称平台响应已核验。
2. CLI 会先写回刷新响应，再输出或报错。因此命令失败不保证登录缓存未变。自有代码不读取或修补真实认证文件；将来官方 CLI 使用登录目录，可能自行刷新其缓存。
3. 取得一次有效快照之后，后续三条关联查询与 SDK 复用该快照；不得刷新补取、混用另一批凭据。
4. CLI exit 0 不等于凭据有效；已过期输出仍须被宿主拒绝。初始化状态也不能由“凭据获取成功”推导。
5. 本次只覆盖固定版本的这些分支，不证明平台响应形状、IAM、实际网络或生产同批链。原先“刷新分支离线未完成”的历史记录不改写，由本报告接续。

无需再开发通用凭据工具。复用已验收的 `runReadOnlyObservation`，使用受审的一次性本地执行包装调用模块，唯一能力开关为 `allowRealCredentialFetch:true`；不注入 fetchCredential、spawn、worker、时钟、fixed 路径或任何响应替身。公开 CLI 默认开关继续关闭，不修改业务实现或 proven 常量。

执行包装在运行前核对本文第5节固定代码指纹、原始CLI指纹与本地准备结果。包装只接收原编排器返回的净化报告，不接收或打印凭据快照。将净化结果以新时间戳和UUID命名并使用排他创建保存；异常只输出固定失败类别，不输出 stack/message/cause 或原始子进程内容。

采用两层证据：原编排报告原样保留其 INCOMPLETE/proven=false；外层只记录实际启动、时点、代码哈希、是否使用真实未替换模块及哪些阶段取得有效响应。不制造“已完整通过”的绿色状态，不把数据读取成功等同初始化资格。

1. 检查固定安装与已验收模块、本地15项准备、获取 cwd/profile 发现边界。仅检查真实认证文件位置，不打开内容。
