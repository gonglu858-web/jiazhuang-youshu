## 2. 一次归并的剩余返修清单

### R4 / P1：先恢复证据守卫与最终判定，再据此声称通过

定位：[v5 核验](证据/CodexL2单根对照离线核验v5-20261031.cjs)第 43–65、73–100、490、543、620–635 行。

1. 本版只包装 http/https.request 和七个公共进程函数。此前的 Socket、dns.promises、fetch、ChildProcess.prototype.spawn 等覆盖没有保留。四类真实入口形状的 VM 反例由独立兜底各阻断 1 次，受审脚本均记录意外 0、36 项全过、ok=true/exit0。不能把独立兜底拦截当作本脚本守卫通过。
2. `FILES` 的首次文件读取发生在守卫安装前。在该读取点注入被 catch 的合成 HTTPS 尝试，仍 ok=true/exit0。应在全部受审业务读取/装载前安装守卫；明确探针阶段，不以“前五次命中”自动划成探针。
3. `ok/exitCode` 在 `H(bytes.strictCheck)` 等摘要计算前冻结。实际摘要计算点注入一次被 catch 的 HTTPS，真实摘要照算，最终 JSON 为 **ok=true/exitCode=0，同时 guard.unexpected=1**。所有必要读取、摘要、核验与收尾事实完成后，再由最新计数形成唯一结论。`!IS_FAULT` 也不应成为故障必失败的独立捷径，须证明计数本身决定出口。
4. `vmLoadVerified(digest, bytesBuf, relPath, deps)` 只比较调用方传入的摘要标签，不计算 bytesBuf 的实际摘要；未知 relPath 还直接豁免。实际私有装载入口反例：清空缓存后，传受审 driver 摘要加不同的合成源码，源码仍被执行；未知路径也可装载。应由装载器对自己将执行的字节计算摘要，先核验路径、实际字节与固定预期，再访问绑定同一来源的缓存。准备器与严格检查器目前另行 require，也需纳入必要依赖的唯一来源，不得让报告摘要与执行版本分离。

验收：正常对照、已有故障、四个遗漏入口、首次读取前、实际末尾摘要点、伪造摘要标签、未知路径、缓存不一致及必要依赖装载漂移统一进入实际出口。全部网络/进程反例必须保留独立离线兜底；历史 v5 不修改，新版才承载修复。

### R1 / P1：固定来源槽位必须约束真实交付路径

定位：[驱动 v3](证据/CodexL2单根产物绑定与单次驱动v3-20261031.cjs)第 83–103、123–150 行。

`bind()` 强制来源声明为 `artifacts/psr-l2/rootonly-v3-helper/rootonly-helper.exe`，但 `createRunner()` 只要求实际 productPath 是非空字符串。用正确来源声明和匹配的合成 PE 摘要、将实际路径置为 `C:\synthetic\bound.exe`，持有/启动/后验全走另一位置，仍 ok=true。这不是路径访问器二次读取问题，而是声明与消费之间缺少对应关系。

此外 binding 的 artifactRelPath/configRel getter 仍读取调用方 provenance，绑定后改变原对象即可改变公开的来源事实。

验收：把必要来源字段形成内部不可变快照，将固定仓库根、固定产物相对路径与实际持有/启动路径关联。不同路径、相对/非规范目标、来源事后改写均不能转成合法来源；拒绝必须零启动。同路径及来源合法对照保留。本轮仅准备替身接口；不得伪造真实编译后记录，也不能把 compiled=false 的准备声明当成真实产物来源证明。

### R2 / P1：关闭未知要回收，已有意外不能被后读覆盖

定位：驱动 v3 第 198、250–270、290–291 行。

- awaitExit 返回 `{closed:false,timedOut:false,status:0}` 时，代码记录 CLOSE_UNCONFIRMED 后直接进入 finally，实测 wait=1、kill=0、release=1。拒绝结果本身正确，但没有尝试终止及有界回收；不能释放产物持有后留下可能仍活着的子进程。该分支必须进入与其他失败一致的收尾，保留第一失败和实际关闭未知事实。

### R3 / P2：独立预期和被检查值都必须不可变

### R5 / P2：夹具源码未闭合，不能归为“只待动态验证”

定位：[准备器 v3](证据/CodexL2单根Run合成边界准备v3-20261031.cjs)第 31–32、147–149、329–382 行及[生成夹具](证据/CodexL2单根Run合成边界夹具v3-20261031.cs)第 153、167、174、246–299 行。

验收：修正准备器而非仅改落盘夹具；保持真实 Run/Receipt/Output 等控制流提取，对每个 Hook 建立一致的类型、输入、返回与状态约束，逐场景推导成功/失败和资源事实。针对作用域、成功收尾、字符串回执、正文提取、删关闭/乱序增加有区分力反例。静态核验不能冒充完整编译证明；允许范围内仍无法闭合时标“准备未完成”，不要发出编译建议。本轮不新增编译授权。
