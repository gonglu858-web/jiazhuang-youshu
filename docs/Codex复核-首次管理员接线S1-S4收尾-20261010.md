## 2. S2 剩余：三种期限与异步边界不能混用（P1/P2）

### 2.1 计划单独到期仍然提交（P1）

worker 393–416 行只比较 `cred.expiresAtMs` 和 `payload.approvalExpiresAtMs`，没有比较 `plan.expiresAt`/`normalizedPlan.deadlineMs`。479 行的 `planExpiredDuringRun` 实际统计的是批准期限，也会误报。

实测：计划 1 秒后到期，凭据/批准 100 秒后到期；在 users 事务读事件把时钟推进 2 秒。结果：primarySet=1、auditSet=1、commit=1、abort=0；随后回读才因计划无效返回未确认；`planExpiredDuringRun=false`。这不是平台行为，是本地守卫少了一项。

最小修正：执行守卫分别检查计划、批准、凭据三个期限；事件测试分别只让一种过期，其余保持有效。计划读后过期必须零 set/commit，并保留 abort 实见事实。

**对上轮 Codex 建议的更正：** P4 `resolveNowMs`（257 行起）只接收有限数值，不接收函数。上轮报告建议“给 P4 传实时函数”不可直接照做。WorkBuddy 在新 worker 包裹适配边界的方向正确，继续保留 P4/适配器不变；只是守卫覆盖尚不完整。

### 2.2 begin 后过期丢失事务句柄（P2）

worker 686–692、707 行把 begin 也套进“执行后再检查”的通用 wrapper。底层已返回 tx，后检查抛错，P4 的 `tx = await beginTransaction()` 没机会赋值，catch 无 tx 可 abort。

实测：begin 事件过期，begin=1、abort=0、读写均 0。应在新 wrapper 内保留并尝试回滚已取得的句柄，或采用不会丢失句柄的等效顺序；记录回滚失败，不能声称平台已自动回滚。无需改核心。

### 2.3 回读中途过期仍第二读且报成功（P1）

worker 478–479 行在回读前计算期限标记；`readOnlyGet`（712 行）未包守卫，回读后也没重新计算。

实测：提交正常完成，在 primary 非事务回读事件令凭据过期。仍发生审计第二读，readOnlyGet=2，最终 `ok=true/credentialExpiredDuringRun=false`。

最小修正：只读阶段每次实际读取前后及最终收尾复核同批凭据；过期停止后续读，保留已经提交事实，标核对未完成，不重写、不补取另一批凭据。批准的写入期限与只读核对权限须准确区分，不能靠混用标记得出结论。

### 2.4 S2-a 测试实际没有走到读取

测试 1512 行 `approval: syntheticApproval(plan)` 错把计划对象当 userId。该函数需要目标字符串。独立重建完全相同入参：`WORKER_APPROVAL_INVALID`、begin=0、SDK 事件=0；原用例仍因只断言零写和 ok=false 而通过。

改用正确批准夹具，并断言读取事件确实发生、begin=1、预期 abort、预期错误阶段；拆开三种独立期限。WorkBuddy 独立证据脚本使用 `approvalOf(plan)`，确有读后凭据/批准过期验证，不把两份夹具的覆盖混同；但该脚本也没有覆盖计划单独过期。

## 3. S3 剩余：核对能力和未知结果保存没有接完（P1）

位置：host 889–933、938–962。

### 已通过

确定性键在 started 和失败报告中保留；正常退出坏 JSON 不再误判为确定未写；worker 未知结论不会被父层正常退出覆盖。上述不重做。

### 未完成

1. `reconcileReadOnly` 仍是可选注入回调，没有默认的固定两条只读接线。超时样本同批凭据仍有效，却 `NO_RECONCILE_CAPABILITY`、readOnlyGet=0；WorkBuddy 交付 JSON 也明确记录此事实，因此“15/15”不代表原要求的核对路径完成。
2. 结果未知直接 return，没有保存终态。**不保存为成功，不等于不保存未知结果。** 当前唯一持久化是 started，执行事实、终止状态和核对结果会随进程丢失。样本中提供了 persistResult，调用仍为 0。
3. `persistResult` 是否存在仍在成功提交后才检查。删除该回调，完整链照样 commit=1，随后才说未提供保存能力；上轮要求外部动作前确认保存能力尚未落实。
4. `report.reconcile = rec` 原样透传。合成回调返回 `{ok:true,state:'present',extra:'SYNTH_PRIVATE_MARKER'}`，标记原样进入报告，并得到 `reconcileConfirmed=true`；既没有实际两读，也没有本计划审计归属、摘要与记录一致性的核对证据。

### 最小收尾

- 在当前 host/worker 范围内接入固定、受同批身份与时效约束的两读核对，复用 P4 `observePrimary` 的实际契约，不让普通返回对象替代核对事实。允许合成传输注入以离线测试，但必须真正走两条固定读取；不新增云路由/通用恢复系统。
- 核对所需受信上下文从已绑定快照传递。若能力不可用，在写请求前拒绝，而非允许开始后才发现不存在。
- 执行前核对保存能力；保存成功、失败、未知等终态并区分类型，结果新建而不覆盖。不保存未知为成功，不自动重试初始化。
- 核对返回值逐字段/逐值净化；保留原错误、提交与终止事实。子进程未确认结束时，暂时没读到不能证明稍后不会提交。
- 验收：超时/坏输出路径确实两读；凭据过期明确跳过；未知终态独立保存；无第二次初始化/第二批凭据；恶意额外字段不出报告。

这项不是新增范围，是上轮第 4 节与原任务 §4.4 未交付完成的部分。

## 4. S4 剩余：不匹配“丢值”后仍判成功（P1）

host 1160、1180–1181、1218–1223 行把错误审计键与摘要归 null，但不降低 `ok/observationConfirmed`。host 873 行又仅检查 auditId 是字符串时是否不等，null 恰好绕开。

实测：合成 worker 返回干净退出、ok=true，审计键与摘要属于另一计划。父层 bootstrap 的 auditId/inputDigest 被置 null，但仍 `initialized=true/resultPersisted=true/incomplete=[]`，保存回调调用 1 次。

修正要求：对于成功路径必须提供且精确匹配本计划的关键键/摘要；不匹配或缺失应降低为未确认，进入保守只读核对，不能仅丢弃字段后采信成功布尔值。状态、ok、initialized、granted、observed 等相互一致性也应基于已净化的记录，而非独立采信顶层布尔。

补贯穿测试到 executeOnce 的终态与保存调用，不能只断言 `auditId===null`。正常正向链继续通过。S3 新增核对返回对象的原样透传一并修正，不重新开放旧错误码白名单。

## 5. R3-e 测试路径与 EBUSY 表述（需修正）

本次全量实跑：**53 项，52 通过 / 1 失败 / 0 跳过**。单独复跑 R3-e 同样失败：

`Cannot find module './sandbox-primary-bootstrap.cjs'`。

测试 1133–1143 行只把 worker 文件复制到临时目录，未保留它相对 require 的依赖；此失败发生在模块加载阶段，不是 worker 的业务路径失败。

独立新 Node 进程核验：

- `spawnSync(process.execPath, ['-e','console.log(1)'])`：exit 0，stdout=1。
- 直接运行原路径 worker，stdin 只有 credential 而缺 plan/approval：exit 2、WORKER_STDIN_INVALID（第一份证据，保留）。
- 补齐必要对象、保持合成凭据已过期，直接运行原路径 worker：exit 0、WORKER_CREDENTIAL_EXPIRED、stderr 0 字节。SDK/云端路径未进入。

最小修正：直接运行原固定 worker 路径，保留原相对依赖；不要无依据复制单文件绕过“可能 EBUSY”。若当前宿主确实 EBUSY，如实记该时点错误/未验证，不能把所有探针失败硬归因 EBUSY。

**撤回“Codex 网络拒绝钩子残留导致 EBUSY”的因果断言。** 上轮钩子是独立 Node 进程内修改模块对象，随该进程结束失效；没有改磁盘库、系统网络或全局 Node 配置。现有资料不支持它跨进程残留的说法。保留 WorkBuddy 当时观察到 EBUSY 的记录，原因未知；不要改写历史证据来对齐本次结果。
