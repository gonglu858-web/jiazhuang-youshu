## 3. U3 剩余 · P1：页面创建的合法操作被自己的恢复校验判坏

**分类：本轮修复引入的回归；属于原 U3 范围，不是新要求。**

位置：`miniapp/miniprogram/pages/schedule-sandbox/schedule-sandbox.js:351–354`；`utils/schedule-sandbox-client.js:662–671`、`:476–478`。

页面 `buildPayload()` 在有登记项目时给**所有动作**都加 projectId；客户端 preflight 允许 PROJECT_OPTIONAL 动作携带该目标并保存/发送。新 `validateEnvelope()` 却把同一记录判为“无项目动作却带有目标”。

**已复现，不改存储、不伪造记录：**

1. 合成配置登记 `p_sbx_target`，正常 identify 绑定账号。
2. 实际 Page `onLoad()` 后执行 `runAction('listMyProjects')`。
3. 请求带上该 projectId，注入传输超时。
4. `readPending()` 返回 `available:false`；恢复报 `SANDBOX_STORAGE_UNAVAILABLE`，不能按原号重试，后续普通提交也被这个记录卡住。

WorkBuddy 的 U3-c 直接向 client 提交**没有 projectId**的 createProject，绕开了实际页面，因此没有覆盖本例。

**固定修复方向：**统一 Page 组包、client 发送前置及 envelope 校验的动作目标契约。既然本轮定义五个 PROJECT_OPTIONAL 动作不需要项目，正常组包不要为其自动添加目标；客户端须在保存和发送前统一处理不符合契约的输入，不能发送一个自己稍后判损坏的 envelope。项目必需动作保持目标非空及严格匹配。不要在恢复阶段删除/改写历史快照来绕过检查，不清用户缓存。

**完整验收清单（同一批完成）：**

| 场景 | 预期 |
|---|---|
| 实际 Page，有/无已登记项目，五个无项目动作组包 | 动作契约一致，不自动加项目；identity/listMyProjects/createProject/取号/申请均检查组包，使用合成凭据 |
| Page listMyProjects/createProject 响应丢失后显式恢复 | 可读原 envelope、当前身份一致、同编号同快照，不注入配置目标 |
| 取号/申请结果未知 | 可读且保留证据，继续按非幂等策略拒绝重发，不能误报结构损坏 |
| 项目必需动作缺目标/换目标 | 零请求，原记录保留 |
| 真正动作/项目/账号/快照损坏 | 保持拒绝，不以本次修复放宽 |
| 客户端直接收到违约目标参数 | 发送前可预测地拒绝或按明确无项目组包契约处理；不得发送后才判坏 |

## 4. U5 剩余 · P2：把 checkbox 的事件当成 switch 的布尔事件

**分类：上一轮已经明确要求的组件事件核对未完成；日期绑定逻辑本身已通过。**

位置：`pages/schedule-sandbox/schedule-sandbox.wxml:81`、`schedule-sandbox.js:294–309`、`tests/schedule-sandbox-frontend.test.cjs:1109–1127`。

当前使用原生 `<checkbox bindchange="toggleDateConfirm">`，处理函数只接受布尔 detail.value；新增测试也硬性要求这一写法。微信原生 checkbox 的选中集合由 **checkbox-group 的 change 事件**报告，value 为字符串数组；布尔 value 是 switch change 的契约。

本轮核对的第一方依据：

- [微信官方 API 类型](https://raw.githubusercontent.com/wechat-miniprogram/api-typings/master/types/wx/lib.wx.event.d.ts)：CheckboxGroupChange 为 string[]，SwitchChange 为 boolean。
- [微信官方原生 checkbox 示例](https://raw.githubusercontent.com/wechat-miniprogram/miniprogram-demo/master/miniprogram/packageComponent/pages/form/checkbox/checkbox.wxml)：change 绑定在 checkbox-group 上，内部 checkbox 提供 value。

官方组件文档站本次无法读取，采用上述微信官方仓库源码核对，未把第三方文章当作依据。没有进行模拟器点击或真机验证。独立脚本确认：模板没有 checkbox-group；向实际处理器送入符合 group 契约的选中数组，仍被判未确认。因此现有布尔模拟通过与 WXML 编译通过均不足以关闭 U5。

**固定修复方向：**使用原生 `checkbox-group bindchange` 包裹唯一 `checkbox value="date-confirm"`，处理器按数组判断该固定值是否选中，保留已正确的 dateConfirmedFor 日期组合绑定。无需再选择方案，无需改其他页面。

**完整验收清单（同一批完成）：**

1. 模板 change 绑定在 group；checkbox 有固定 value；处理器接收 `['date-confirm']` / `[]`。
2. 选中后才能发送日期不一致的表单；取消选中立即撤销确认。未知值/错误类型不确认。
3. 修改 endDate 或 expectedDate 后原确认失效；重进/切动作不沿用旧确认。
4. 日期一致不额外阻断；原未决请求的恢复仍使用原快照，不被当前表单改变。
5. 替换原来强制 `<checkbox bindchange>` / 布尔的错误断言及文档说法；新增证据，不改写历史 JSON。
6. 编译与处理器测试分别记录；没有实际点击验证时如实说明，不把调用 Page 方法称为原生控件运行验证。
