## U1 [P1] 回执被移到独立事务，实际写事务失去并发幂等检查

位置：`miniapp/cloudfunctions/memberAccess/schedule-service.js:883–901`；四个写回调从 `:1012`、`:1074`、`:1138`、`:1180` 起。

`tryReceiptReplay` 在独立事务中查回执，无回执才开始扫描/写事务。但实际写事务已删除 `checkIdempotency`。两个相同requestId请求可以同时查到“无回执”，其中一个先提交，另一个冲突重试/重扫后直接检查占用、业务版本或取消状态，无法返回刚刚产生的原回执。

独立复现使用两个服务实例（对应两个独立请求）共享具备冲突检测的内存数据库，固定双方先完成“回执不存在”检查：

| 同号同载荷动作 | 先完成请求 | 后完成请求实际结果 |
| --- | --- | --- |
| create | 成功 | SCHEDULE_CONFLICT |
| update | 成功 | VERSION_MISMATCH |
| reassign | 成功 | VERSION_MISMATCH |
| cancel | 成功 | BAD_INPUT：已取消 |

当前样本没有重复落库，新增审计/回执也只有一次；**缺陷是成功请求被错误报告成业务失败，原号重试契约未满足**。不要把它描述为已证实重复落库。

### 必须修复和验证

- 独立的回执快速返回可以保留，但每次实际写事务/SDK回调重入/外层重扫也须在当前身份、权限、维护策略核验后重新查回执，然后才检查目录、容量、业务版本与占用。
- 同号不同载荷仍拒绝；失权/维护不能因有回执而放行。
- 四动作分别加入同号同载荷并发，双方得到完全相同原成功结果；业务版本只推进一次、审计/回执恰好一次，八类集合结果确定。
- 补同号不同载荷竞争；确保不是靠SDK重复键错误代替明确业务码。
- 修复将增加实际事务操作数，U3预算表须同步重测；不能沿用当前74作为返修后的证明。

## U2 [P1] 维护切换入口仍能使用失效权限，且无就绪核验即可恢复ready

位置：`miniapp/cloudfunctions/memberAccess/service.js:356–360`；`schedule-service.js:642–653`。

批准成员和指定管家的新维护守卫、epoch写均已在各自事务内，原T4静态维护漏洞已修。**但原T4同时要求的维护切换控制仍未修**：`setScheduleWriteMode` 只在事务外调用managerAccess；`setMaintenanceMode` 没有接收执行人，只检查项目存在就切换。

补充复现：事务外鉴权后、切换事务开始前，把执行人账号设disabled、成员设left，切maintenance仍返回成功。另一个案例中项目处于maintenance且成员缺少锚点，仍可直接切ready。当前只是内存复现，没有改变任何真实账号或云端模式。

### 必须修复和验证

- 维护操作应有明确受控执行权限，并在实际事务内重新核验账号、角色及项目有效范围；不能凭事务外旧身份切换。
- 恢复ready必须依赖就绪核验。尚未实现修复/核验流程时，选择先封闭普通接口的ready分支，明确返回拒绝并留在maintenance；不要用“以后部署流程保证”的注释代替现有入口约束。本轮不要求安装或执行迁移脚本。
- `approveInvitation` / `assignManager` 与实际维护切换分别补两种提交顺序、冲突重试和最终成员/锚点/epoch/审计断言。
- 当前T4c只测试removeMember，并直接修改projects模拟干扰；其注释与实际提交顺序也相反。它不能证明上述两个新成员入口和实际维护切换路由的双向交错。
- 明确更新旧项目影响：字段缺失现在不仅阻止removeMember，也会阻止approveInvitation/assignManager。A/B/C的兼容准备仍由Codex部署前另做，不在本轮改云记录。

## U3 [P2] 计数器是服务实例共享状态；预检低估且测试没有验证产品边界

位置：`schedule-service.js:74–89`、`:108–123`、`:792–822`；`miniapp/tests/schedule-service.test.cjs:2556–2571`。

### 实现问题与准确范围

1. `attemptOps/attemptPeak` 定义在createScheduleService作用域，每次transaction开始重置同一变量。它不是每个transaction callback私有状态。
2. 独立复现：同一服务实例A尝试已读60次时暂停，B尝试开始、重置计数并读10次，A继续30次。A实际读了90次仍成功。当前云函数index.js每次调用创建独立service，**这不是已证实不同云调用共享计数**；它证明复用同一实例时违反“每attempt独立预算”，也会污染同实例并发测试。
3. 单次顺序执行的产品计数确实存在，逻辑允许前80次、在第81次底层操作前拒绝；不能描述成“第80次被拒绝”。
4. `wrapTx`缓存的是collection包装对象，并没有缓存文档读取结果。预算注释称重复读取可复用，与实际不符。预检70、实测74不相等；两者虽均小于80，仍不能把低估式作为完整上界。其余动作也有低估（18/19、16/22等）。
5. T3b直接调用`db.runTransaction`，没有经过产品transaction包装；它断言的是夹具APP_TXN_BUDGET_EXCEEDED或平台码，不是产品的SCHEDULE_OPERATION_BUDGET_EXCEEDED。读取导出的常量不能证明产品边界。

### 必须修复和验证

- 把计数器放到每次SDK回调创建的闭包中，由该回调的wrapTx传递；同实例并发和SDK重入互不重置或累计。
- 预检采用覆盖所有实际分支的保守上界，或逐项精确计数；不要求为了表格好看缓存文档，但不能虚构缓存。标出首用/已初始化、换责任人、单/双工种和桶数量的实际差异。
- 隔离验证产品80：底层夹具不做80拦截或只设100，经过真实产品包装读满80次成功、第81次前抛产品预算码，并核实底层只执行80次；再测两个并发attempt独立计数、SDK重入从0计数。
- 为首写前预算预检补独立断言：预算超限时底层写调用0，八集合不变。可用受控测试注入构造不可支持预算，不能只验证常量，也不能把写后回滚称为“首写前拒绝”。
- 保留真实26桶成功的固定预期，U1补检查后重新记录峰值；本轮74成立，后续新版本不得直接复用。
