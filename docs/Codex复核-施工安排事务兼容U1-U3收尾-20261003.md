## V1 [P2] 同号并发正式测试没有锁住“快速检查之后”的竞态

位置：`miniapp/tests/schedule-service.test.cjs:2865`、`:2877` 起的 U1a–U1d。

现有 barrier 停在 A 的快速回执事务**提交前**；B 完整提交业务及回执后，A 的快速事务发生冲突重试，便可直接找到回执返回。注释“恢复 A 后必须在实际写事务重新查回执”不成立。

实证：仅在内存中删除四个实际写回调的 `checkIdempotency` 与命中返回，保留快速返回路径，现有 U1a–U1d **仍全部通过**。这证明回归覆盖有缺口，不代表当前产品实现仍有原缺陷。

Codex 另将 barrier 放在双方快速事务**成功结束、返回 null 之后**，再释放实际写入。当前四动作均返回完全相同原结果，业务版本只推进一次，回执/历史/审计各增加 1 条。

下一步仅补测试：将这个屏障位置及明确的 `fastNullReturns === 2` 断言纳入正式回归；四动作检查相同返回值、业务版本、回执/历史/审计与全集合变化。保留不同载荷、失权、维护拒绝用例。测试须能检出删除实际写回执复核的变异，不得只靠测试标题宣称覆盖。

## V2 [P2] U2d–U2f 未完成两条实际成员入口的双向交错回归

位置：`miniapp/tests/schedule-service.test.cjs:3109`、`:3163`、`:3178`。

- U2d 第一半是移出事务受直接 epoch 修改干扰，移出完成后才调用维护接口；维护事务没有与成员写并行，也没有发生注释所说的维护重试。
- U2d 第二半覆盖移出与维护交错，但不是上一轮明确要求的 `approveInvitation` / `assignManager`。
- U2e/U2f 是先切维护、再顺序调用成员入口；U2e 还是不存在邀请和无效格式编号。它们能验证静态维护拒绝，不能证明有效成员请求在途冲突。

Codex 独立使用有效合成申请和编号，对这两个真实成员路由分别跑两种顺序，均通过：

| 先提交方 | 被暂停并恢复的一方 | 最终结果 |
| --- | --- | --- |
| 成员写 | 维护事务 | 维护冲突重试成功；epoch 1→2→3；成员、锚点和一次审计保留 |
| 维护 | 成员事务 | 成员冲突重试后 PROJECT_NOT_WRITABLE；epoch 1→2；无新增成员/批准审计，编号未消费、申请仍 requested |

每例实际观察到 3 次事务 attempt。正式测试应纳入上述四例及最终状态断言，并修正 U2d/旧 T4c 的顺序注释；勿用直接修改 projects 替代真实维护路由。

## V3 [P2] U3d 标题宣称零写入，但实际断言不是该场景

位置：`miniapp/tests/schedule-service.test.cjs:3290`。

U3d 在事务外直接调用 `assertWithinBudget` 检查公式，再成功执行 26 桶更新并断言写入大于零。没有检查超限真实业务路径的底层写调用为 0，也没有断言拒绝后全集合不变。

Codex 仅在内存里将 create 固定预算 18 调高至 90，经真实 service 创建路由执行：返回 `SCHEDULE_OPERATION_BUDGET_EXCEEDED`，**底层写调用 0、全部集合快照不变**。产品首写前拦截位置已验证正确；应将这种受控注入纳入正式测试，并保留正常 26 桶成功回归。

另作同范围测试补强：U3c 目前仅检查 attempt 数量与最终成功，没有直接量化重入的计数从 0 开始。可让两次 SDK 回调分别接近/达到 80 次并记录每次底层计数，以确保累计计数错误会失败；不需要修改产品计数实现。
