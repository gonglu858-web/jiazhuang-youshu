## 二、H1 仍未关闭 / P1：客户端先把所有字符串 code 判为 validation

定位：`miniapp/miniprogram/utils/schedule-client.js:34–54、78–84`，页面 handleSendError/handleCancelError。

classifyError 开头对任何字符串 code 直接返回 validation，后面的 TIMEOUT/NETWORK/ECONNRESET 等判断无法执行。页面优先采用 error.kind，因此客户端处理过的 TIMEOUT 不会被页面的兜底网络判断挽回。

独立联测结果：实际 service 已创建成功 → wx.cloud.callFunction 替身抛带 code=TIMEOUT 的网络错误 → 真实客户端标 validation → 实际页面变 failed/recoverable → 用户改日期再保存 → 内存数据库出现两份安排。现有页面测试直接 mock createSchedule 抛 TIMEOUT，绕开真实客户端，所以没有覆盖这个缺陷。

响应结构也没有严格验证：

| 模拟响应 | 当前客户端结果 | 应有边界 |
|---|---|---|
| result={} | business / SERVER_ERROR | 缺少可靠业务结论，结果未知 |
| result={ok:false} | business / SERVER_ERROR | 缺少明确业务码，结果未知 |
| result={ok:'yes'} | 成功返回 | 非布尔成功标记，拒绝作为成功 |

**最小修复与验收：**

1. 以错误来源分类：callFunction 的传输拒绝不能因带 code 就当本地校验；发送前的本地校验/入口拒绝明确标记。已知网络码与未知传输异常均保留 unknown。
2. 校验响应为合法对象，ok 必须严格布尔；明确业务拒绝须有符合协议的业务码，缺项/畸形不伪装成业务失败。写成功响应也核对接口必需字段。不要仅换正则顺序后遗漏未知字符串 code。
3. 保留原 requestId 和完整快照，未知结果只能原请求重试。取消 retryCancel 直接使用 pendingCancel 快照；当前仍调用 cancel() 再弹原因输入框、比较实时页面 version，与“无需读取当前页面、以完整快照重试”不符。取消重试不应要求用户再次准确输入旧原因，也不应被旧页面状态提前挡住；在途防重保持。
4. 补真实客户端参与的页面—服务离线联测：带 TIMEOUT/ECONNRESET 的异常、errMsg 对象、未知 code、响应缺失/畸形、普通业务拒绝；服务端已写成功但响应丢失后，修改被挡、原号重试只有一份安排/一次版本变化。取消也补已成功但丢响应后原快照恢复结果。

## 三、H2 仍部分未关闭 / P2：取消与本机校验错误不能恢复

### 取消路径

定位：`miniapp/miniprogram/pages/schedule-detail/schedule-detail.js:185–195`。

取消弹窗填空 → 设置 errorKind=recoverable 与 error → 再点击取消，入口条件 `(this.data.error && !isUnknown)` 直接返回。独立复现 modalCount 仍为 1，用户没有第二次填写原因的机会；编辑按钮也被 error 拦截。明确业务拒绝同样会留下这个阻断。

要求取消入口区分 blocking/unknown/recoverable，允许可纠正错误重新填写；权限、加载、在途和未知结果限制必须保留。

### 本机路径

定位：`miniapp/miniprogram/pages/schedule/schedule.js:154–156、274`。

本机空施工内容保存触发 business.saveSchedule 普通 Error，errorKindOf 默认返回 blocking；用户补内容再保存被 save() 的 blocking 条件拦截。独立复现与上一轮云端卡死相同。

要求本机发送前字段校验失败可纠正；不要全局将未知错误都改 recoverable。增加“空内容 → 改正 → 本机保存”及“空取消原因 → 改正 → 取消”的真实事件链测试，断言实际保存/请求及权限限制。云端新增错误恢复本轮已通过，不重复重写。

## 四、H3 仍未关闭 / P1：已有 OCC 夹具，但尚未用于完整移出并发事务

定位：`miniapp/tests/schedule-service.test.cjs:735–1100`；`member-access-schedule.test.cjs:70、164–211`。

本轮确实新增 OCC（提交时检测读写冲突并重试）夹具和更多故障注入，应保留。但：

- 两个交错测试运行的是 hasActiveSchedules 只读检查，不执行实际 removeMember 的成员更新、lockGuard 和审计。

**最小验收矩阵（沿用原 H3，不扩大业务）：**

3. 适用写节点的 add/update/remove 故障注入，以全相关集合快照相等证明回滚；覆盖安排、占用释放、已有 guard 更新、历史、回执、审计。改派双方 guard 不可部分变更。重试成功只产生一次对应变更与审计。
4. 将新增的并发夹具复用于实际路由测试，不以 helper 替代移出，也不通过把全部事务串行化使测试通过。纠正用例名称和完成报告；明确真实 CloudBase 并发仍未验证。
