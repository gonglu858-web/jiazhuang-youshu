## 2. S1 / P1：目录发现使用父进程Home及字面路径，范围仍不等同CLI

位置：`miniapp/scripts/lib/cloudbase-cli-credential-host.cjs:467–502`。

### 两个已复现分支

1. `assertConfigDiscoveryClean` 使用父进程 `os.homedir()` 作为停止点。实际CLI的 `USERPROFILE/HOME` 被设置为登录profile，因此CLI的Home不同。默认系统临时目录通常在父进程Home下：检查会在用户Home停下，而CLI可能继续到更上层。合成access替身仅在父Home上一层报告一个配置标记，当前检查通过，固定bundle的原始 `findProjectRoot` 函数以子进程Home计算时则命中标记。
2. 当前检查从 `path.resolve(cwd)` 开始；固定bundle先调用 `canonicalizePath`，优先 `fs.realpathSync`。本机在全新临时夹具内创建junction，字面路径祖先干净，实际目标祖先有合成cloudbaserc.json。当前检查通过，原始发现函数沿真实路径命中该标记。

第1例没有向真实用户祖先写配置；只是内存存在性替身。第2例为本机真实junction，全部文件位于新夹具根内。算法对照只读取并执行固定bundle中的发现函数片段，**没有执行公共CLI或认证流程，也不替代H1公共入口证明**。不据此声称真实登录配置已污染。

### 最小修复与验收

- 检查以**将传给CLI的实际profile/Home**为参数，不能取父进程Home。
- 以CLI实际采用的规范化/真实路径为起点核对发现范围；至少覆盖可能的临时根目录联接，不以“刚创建叶子”排除祖先联接。
- 不确定范围则启动前停止；不修改官方CLI、不读认证内容、不删除标记。不重写隔离框架。
- 保留新随机cwd正向、已有污染拒绝测试，新增“父Home与子Home不同”和“junction指向带标记祖先”两个场景；断言配置污染时凭据命令尝试0次。
- 同步注释：当前新函数附近仍有“向上找package.json”“后续关联需要真实登录目录”的残留；应按已核对的marker列表及后续全新空profile表述。

## 3. S2 / P2：进程失败未带出尝试事实，错误码/模式存在断层

位置：host `:333–367`；SDK observer `:1384–1389,1669–1699`。

### 实测

真实宿主与编排器配合EventEmitter子进程，四个分支均已进入spawn一次，后续关联请求0次：

| 分支 | 实际行为 | 当前最终报告 |
| --- | --- | --- |
| 非零退出 | code=1，完成exit/close | attempted=false、mode=NONE、diagnostics=null |
| 超时 | 超时后kill1次 | 同上 |
| 合并输出超限 | kill1次 | 同上 |
| 信号退出 | SIGTERM，完成exit/close | 同上 |

原因：只在JSON解析的catch中设置 `fetchAttempted/fetchExitFacts`。这些较早的进程失败从try外抛出，虽有detail但父层只读fetchExitFacts。错误码白名单也与实际宿主不一致，例如实际 `CREDENTIAL_COMMAND_TIMEOUT` 对应列表却是 `CREDENTIAL_TIMEOUT`，另有 `CREDITAL_SIGNALED` 拼写残留，所以均归为泛化失败。

另一个合成异常给出 `fetchMode=任意标记`，`error.fetchMode || 'NONE'` 原样写入报告，标记实际出现。detail已净化不代表新增字段也净化。本例仅损坏错误协议，不是已发生的真实密钥泄漏。

### 最小修复与验收

- 从调用spawn的实际位置统一记录“尝试”事实；所有成功、解析失败、超时/溢出/信号/非零/启动错误都携带同一套净化事实。区分“尝试启动”和“确认进程运行”；创建目录/指纹拒绝等前置仍为未尝试。
- 父层继续逐字段投影，禁止为恢复事实而重新透传detail。错误码与宿主实际导出的常量逐项对齐，不再手抄一组近似名字。
- fetchMode按固定枚举重建，未知值拒绝或省略/归为固定未知分类，不能保留原字符串。保持整体FAILED及零后续请求。
- 补上述四条进程失败、启动失败、解析失败对照与异常fetchMode样本；事件驱动触发，复用既有spawnBounded，不重新修改其已验收计时器和监听逻辑。
