## 2. §14 定点修正

### F1（P1）：补 schema 必须按单字段缺失判断，不能重新捆绑三字段

位置：§14.2 A-1（约第 955 行），B-1/C-1 引用同一条件。

当前同时要求“维护态可建立且围栏可信”与“三字段分类仍为 FIELDS_MISSING”。但 `setMaintenanceMode`（schedule-service.js:658–677）会写 `scheduleWriteMode=maintenance` 与 `scheduleEpoch`，不补 schema。实际进入维护后，项目已不再是三字段全部缺失，schema 却仍需要补；按表执行会再次排除这条合法准备路径。§5 已解决过此问题，不能在新草案中重新引入。

固定改法：

- A-1/B-1/C-1 的补 schema 条件改为“scheduleSchemaVersion 字段不存在；其余字段按实际值分别核验并保留”，不要求项目整体仍为 FIELDS_MISSING。
- 拟执行前重新读取现值；合法现值保留，非法/部分锚点按既有停止规则处理。初始观测标签只说明原基线，不是写入后的永久前置。
- epoch 如果已由维护事务建立或递增，则 A-2/B-2/C-2 的补缺动作跳过并记录，不覆盖、不改回 0。缺失时拟值及承担递增的事务仍留待具体变更包。

### F2（P1）：锚点补缺前置缺少“无”，且拟写字段必须使用真实名称

位置：§14.2 A-3（约第 957 行），B-3/C-3 沿用。

当前写“历史非零代际已被完整证明”，字面上要求已经证明存在非零代际，却拟补 generation=0，方向相反。应为“**已有充分依据证明不存在历史非零代际**”；有证据表明存在或无法证明不存在时仍不可执行。现存 53 条审计未命中不足以满足此条件。

候选拟值使用实际字段 `taskDirSchemaVersion=1`、`taskDirGeneration=0`，不要写成可能被当成实际写键的 `schemaVersion/generation`。保持“两个锚点均不存在 + 无 guard + 该成员完整扫描为空 + 历史门槛满足”的完整条件；NOT_EXISTS 不替代 EMPTY 或历史证明。

同表 B-4“进入维护态”的现值应填写项目 `scheduleWriteMode` 缺失及无管家事实；“无 guard”不是该字段现值。A-4 仅是未来合法业务首用产生目录的行为说明，不作为迁移时主动创建安排/目录的指令。正式包必须使用完整记录 ID；当前缩写只供阅读，不可复制成执行目标。

### F3（P2）：按实际路由描述共享部署影响，删除未经证明的强制全量迁移结论

位置：§14.3（约第 986–997 行）、方案开头 §14 摘要，以及进展/交接最新段落。

“缺三字段项目立即不可写”过宽：新实现的安排四个写动作及批准/指定管家/移出成员会受到新守卫限制；`createInvitation`、`applyInvitation`、取号及身份初始化等仍可能写入。`setMaintenanceMode` 有自己的鉴权/写入路径，也不是统一缺字段拒绝。依据 service.js:44–64、:220–268、:319–362 与 schedule-service.js:625–678。这与方案 §1.3 已列出的逐路由事实须一致。

共享代码更新确实影响所有调用该函数的项目，**但不自动推出“必须同时补齐 A/B/C”或“部分不可写中间态无法回退”**：代码部署与数据库迁移并不因此成为一个原子事务，是否有受控分阶段路径/兼容包/暂停窗口/安全回退要由未来具体方案证明。也不能反过来宣称回退旧包必然安全；旧包可能绕过新围栏，须结合实际已写数据判断。

固定改法：

- 写为“按当前未部署实现，安排四写及三类成员变更在未就绪项目被拒；其余路由按 §1.3 各自处理”。不要写所有写入都停止。
- 写为“完整变更包必须评估 A/B/C 及其他调用方的影响，列明每项目处置、在途请求约束、中断窗口、失败接续及回退适用条件”。
- 删除“必须一次性覆盖 A/B/C 补缺与 B 权限处置”“无法回退”这类未经验证的绝对结论。保留不删除 guard 回到首用、不降低代际、不回退 epoch 的数据约束。
- B 无管家问题保留未决，不自动加角色、不授权 app admin 绕过当前管家入口；本轮不选择或开发新载体。
