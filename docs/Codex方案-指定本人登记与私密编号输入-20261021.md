## 3. 私密编号输入：推荐本机窗口双次输入

### 3.1 用户操作

1. 以后在独立批准的录入步骤打开本机原生窗口，每次仅录入1人。窗口固定显示参与者1或2、对应已核验轮次及尾号，不提供切换角色。
2. 负责人从自己保存的记录输入完整编号两次；输入框默认遮挡，两次须完全相同，严格匹配u_加40位小写十六进制。不可自动补齐、截断或纠正。临时按住显示只用于本人复核，释放恢复遮挡。
3. 用户可主动粘贴进输入框；程序不调用剪贴板读取/监听接口，不记录剪贴板内容。错误提示固定文案，不回显输入值。程序不主动读取聊天、图片或OCR结果。
4. 本地校验格式、两次一致、尾号及参与者/历史核验来源绑定；尾号仅辅助发现输错，不是完整身份的证明。即使错号碰巧同尾，未来服务端必须按可信微信身份与完整允许账号精确匹配，不得退化为尾号校验。
5. 同一批资料内1/2号完整编号必须不同；禁止把0号或其他人混入。与0号排重只能依赖另行批准且已受控取得的完整记录，不能为此翻凭据缓存或猜编号。没有该记录不得声称已对0号完整排重。

### 3.2 存储与使用

- 建议固定私密根为项目下artifacts/schedule-sandbox/.participant-private/。现有隐藏目录忽略规则可覆盖；实现须在任何写入前运行git check-ignore并确认目标未被跟踪，检查根及祖先不含链接/junction、目标为允许目录，失败零写。
- 每人每次录入一个不可覆盖的新记录。用Windows CurrentUser DPAPI加密完整负载，负载含完整编号、参与者代码、固定AppID/环境、核验轮次/服务端时间、来源证据摘要、交付确认、输入时间及schema。检查并限制本机文件访问权限，失败停止。DPAPI不防同一已登录用户或有权限的本机进程访问，不承诺绝对安全。
- 不把编号放进命令行参数、环境变量、stdout、终端历史、日志、异常、测试快照或Git；不写编号明文中间文件。不把全文输入回传助手。
- 对外只出净化回执：参与者代码、尾号、来源轮次、记录随机引用、密文摘要、双次输入一致、加密及忽略检查结果。回执必须标明“人工输入来源，不是平台登记回读”。不公开完整编号的裸哈希作为额外关联标识。
- 不覆盖旧记录；输入有误就新建版本并标记旧引用停用。取消、校验失败不留可用密文；失败后若已排他创建文件，精确记录部分文件并仅清理本次创建路径，不递归清理目录。
- 原始编号仅在输入窗口/加密/装配必要内存中短时处理，尽力清空控件与缓冲区，不宣称运行时内存已可靠擦除。

### 3.3 完整编号会出现在哪里

推荐首版以**完整单一允许账号**作服务端精确匹配，便于与现有算法逐字核对。装配器读取密文并在内存解密；完整值仅写入被Git忽略、访问受限的服务端候选配置，不能进前端包、页面、公开manifest/计划/证据或预览版本输入。公开清单仅记录受审服务端文件摘要，私密输入引用另存忽略目录。

因此候选源文件、上传ZIP及平台函数代码中会含完整允许账号；数据库登记记录和审计也含完整编号，用户记录含OPENID。**不得承诺“编号只在本机/只在内存”。** 未来真实包必须明确告知这些落点并取得批准。关闭覆盖不保证平台旧版本、日志或备份即时删除。

本地私密制品保留到登记回读及后续必要绑定完成，再按准确文件清单另行确认清理；不在本轮删除历史冻结包或原截图。DPAPI密文不作为唯一备份，负责人继续保管原记录。

## 4. 指定本人登记：每包一人、两人分开

### 4.1 请求与身份门槛

- 新协议建议participant-self-registration-request/1，单一动作registerSelf；不接受旧identify或只读inspectSelf。外层容忍平台附带键但不读取其值；内层严格枚举schema/action/registrationRoundId/passphrase，拒绝身份/角色/集合/目标/写入内容自报字段。
- 仅cloud.getWXContext()和受审运行环境提供可信AppID、OPENID、envId。派生算法保持u_+sha256(APPID+':'+OPENID)[0:40]，与本包完整唯一允许账号精确一致。
- 开关默认关闭，目标、协议、轮次、口令、真实时钟、窗口、允许账号全部通过后才创建数据库工厂/事务。未知字段、访问器、Symbol、自定义原型及元操作异常按已审查分层规则拒绝；不修改原只读适配器来扩权。
- plan显式participantCode仅1或2，synthetic/真实模式隔离，真实构建只能消费已核本机密文来源；不能接受计划自报完整编号或跳过来源。窗口正长且≤30分钟；准备允许未来时间，严格执行仍须入窗，剩余>15分钟才启动覆盖。不得更改系统时钟延长窗口。
- 手机展示本机版本、配置轮次、实际提交轮次、服务端返回轮次；不显示完整允许账号。版本计算排除编号/口令/其摘要/绝对路径和随机来源引用，真实生成字节仍由受审manifest绑定。手机说明须明确“首次登记将新增本人测试账号与登记审计”，不能复用只读文案。

### 4.2 原子写入与重复处理

只允许固定两集合、固定两主键，不list/where，不读写项目/邀请/成员/管理员。拟定审计主键为a_reg_+sha256('participant-self-registration/1:'+APPID+':'+envId+':'+完整userId)[0:40]，与人绑定而非新轮次随机生成；完整表达式必须被实现测试和证据锁定。

事务内读取本人用户及该确定性审计两条记录，再按下表执行。用户与审计必须在同一事务原子创建，禁止set覆盖、补写旧记录或失败后另开事务修复。

| 当下事实 | 处理 | 本次持久写入 |
| --- | --- | --- |
| 本人用户不存在，确定性审计不存在 | 同事务创建用户及登记审计 | 恰2条新增 |
| 用户存在、字段齐备且openid/主键匹配、status=active；本包审计不存在 | 返回ALREADY_ACTIVE；不伪称本包创建或补审计 | 0 |
| 用户与本包审计均存在且绑定/内容一致 | 返回ALREADY_ACTIVE，允许报告已有审计归属 | 0 |
| 用户不存在但审计存在，或已有审计冲突 | 冲突停止，不修复 | 0 |
| disabled、未知status、缺字段、主体不符或读取异常 | 停止，不激活/覆盖 | 0 |

用户字段保持_id/openid/status='active'/createdAt/updatedAt；不加角色或绑定码。审计保留既有字段，actorRole='本人普通账号'、action='registerIdentity'、projectId=null、actorUserId=subjectUserId=本人编号、before=null、after.status='active'；可增加受控来源协议及登记轮次字段用于回读关联，须兼容性审查后冻结，不能靠note自由文本替代绑定。

同账号并发须由事务冲突/确定性主键保证最终至多一条用户和一条本登记审计。SDK自动重试事务回调与页面重试不同：每次回调都重查身份配置、时钟和记录，不在回调内执行外部副作用，不吞异常后假报成功。后续换轮仍不重复写审计。

时钟在入口、事务回调入口、每次写调用前及返回前复核；发现到期/NaN/异常即停止未完成事务。**不能声称平台提交一定在截止前完成**：最后一次本地检查至平台提交之间存在间隔。已提交后返回前到期或响应失败，结果必须标为待核实，保留writeAttempted/commitConfirmed等实际事实，不能说零写或自动重发。
