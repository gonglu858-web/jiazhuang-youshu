## 2. T1 · P1：不能把所有未知结果都当作可同号安全重试

位置：`miniapp/miniprogram/utils/schedule-sandbox-client.js:365–477`；`pages/schedule-sandbox/schedule-sandbox.js:287–296`。

**已复现（证据 02/03/10）：**

1. 真实客户端连接真实 `index.main`、完成管家准备后，第一次 `createInvitation` 已提交，但传输替身丢失响应；携带同一个 requestId 再调用，最终出现 **2 份邀请**。原 service 的这个动作没有 requestId 幂等保障；取号同样不能仅凭同号宣传为安全重试。原 S4 清单已明确要求区分。
2. `discardPending()` 不核对原结果就清标记。第一次施工提交超时，点“放弃该未决标记”后，第二次提交使用新 requestId 发出。按钮本身不发请求，不能证明随后新提交不会重复。不能靠用户清缓存/放弃状态解除未知写入锁。
3. 实际业务码 `SCHEDULE_CONFLICT` 不在确定拒绝清单，被标为 unknown 并锁住表单。证据 10 是匹配真实业务码的传输替身分类测试，不冒称执行了施工冲突事务。`TASK_DIR_NOT_READY`、`GUARD_INCONSISTENT` 等也应按实际接口契约核对，而不是只测 BAD_INPUT。

**修复要求：**

- 明确区分只读动作、已有服务端回执保障的写动作、无幂等保障的写动作。无保障动作结果未知时保留证据并停止，提示管理端核对；本轮可采用停止策略，不必扩展 vendor 幂等算法。
- 取消“无核验直接放弃未知写入”的路径。已有结果未知时，后续一次权限/窗口拒绝只说明本次未执行，不自动证明第一次未提交；不得将其当作原请求结果已核实并放开新写。
- 对首次请求的已知业务拒绝正确分类并允许修正；未知/服务端错误仍保留。恢复策略按动作说明，不笼统显示同号重试。

**验收：**真实 main 的邀请“提交成功→响应丢失”后不得产生第二份；取号未知停止；施工回执重试不重复；首次日期冲突可修改；未知后窗口到期/失权不被当作原提交未发生；无直接清锁重发路径。

## 3. T2 · P1：未决记录没有完整绑定，仍可串项目或串快照

位置：`utils/schedule-sandbox-client.js:94–99`、`:225–289`、`:378–410`。

**已复现（证据 04/05）：**

- A 目标提交超时，同轮次配置改成 B 后重试原 requestId，`:410` 用当前目标覆盖原 snapshot.projectId，实际发往 B。当前配置校验没有校验“原提交的目标仍相同”。
- 两键存储独立：一次成功后删 pending 成功、删 snapshot 失败，留下旧快照；下次写新 pending 成功、写新 snapshot 失败。首次发送被阻断，但随后重试因旧快照的自有摘要仍有效，发送 **新 requestId + 上次载荷**。不是单纯“篡改内容导致摘要不符”；当前记录与快照之间缺少共同身份绑定。
- 源码只按环境/轮次分键，未落实上一轮明确提出的可信账号隔离；测试 S4.10 只测轮次，不能据此声称账号切换已覆盖。
- S4.6 主动把“同号带不同内容”断言为发原内容，未实现原清单要求的普通提交内容冲突拒绝。显式恢复可以重建原快照，但不能把任意变化载荷都静默解释成确认重试。

**修复要求：**

- 原动作/项目/requestId/账号/轮次/快照必须作为一个可核验整体保存（可选择单条 envelope 等最小实现）；失败与半写不得拼接出合法请求。不存在 pending 但存在残留 snapshot 等状态需明确处理。
- 恢复时检查当前目标与原目标，变化即停止，不覆盖。普通提交和明确恢复接口区分，普通同号变更载荷拒绝。
- 按可信账号绑定/隔离恢复，不信任表单 actorId。若依赖平台原生隔离，必须明确证据与客户端信任边界，不能把未验证的假设写成测试通过。

**验收：**半写/半清理故障、两个各自合法但不配对的记录、同轮次换目标、同号换内容、账号切换；全部阻止错误发送。用原完整快照的显式恢复正常。

## 4. T3 · P1：创建回放缺少状态与当前权限核验

位置：`cloudfunctions/scheduleSandbox/project-guard.js:88–92`、`:139–148`、`:200–232`。

**已复现（证据 06/07/08）：**

- 保留轮次回执但删除合成项目，再次创建直接返回 `ok:true/replayed:true`，实际项目数 0。现有测试只覆盖反方向“项目存在、回执缺失”。
- 第一个请求完成事务外权限检查后，另一个正常请求先建好项目并将 primary 改绑；第一个进入事务读到回执，走并发 catch，在未重新核验当前权限的情况下向原管理员返回成功。S2.6 只测进入函数前已失权，未覆盖并发回放分支。
- 真实业务事务成功后，注入提交后回执读取失败，项目和回执均为 1，但错误信息写“已整体回滚，未留下半套状态”。不能由一次后置读取失败推断已回滚。
- `currentRoundProjectId` 仅取 record.projectId，不核验其与 roundId 推导 ID、记录 action/round/result 及实际项目的一致关系；它又是后续范围依据，应与创建回放共享最小状态核验。

**修复要求：**正常回放、并发回放统一验证当前身份权限与轮次记录/项目一致性；损坏状态停止。并发回放不要绕过当前权限。区分事务明确失败与提交后结果未知，错误信息只陈述已证实事实，已提交但响应丢失时可通过受控回放恢复原结果。

保留本轮已通过的 enlist 同事务方向、轮次唯一键，不重新设计旧业务。该要求不意味着用新项目覆盖损坏数据或自动修复云端。

**验收：**本次三例、记录字段/确定性 ID 不匹配、正常已提交回放、失败后再试和同轮次换执行人唯一性；结合 T5 修正后的替身验证。

## 5. T4 · P1：带凭据的页面恢复仍卡死，表单还有两处不一致

**已复现（证据 01）：**批准请求超时→退出重进→页面要求重新提供 applicantNumber，但 `inputField()` 对有 pending 的所有字段都拒绝输入。编号保持空，重试发送次数为 0，返回 `SANDBOX_SNAPSHOT_INVALID`。不能通过移除防重标记绕过。

源码核对另发现：

- snapshot 的 restDays 被回填到 `form.restDays`，表单实际显示/构造使用 `restDaysText`；invitationId 等常用字段也未完整恢复。当前测试 S5.6 只做 listSchedules，不需要这些字段。

**修复要求：**仅允许补回该未知请求所需的敏感凭据，匹配原摘要后才进入其允许的恢复路径，其余业务字段仍锁定；正确回填展示字段。日期不一致应要求明确确认，或在确认能力尚未提供时直接拒绝，不默认填 true。不需要扩大成正式业务 UI。

**验收：**加载实际 Page，通过真实 inputField/inputForm 事件测试（setData 替身须支持点分路径），覆盖带凭据恢复、错误凭据拒绝、休息日/邀请编号显示、日期不一致未确认/已确认。不能只直接 setData 绕过事件锁。

## 6. T5 · P2：事务替身泄露未提交写入，现有并发证明不可靠

位置：`miniapp/tests/helpers/sandbox-test-db.cjs:235–289`，尤其 `:271` 使用共享 data 作为事务数据。

**已复现（证据 09）：**创建事务执行完回调但暂停在提交前，第二个真实 main 请求已能读到第一事务的回执并报告成功；让第一事务在提交前失败回滚，最终 **项目 0、回执 0，第二请求却已经报告成功**。这是内存替身的脏读，不是已证实的 CloudBase 缺陷。

因此“两个请求都成功、最终一份项目”的正向例不能独立证明真实提交冲突路径。当前 rollback 的共享数据撤销及全局 writeLog 截断也不能被当作可靠的他事务保留证明。

**修复要求：**使用每 attempt 的隔离视图/写集，提交前不对事务外和其他事务可见；提交冲突后只丢弃本 attempt 写集，不回滚其他已提交数据或日志。可以复用项目已有成熟冲突夹具，限定在测试文件，不改业务。保留隔离前缀检查。

**验收：**未提交记录对外不可见；一事务回滚不会让另一请求假成功；并发成功需看到已提交回执；双方都先看到无回执再竞争，失败方按可信提交结果回放；交错失败后他事务数据与日志保留。修复后重新跑 S2 的并发与 SDK 重入用例。如替身尚不能证明某路径，明确标未验证，不能用更宽断言保绿。
