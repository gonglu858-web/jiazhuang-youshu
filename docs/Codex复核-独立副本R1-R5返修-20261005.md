## 2. S1（P1）：不能要求 wx.getAccountInfoSync 返回 CloudBase envId

定位：`miniapp/miniprogram/utils/sandbox-test-driver.js:140–194`，尤其 `if (!env.envId)`；新测试 `makeApi`。

**事实**：微信官方 `api-typings` 的 `AccountInfo.miniProgram` 类型为 `MiniProgram`，字段是 `appId`、`envVersion`、`version`，不含 `envId`。官方源：

https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.api.d.ts

本次读取对应 `AccountInfo` 及 `MiniProgram` 定义（抓取时约 8035–8051 行）。微信文档页面本次读取失败，以微信官方仓库定义核验；没有使用非官方博客作为结论依据。

**复现 S1-official-account-info-shape-blocked**：提供正确 appId、develop、version 的真实契约形状，但不添加虚构 envId，得到 `TEST_DRIVER_GATE_BLOCKED / 运行环境未返回环境 ID`，零请求。也就是说，所有成功夹具都靠手工增加 envId 才放行，真实入口按标准接口形状不能运行。

**最小修法**：实际账号信息只验证 AppID 与明确 develop/trial；CloudBase 目标由固定 proof、两配置一致性以及每次 `callFunction.config.env` 精确限定。不要伪造 runtime envId，也不要放宽实际 AppID/版本或采用隐式默认环境。正常夹具去掉 envId，以真实结构验证 Page/驱动正向；错配置环境、错调用目标仍零业务请求。

## 3. S2（P1）：损坏/历史记录与内部所有者不能被当成空白或授权

定位：`sandbox-test-coordinator.js:263,278,302,340,429,610`；`schedule-sandbox-client.js:57` 的 `enterOrdinary` 和导出的 `refreshSessionIdentity(api, internalOwner)`。

### 独立复现

1. **S2-malformed-batch-cases-silently-reset**：批次 JSON 可解析，但 `cases:[]`；驱动把它当成没有历史，发送两笔并 candidate。`readCase/blockingCases` 用 `{}` 兜底，`ensureBatchDoc` 还能把损坏 cases 重置成空对象。当前只覆盖坏 JSON，没有覆盖可解析的坏结构/未知状态。
2. **S2-legacy-stopped-case-hidden**：保留上一轮真实键格式 `...batch:env:round:actor:case:V06-a`、`kind=...case/1`、state=stopped；枚举直接跳过 `:case:`，本轮重新发两笔。旧记录保留在磁盘但准入忽略它，仍属于隐藏未决。

### 最小修法与验收

- 严格验证批次 kind/环境/轮次、cases 字典、每项状态及绑定。存在但损坏必须阻断，不重置、不覆盖，不把未知状态跳过为已完成。已有数据读取错误不得通过 legacy 正常值掩盖。

- 内部重入只接受当前真正持有的 ordinary token，或者改成未导出的内部函数承接；任意 truthy owner、错误/过期/test token 都拒绝。外部 API 不新增跳锁选项。
- 验收：坏 cases/坏 record/未知 state/错绑定、旧 stopped/armed、普通与驱动两方向、换账号/重进、伪造 internalOwner、合法恢复内部重入不自锁。不要重做已通过的正常 v2 占用逻辑。

## 4. S3（P1）：两笔响应必须从发送时各自监听，回读必须保住证据

定位：`sandbox-test-driver.js:974` 起发送段，尤其 `for ... await withTimeout`；`sandbox-test-coordinator.js:529`。

### 独立复现

- **S3-second-response-not-persisted-until-first**：第一笔保持未完成、第二笔先成功；第二笔已经返回，但持久响应数仍为 0。释放第一笔后才一起推进。当前 `for` 按序 await，不是“每笔到达即保存”。第二笔的超时计时也到第一笔等待结束才开始；如果第二笔先拒绝，代码还没有为它安装 rejection handler，存在未处理拒绝风险（该风险按代码路径指出，本轮未把它冒充独立运行结果）。
- **S3-candidate-readback-lost-responses-accepted**：存储故障注入只删除 candidate 的 responses，保留状态和 snapshot 摘要；runCase 仍报告 candidate，持久响应数 0。`setCaseState` 仅核对状态和快照自身摘要，不核对本次拟写证据与实际回读是否完整相等。

### 最小修法与验收

- 两个调用在同一同步段启动，并立即为各自注册完成/拒绝及超时处理；每笔独立保存到固定槽位，不能等另一笔才能保存。不要因第一笔持久化失败提前退出而放弃监听已经发出的第二笔；维持全局停止结论，不补发。
- 完成时刻与超时起点对应实际发送/回调，而不是 for-loop 轮到该项的时刻。晚响应只补留证，不自动改 candidate/解锁。
- 状态回读核对本次要写的完整非敏感数据（响应、绑定、请求、状态与摘要），不能只核对“状态一样”和“自报摘要自洽”。任何失败保守停止，保留已有记录；`step` 失败不能被后续成功覆盖成 candidate。
- 补第二笔先成功/先拒绝、第一笔永久等待、两者超时起点、首响应写失败后另一笔到达、回读丢响应/改绑定/旧内容回退。保留已通过的同步抛错和截止前置测试。

## 5. S4（P1）：保持当前安排语义，未知查询/坏响应不能成为通过前提

定位：`sandbox-test-driver.js:78,99,292,497,529,899`。

### 独立复现

1. **S4-current-expected-date-overwritten**：通过真实 Page，在 a 已 reviewed 后，getSchedule 返回当前 endDate=11-03、expectedDate=11-05；两笔 update 都把 expectedDate 写成 11-03，仍 candidate。原因是读取后没有采用当前 expectedDate，`buildPair(update)` 又直接设 `expectedDate:input.endDate`。这不是“只改内容”的固定测试。
2. **S4-invalid-pagination-treated-as-empty**：listSchedules 返回 `ok:false`、包含无 id 坏行、`pagination:{}`；当前不检查 ok，丢弃坏行，把缺 hasMore 当 false，于是 V07-B 发送 removeMember 并 candidate。不能把无法确认的数据当成“乙已无 active 安排”。
3. **S4-unvalidated-nested-field-persists**：成功响应 core 字段合法，但 content 是含合成 token 标记的对象；a 被判 candidate，嵌套标记写进长期存储。`sanitizeResult` 复制公共字段时未核对其类型，后续成功验证也未覆盖这些字段。该标记是内存合成值，不是真实秘密泄露。

### 最小修法与验收

- c 采用真实当前完整 form，不得悄悄覆盖 expectedDate 或用空 restDays 替代缺字段。本轮固定测试既然收窄为日期相等：遇到当前 expectedDate≠endDate 就明确停止，零 update；不要改变业务安排来让测试通过，也不自动补确认。
- listSchedules 必须 ok=true、schedules 数组内每条可验证且属于目标项目、状态与筛选一致；pagination.hasMore 必须明确布尔值，hasMore=true 必须有合法推进 cursor。坏行不静默丢弃；不完整/循环/错误结果一律“前提未知”，不是 EMPTY。只使用现有公开契约，不新增云路由。
- 持久化前按真实白名单及每字段类型/值验证成功响应；不能先把任意对象复制进报告/存储、事后才标错误。坏成功只保存安全诊断码。复用 `publicSchedule` 实际字段形状，不回退成 scheduleId 顶层假契约。
- 验收：当前不等日期/缺日期/缺休息日停止且不改安排；ok=false/缺或错 hasMore/坏行/错项目/非 active/重复 cursor 均不移出；嵌套对象和非法数组元素不落报告或持久存储。保留已通过的 a-reviewed/getSchedule、不同号/内容、严格 core 响应检查。
