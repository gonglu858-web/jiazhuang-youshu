# 施工安排第二单元实现说明

日期：2026-10-03。状态：本地返修完成（F1–F7）、G1–G6 收尾并 H1–H5 复查修复，未操作云端。

## 1. 目标与边界

本说明约束 `miniapp` 本地新增代码，实现施工安排新增、调整、改派、取消、成员只读查看和版本历史，并同步实现责任师傅移出保护。不创建真实数据库集合、不部署云函数、不生成预览/发布。

沿用 `memberAccess` 云函数及可信身份机制，将安排逻辑分为独立服务模块 `schedule-service.js`；`memberAccess/service.js` 在 `removeMember` 中调用安排服务的移出保护校验。不修改 `connectionCheck`、旧身份/邀请/批准探针、四份旧验证凭据、env-gate。

## 2. 数据集合与字段（逻辑设计，未创建）

为便于本地代码审查，使用以下逻辑集合命名。物理集合可合并，但逻辑隔离不能丢。

### 2.1 `schedules`（当前安排）

- `_id`: `s_${uuid}`，稳定公开 ID
- `projectId`: 项目 ID
- `stage`: 11 阶段之一
- `trade`: 工种
- `workerUserId`: 主要上传责任人 userId
- `startDate`, `endDate`: `YYYY-MM-DD`，含首尾
- `expectedDate`: `YYYY-MM-DD`，预计完成日期
- `restDays`: `YYYY-MM-DD[]`，休息/停工日
- `content`: 本次施工内容，1-500 字
- `status`: `active` | `cancelled`
- `version`: 整数，从 1 开始
- `createdAt`, `updatedAt`: ISO 8601
- `createdByUserId`, `updatedByUserId`: 操作者 userId
- `createdByRole`, `updatedByRole`: 操作者当时角色

### 2.2 `schedule_revisions`（不可变历史）

- `_id`: `sr_${uuid}`
- `scheduleId`: 对应安排 ID
- `projectId`
- `beforeVersion`: 变更前快照版本
- `afterVersion`: 变更后安排版本
- `version`: 保留兼容旧字段，同 `beforeVersion`
- `snapshot`: 变更前完整快照（不含历史链、_openid）
- `changeType`: `create` | `update` | `reassign` | `cancel`
- `reason`: 调整/改派/取消原因，非空，1-200 字；创建为空
- `actorUserId`, `actorRole`, `actorLabel`
- `createdAt`

**版本语义**：`schedules` 的 `version` 为当前版本。`schedule_revisions` 的 `beforeVersion` 为快照对应的旧版本，`afterVersion` 为变更后的新版本。创建记录：`beforeVersion=0, afterVersion=1`；调整/改派/取消记录：`beforeVersion=current.version, afterVersion=nextVersion`。页面展示“此次变更：第 afterVersion 版 · 调整”及“变更前内容（第 snapshot.version 版）”，避免把旧快照内容误作新版本内容。历史分页游标使用 `afterVersion`，`beforeVersion=0` 不被当作缺失。

### 2.3 `schedule_occupancy`（实际施工日占用）

- `_id`: `${projectId}:${trade}:${date}`，如 `p_xxx:水电:2026-10-05`
- `projectId`, `trade`, `date`
- `scheduleId`: 当前占用该日的有效安排 ID

用于事务内保证"同项目、同工种、同实际施工日仅一份有效安排"。创建/改派时原子写入占用；调整日期时释放旧日期并占用新日期；取消时按旧安排的实际施工日逐个确定性释放，不依赖查询首页。

### 2.4 `member_task_guard`（成员任务保护记录）

- `_id`: `${projectId}:${userId}`
- `projectId`, `userId`
- `activeScheduleCount`: 该成员在当前项目未取消安排数，必须为非负整数
- `version`: 保护记录版本，用于事务冲突检测

`removeMember` 与安排创建/改派使用同一份保护记录。移出前在事务内检查 `activeScheduleCount === 0`；若 guard 缺失，回退查询 `schedules` 集合核验。创建/改派指向某师傅时递增；取消或改派走掉时递减。移出时读取 guard 并递增其版本（不改变计数），建立与创建/改派事务的写冲突点。

**guard 缺失处理**：所有更新 guard 的路径在 guard 缺失时，通过事务内 `paginatedFetch` 查询 `schedules` 中该成员 `active` 记录数重建权威基线，避免数据库单页截断导致计数低估。为避免当前操作影响重建结果，调整 guard 的顺序为：创建时先递增 guard 再写入 schedule；改派时先调整双方 guard 再更新 schedule；取消时先递减 guard 再将 schedule 标记为 cancelled。`lockGuard` 用于移出建立冲突点，调用前已通过 `hasActiveSchedules` 确认无 active 安排，缺失时创建 count=0 安全。

### 2.5 `schedule_receipts`（提交回执）

- `_id`: `receipt_${sha256(requestId)}`
- `requestId`: 幂等键
- `projectId`, `action`
- `actorUserId`: 回执绑定账号
- `payloadHash`: 规范化业务载荷哈希
- `result`: 回执结果（成功时含 id/version/status）
- `createdAt`

用于同请求重试返回原结果，不重复生成安排/版本/审计。重放时校验账号、项目、动作、规范化载荷均一致；任一不同返回 `REQUEST_ID_REUSED_DIFFERENT_PAYLOAD`。`create`/`update`/`reassign`/`cancel` 的 payload 分别包含 `expectedConfirmed`/`expectedVersion`/`expectedConfirmed`/`expectedVersion`/`expectedVersion`，使版本或确认状态变化时同一 requestId 不能覆盖旧结果。

### 2.6 复用 `audit_events`

沿用已有审计集合，记录 `createSchedule`/`updateSchedule`/`reassignSchedule`/`cancelSchedule`/`removeMember` 等动作、当时角色、前后状态摘要。

## 3. 索引草案（部署前复核）

- `schedules`: `{ projectId, status, trade }`, `{ projectId, workerUserId, status }`
- `schedule_revisions`: `{ scheduleId, version }`, `{ projectId, createdAt }`
- `schedule_occupancy`: 以 `_id` 为唯一键即可
- `member_task_guard`: 以 `_id` 为唯一键即可
- `schedule_receipts`: `{ requestId }` 唯一

容量限制：单条安排的实际施工日受日期范围限制，上限 365 天；超出时返回 `SCHEDULE_RANGE_TOO_LONG`，不截断日期。单项目同工种同日唯一占用键数量与日期范围成正比，属于本地实现限制，需在部署前用真实环境验证。

## 4. 接口命名与公开形状

在 `memberAccess` 云函数内新增 action，统一返回 `{ ok, ...result }` 或 `{ ok:false, code, message }`。

### 4.1 查询类

- `getScheduleContext({ projectId })`
  - 返回：项目公开投影、`isManager`、当前成员可安排的工种列表、可指派师傅列表（含 userId/label/roles/trades）。
  - 权限：项目成员可读；负责人（admin）非成员也可读，但 `isManager=false`。
  - 师傅名单通过 `paginatedFetch` 取全，避免数据库单页 100 条截断。
- `listSchedules({ projectId, status, trade, date, cursor, limit })`
  - 返回：`schedules`（公开字段数组）+ `pagination: { limit, hasMore, nextCursor }`。
  - 所有分支统一公开字段；日期过滤按安排自身 `startDate`/`endDate`/`restDays` 计算实际施工日并匹配，确保已取消安排仍可按日期查到，不依赖 `schedule_occupancy`（取消会释放占用）。
- `getSchedule({ projectId, scheduleId })`
  - 返回：单条安排详情（公开字段）。
- `listScheduleRevisions({ projectId, scheduleId, cursor, limit })`
  - 返回：历史版本列表（含 snapshot），支持分页。

### 4.2 写入类

- `createSchedule({ projectId, requestId, form, expectedConfirmed })`
  - form: `{ stage, trade, workerUserId, startDate, endDate, expectedDate, restDays[], content }`
  - `expectedConfirmed`: 当 `expectedDate !== endDate` 时必须为 `true`
  - 返回：{ scheduleId, version, status }
- `updateSchedule({ projectId, scheduleId, expectedVersion, requestId, form, reason, expectedConfirmed })`
  - 返回：{ scheduleId, version, status }
- `reassignSchedule({ projectId, scheduleId, expectedVersion, requestId, workerUserId, reason })`
  - 返回：{ scheduleId, version, status }
- `cancelSchedule({ projectId, scheduleId, expectedVersion, requestId, reason })`
  - 返回：{ scheduleId, version, status }

### 4.3 错误码

- `NO_ACCESS`: 无项目/无权限/非管家
- `BAD_INPUT`: 字段缺失、日期非法、原因长度不符、restDays 非数组或非字符串等
- `WORKER_INVALID`: 责任人账号停用、非成员、无师傅角色、缺工种
- `SCHEDULE_CONFLICT`: 同工种同日已有有效安排
- `VERSION_MISMATCH`: 版本冲突，需重新加载
- `SCHEDULE_RANGE_TOO_LONG`: 日期范围超实现上限
- `SCHEDULE_NO_WORKING_DAY`: 排除休息日后无实际施工日
- `EXPECTED_DATE_MISMATCH`: 预计完成日与结束日不同，需确认
- `WORKER_HAS_ACTIVE_SCHEDULES`: 移出时该师傅仍有未取消安排
- `GUARD_INCONSISTENT`: 保护记录计数与实际 active 安排数不一致，禁止移出
- `REQUEST_ID_REUSED_DIFFERENT_PAYLOAD`: 同 requestId 不同内容/项目/动作/账号
- `SERVER_ERROR`: 其他服务端失败

## 5. 事务协调与幂等

写操作在 `db.runTransaction` 内执行：

1. 先在事务内复核执行人当前 `users.status`、项目 `status/scope`、当前成员 `status/roles`（管家）。
2. 再检查幂等回执：同账号/项目/动作/载荷返回原结果；任一不同返回 `REQUEST_ID_REUSED_DIFFERENT_PAYLOAD`。
3. 重新读取目标师傅、安排当前版本；校验字段、版本、冲突、原因长度。
4. 写入/更新安排、追加修订、调整占用、更新任务保护计数、写入回执、追加审计。
5. 任一步失败抛出 AppError，CloudBase 事务回滚；服务端返回业务错误。

回执重放不能跳过当前权限复核：若事务内发现执行人账号停用、成员被移出或项目失效，即使 requestId 已有成功回执，也返回当前权限错误，不返回旧结果。

客户端写方法支持传入稳定 `requestId`。页面层在保存/取消时维护 `pendingRequest`/`pendingCancel` 状态，并按错误类别区分行为：

- `schedule-client.js` 的 `call()` 将网络/超时/响应缺失类错误统一归类为 `kind='unknown'`，将服务端明确业务拒绝归类为 `kind='business'`，入口/校验/鉴权错误归类为 `kind='entry'`/`kind='validation'`，并导出 `classifyError()` 供页面使用。
- 提交前记录完整请求快照：`projectId`、`scheduleId`、`version`、`requestId`、`cloudForm`、`reason`、`expectedConfirmed`、`isEdit`、规范化载荷签名及当前状态；重试时直接使用快照中的字段，不再读取可能被用户改过的页面输入。
- 网络超时等“结果未知”错误：页面 `errorKind='blocking'`，pending 状态保留，锁定所有输入/选择/提交，仅允许以原快照/原 requestId 重试；禁止在未核验的情况下通过“我已核对”按钮清除未知状态，避免在结果实际已提交时再次创建第二份安排。
- 明确业务/校验错误：页面 `errorKind='recoverable'`，pending 置为失败，允许用户修改表单后再次保存；再次提交时使用新 requestId，表单签名变化后不再复用旧号。
- 入口/鉴权错误：页面 `errorKind='blocking'`，禁用保存按钮，等待用户离开或环境恢复。
- 未修改内容重试复用原 requestId；实质变更后分配新 requestId。

## 6. 数据库分页策略

本地实现受云数据库 SDK 单次返回上限（模拟 100 条）约束：`listSchedules`/`listScheduleRevisions`/`getScheduleContext` 在 `schedule-service.js` 内部通过 `paginatedFetch`/`fetchAll` 使用 `skip`/`limit` 递归取全，再按稳定排序（createdAt+_id 或 afterVersion）做 cursor 内存分页返回。`hasActiveSchedules`/`rebuildGuardCount` 也使用事务内 `paginatedFetch` 取全，避免 guard 重建计数被截断。带 `date` 查询直接按安排自身日期/休息日过滤，不依赖 `schedule_occupancy`，确保已取消安排仍可见。无效 cursor 返回空列表（不回到首页），避免循环或重复。

## 8. 未启用项目兼容

- 未启用项目或缺集合时，新安排请求在客户端被入口配置拦截；
- `removeMember` 对缺 `member_task_guard` 的项目：若 guard 缺失但 `schedules` 集合可查询，则回退查询核验；若集合也不存在，部署前须创建集合并回填；
- 不为了兼容而放宽已有移出权限限制。

## 9. 异常处理

- 事务内失败：整体回滚，返回业务错误码；
- 客户端错误分类：
  - `entry`：入口配置拒绝、release/未知版本/非允许项目，禁止任何云请求；
  - `validation`：表单字段非法，禁用保存按钮；
  - `business`：服务端明确业务拒绝，属可恢复错误，允许修改表单后重新提交；
  - `unknown`：网络、超时、响应缺失或无法判断结果，属阻塞错误，锁定表单，仅允许以原请求完整快照重试；禁止未核验清除状态。
- 客户端超时：保留完整请求快照和 `requestId`，重试时复用原快照，不自动换键重发；
- 云端失败不回退为本机保存，不提示"已保存到本机"；
- 旧功能回归失败立即停止排查，不降低断言。

## 10. 移出并发保护

`removeMember` 在事务内：
1. 重新校验管家权限；
2. 读取 `member_task_guard`（按 `_id` 唯一键）；
3. 无论 guard 是否存在，均通过事务内 `paginatedFetch` 查询 `schedules` 中该成员实际 `active` 记录数；
4. 若 guard 存在：校验 `activeScheduleCount` 为非负整数，并与实际 active 计数交叉核对；不一致时返回 `GUARD_INCONSISTENT`，阻止可能因计数损坏导致的错误放行；若实际计数 `> 0`，返回 `WORKER_HAS_ACTIVE_SCHEDULES`；
5. 若 guard 不存在：回退查询 `schedules` 中该成员 `active` 记录，若存在则返回 `WORKER_HAS_ACTIVE_SCHEDULES`；
6. 读取/创建 guard 并递增版本（不改变计数），建立与创建/改派事务的写冲突点；
7. 移出成员。

安排创建/改派/取消在事务内：
1. 复核执行人权限；
2. 调整 `member_task_guard`（创建递增、改派旧递减新递增、取消递减）；缺失 guard 时按 schedules 真实状态重建基线；
3. 写入/更新安排、占用、回执、审计。

同一事务内同时修改 guard、occupancy、schedule、revision、receipt、audit，确保并发指派与移出不会留下失效责任人。

## 12. H1–H5 复查修复补充

### H1 / 真实客户端网络错误分类与响应结构校验

- `miniapp/miniprogram/utils/schedule-client.js`：
  - 新增 `classifyError()`：保留错误对象已有的 `kind`；对未标记错误，按 `code` 与消息区分 `entry` / `validation` / `unknown`；`TIMEOUT`/`ECONNRESET`/`NETWORK_ERROR`/`REQUEST_FAIL` 等网络/传输类错误统一归为 `kind='unknown'`，不得仅因携带字符串 `code` 就判为 `validation`。
  - 新增 `isPlainObject()` 与 `validateSuccessResponse(action, result)`：`call()` 要求 `result` 与 `result.result` 均为普通对象，`ok` 必须严格布尔 `true`；`ok:false` 必须有明确业务 `code` 才视为 `business`；写成功响应按 action 核对接口必需字段（`scheduleId`/`version`/`status` 等）。畸形响应不再被误判为成功或业务失败。
- `pages/schedule/schedule.js` 与 `pages/schedule-detail/schedule-detail.js`：
