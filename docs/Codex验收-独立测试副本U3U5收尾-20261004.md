## 2. U3 因果链和实际恢复

原因判断成立：旧 Page 为无项目动作加入 projectId，与 envelope 的无目标契约相冲突。新代码没有放宽损坏记录校验，而是在发送之前统一了请求语义。

1. Page 的 NO_PROJECT_ACTIONS 与 client 的 PROJECT_OPTIONAL 五项一致：identify、listMyProjects、requestBindingNumber、createProject、applyInvitation。
2. Page buildPayload 对这五项不写 projectId；preflight 把有效目标归一为空；buildBody 在有效目标为空时明确删除 pickTopLevel 带来的裸 projectId。
3. 恢复从已核验 envelope 重建请求，不补入当前登记项目；身份刷新自身也不带目标。在已检查的发送路径与下列用例中，未发现无项目动作残留 projectId 出网。
4. 不变的云端 index 中，createProject 通过轮次/项目保护逻辑确定项目；applyInvitation 根据邀请及归属保护处理。前端省略目标不等于取消云端归属校验。

独立用例使用真实 Page/client、合成存储与模拟传输，未使用真实云端：

- 项目配置空/非空 × 五动作，共 10 组，分别检查实际 Page runAction 与直调 client（含调用方裸 projectId）的发送体均无 projectId。
- listMyProjects/createProject 经真实 Page 首发超时后，新 Page 能读取有效未决记录，同号同载荷恢复成功；不再误报记录损坏。
- requestBindingNumber/applyInvitation 经真实 Page 结果未知后，拒绝重发为 SANDBOX_RETRY_UNSAFE、零发送、原记录保留。
- 项目必需动作目标清空时 SANDBOX_PROJECT_REQUIRED、零发送且存储不变；目标改动仍拒绝；动作与快照不一致的损坏 envelope 仍拒绝。

## 3. U5 与文案残留

实际模板由 checkbox-group 接收 change，内部 checkbox 固定 value=date-confirm。处理器依据数组是否包含该值确认；当前测试已把正向布尔事件改为数组事件。空数组、非数组、仅其它值、缺 detail/value 均不确认；日期组合绑定及失效逻辑保留。负向模板检查排除了裸 checkbox 自行绑定该处理器。

**精确措辞应是“非数组或不含 date-confirm 时未确认”。** `['date-confirm','other']` 实测仍确认，因此代码注释和交付中“含其它值一律未确认”过强。当前 group 只有一个固定 checkbox，正常交互不会产生混合值，故不把此边界提升为功能阻断，也不要求扩大实现。若以后增加组内选项，需要重新确定组合语义。

历史报告/历史证据中的布尔事件说法按要求保留，属于已被本次结论取代的历史记录，不能继续作为当前操作说明。进展和交接顶部已明确取代关系。
