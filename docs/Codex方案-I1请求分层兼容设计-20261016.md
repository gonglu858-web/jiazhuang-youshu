## 1. 问题与结论边界

两次真实截图均表现为：userInfo 被识别，另一个 9–16 码元顶层键未识别，PIC_REQUEST_INVALID、UNKNOWN、读取未开始。第二精确候选 wxCloudApiToken 本次未命中。尚不知道未知键名字、值、来源及注入时点。

当前前端把 action/passphrase/checkRoundId/includeFullUserId 直接放在请求顶层；服务端把整个 event 传给核心。核心把任何额外顶层键当作非法业务字段，因此这些附带键会提前终止本人核验。现有证据只支持这一触发机制，不证明键由哪一方注入，也不证明传输过程会保留新嵌套对象。

实际身份来自 SDK getWXContext 的 APPID/OPENID，环境来自受审运行环境；口令只限制窗口持有者，不能证明现实本人。核验代码不授予角色、无登记/业务写入模块，查询仅限由可信 APPID:OPENID 派生的本人主键。这些边界不变。

## 2. 三种办法比较

| 办法 | 变化与问题 | 本轮选择 |
| --- | --- | --- |
| 继续增加固定候选或收集更多键名 | 依赖未知键的识别；每次猜测可能又需手机窗口；还需单独审查取证泄漏面 | 不推荐继续猜测 |
| 在现有顶层只挑四个字段，忽略其它字段 | 改动少，但混淆业务字段与附带信息，旧格式多余业务输入也可能被静默忽略 | 不推荐 |
| 新建固定嵌套业务对象，外层与内层分别处理 | 新协议与新适配器；内层仍严格拒绝多余字段，外层不作为身份和业务输入 | **推荐，待确认** |

推荐方案不把外层未知键认定为“平台可信字段”。无论是谁放入，它们都没有业务或身份含义。我们接受它们可以存在，只不使用其值。此处是对旧“整个 event 出现任意额外键即拒绝”的**明确变更**，不能声称原契约完全没变。

## 3. 推荐协议：固定外壳 + 严格业务对象

建议请求形状（示意，全部为合成值）：

```json
{
  "picRequest": {
    "schema": "participant-identity-request/1",
    "action": "inspectSelf",
    "checkRoundId": "synthetic-new-round",
    "passphrase": "synthetic-passphrase",
    "includeFullUserId": false
  }
}
```

### 3.1 外层规则

1. event 必须是非空记录对象，不能是数组、字符串或其它标量。只允许普通对象或 null 原型对象；跨 VM 测试须明确对象创建所在上下文，不能因此放开任意自定义原型。
2. picRequest 必须是**自有、可枚举的数据属性**，不能继承取得、不能是 getter/setter。通过自有属性描述符取值，禁止读取 event.picRequest 的访问器。
3. 其余外层键不递归遍历、不读取值、不拷贝、不序列化、不记录键名/值，不传播到核心、日志、结果或错误。禁止对象展开、Object.assign、整 event 的 JSON.stringify 或 JSON 克隆。
4. 保留少量明确冲突拒绝：外层出现 action/passphrase/checkRoundId/includeFullUserId/schema（旧格式混用）或 openid/OPENID/unionid/UNIONID/appId/APPID/userId/role/roles/collection/docId/envId/functionName（自报身份/业务目标）或 __proto__/prototype/constructor，统一拒绝。判断仅用自有键名，不读值；非枚举同名也拒绝。此列表是歧义和误用检测，**不是身份安全性的全部依据**；未知大小写变体也不能进入核心。
5. 外层自有 Symbol 键拒绝。检查键名和描述符可能触发 Proxy 元操作；不承诺对任意 Proxy 无副作用。元操作抛错一律净化拒绝，不能输出原始异常。额外普通字段的 getter 不得被执行。
6. 如果真实附带键恰好与 picRequest 或拒绝字段冲突，仍应拒绝。本方案不以“必须成功”为理由放宽冲突规则，也不保证下一次真机必过。

### 3.2 内层规则

1. picRequest 同样限普通对象/null 原型；schema 必须精确等于 participant-identity-request/1，不做字符串化、大小写变换或自动纠正。
2. 内层唯一允许字段是 schema 与原四个业务字段；任何额外自有键、Symbol、非枚举字段、访问器、危险属性或自定义原型一律拒绝。枚举使用能覆盖非枚举自有属性的方法；只对固定允许的数据属性读取 descriptor.value。
3. action、checkRoundId、passphrase 为自有字符串字段；includeFullUserId 可缺省，有则必须为布尔值。不能用 Boolean('false') 等隐式转换；false/缺省继续不请求完整 ID。
4. schema 验证通过后仅逐项构造新的四字段对象交给未改核心，schema 不进入核心。新对象不携带外层或内层未知数据、原型或访问器。
5. 核心仍验证 inspectSelf、准确轮次、口令摘要、可信 AppID/环境/OPENID、当下有效窗口；未知核心字段拒绝仍保留。适配器不替代这些检查、不补默认身份、不替换轮次或口令。

### 3.3 禁止兼容回退

新协议缺失/非法时直接失败，不能自动再试旧顶层格式；不做“两个都解析、选能通过的一个”。旧页面访问新候选失败是预期，必须使用新独立包和新轮次。配对关闭包仍拒绝所有业务请求。

## 4. 服务端顺序与错误事实

建议顺序：受审开关/配置门槛 → 受控外壳解析与内层校验 → 读取可信运行时身份 → 创建只读核心并验证口令/轮次/可信目标/窗口 → 本人固定主键 field({_id,openid,status}).get() 至多一次 → 原读后/返回前时效校验与净化结果。

- 新适配器必须位于 cloud.database() 构造之前；适配失败零 database 工厂、零 collection/get。可信上下文获取可按原入口实现保留在配置门槛之前，但不得用 event 作为后备来源。
- 核心准入失败须零 collection/get；建立 SDK 数据库句柄与发起数据库读请求分开计数，不能把前者误称平台读取，也不能把其数量硬写零。
- 适配层失败使用既有结果 schema 与 PIC_REQUEST_INVALID 固定文案：UNKNOWN、identityConfirmed=false、recordMatched=null、readAttempted=false、userId=null、尾号空；轮次仅来自受审配置，不附 serverTime 或 keyDiagnostic，不回显原异常。
- 进入核心后的原失败分类与读取尝试事实保留；get 抛错仍 readAttempted=true，不能因兼容重置。读取失败不能当 ABSENT；不更改现有核心状态和返回契约。
- 原用户选择完整编号、取消勾选立即清除、口令调用后清除、单击单发、加载/切前台零请求保持。
