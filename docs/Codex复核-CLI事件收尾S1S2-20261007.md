## 2. T1 [P1] 宽限从spawn时启动，正常运行超过2秒就提前失败

位置：`miniapp/scripts/lib/cloudbase-readonly-observer.cjs:514`，`const graceTimer = setTimeout(...)`。

注释写“观察到exit后启动”，但setTimeout位于注册监听之后，进入spawnBounded即执行；onExit并未启动该计时器。回调也未检查processExited，故正常仍运行的子进程会被误判close未确认。finish随即取消55秒总超时、移除data/exit/close监听；此路径未请求kill，可能留下仍运行的查询进程。

**独立复现**使用完整生产LIMITS、真实被审模块与合成child，不发任何exit/close：

| 观测 | 结果 |
|---|---|
| 返回时间 | 2012 ms |
| processExited | false |
| closeNotObserved | true |
| timedOut | false |
| kill次数 | 0 |

它应继续受55秒总超时约束，不能从启动计2秒close宽限。这会影响真实云查询，不是纯文案问题，也不是要求把2秒调成更大的数。

### 最小修法

1. 宽限句柄初始为空；仅首次真实exit事件后启动close宽限。重复exit不能刷新或重复启动。
2. close正常收尾时清宽限与总计时器。等待close期间总55秒限制仍有效，以先达到者有界失败；exit前总超时按原逻辑请求终止一次。
3. 宽限回调只能对应已观察exit、尚未close的情况，不能把未退出进程标成该错误。保留尾部读取和晚到error吸收的已通过修法。
4. 2秒可作为本机保守失败阈值保留，不作为平台耗时承诺；无需另设技术选项、安装或改CLI入口。

### 相称补测

- 不发exit，等待超过缩短后的closeGrace但小于总timeout：Promise仍待定；随后发输出/exit/close，应成功。
- exit发生得较晚：宽限从exit开始，非从spawn开始；重复exit不延长宽限。正常尾部data仍保留。
- 永不exit/close：总超时生效、请求kill一次、timedOut=true，不提前closeNotObserved。
- exit后无close：宽限有界失败；总超时更早时仍不能被宽限延长。

优先用可控计时器或明确事件屏障，避免靠极短sleep碰运气。只跑本模块相关测试，不扩成新进程管理系统。

## 3. “5ms事件竞速”说明需更正

旧Codex复现脚本直接传入 `__limits:{timeoutMs:5,maxOutputBytes:100}`，没有新增的closeGraceMs。spawnBounded直接取__limits，不经过resolveLimits补默认值，因此执行 `setTimeout(callback, undefined)`，可能早于5ms总超时。不能据此认定“不是缺陷，只是5ms竞速”。

本次另用timeoutMs=100且仍缺closeGraceMs的直接注入复现，16ms即closeNotObserved=true且processExited=false。**这条属于旧夹具与新增内部字段不匹配，和使用完整生产LIMITS也会2秒早退的T1应分开记。** 可在新测试使用完整限制或统一归一化入口；不修改旧历史脚本/JSON来掩盖差异。
