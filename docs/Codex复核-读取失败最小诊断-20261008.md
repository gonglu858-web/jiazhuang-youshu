## 2. R1：返回错误对象的诊断没有接到最终报告（P1，阻断本轮验收）

位置：worker normalizeReadResult约398—416行；primary非OBSERVED组包约565—573行；users对应组包约621—629行；测试DG-5约3138行。

normalizeReadResult识别并返回errorCode，但primary/users组包仅复制classification/requestId/docId/reason/hasPlatformError，没有复制或构造readDiagnostics，也没有建立读取失败的记录级READ_FAILED。

独立离线复现通过真实worker main、真实SDK初始化/文档转换，仅替换SDK请求传输：

| 返回路径 | 输入 | 最终报告 |
| --- | --- | --- |
| primary | 白名单DATABASE_REQUEST_FAILED | UNCONFIRMED，readDiagnostics=null，errorCode=PRIMARY_UNCONFIRMED |
| primary | 未知码 | 同上 |
| users | 白名单DATABASE_REQUEST_FAILED | UNCONFIRMED，readDiagnostics=null，errorCode=USER_DERIVATION_MISMATCH |
| users | 未知码 | 同上 |

四条路径均丢诊断。用户读取错误被通用兜底归为派生不匹配，也不能据此判断实际身份有问题。与之对照，抛Error且code为同一白名单码的正向样本能正确保留诊断。

DG-5先直接调用normalizeReadResult，再手写primary.readDiagnostics送到父层，绕过了正好缺失的worker组包。它不能证明“get返回错误对象也提供同形状诊断”的交付结论。

最小修复：只在已识别的错误响应分支，按当前读取阶段构造四字段诊断，将净化后的SDK码放入diagnostics.errorCode，记录级仍为READ_FAILED/UNCONFIRMED；primary/users对称传递。不要给所有NOT_FOUND/坏形状路径泛加平台错误含义。

测试改为合成请求传输直接return带code的响应，通过真实worker main→解释器→最终primary/users记录，断言已知码/未知码、阶段、requestId、READ_FAILED均贯穿。不手工补出worker实际没输出的对象。原正常读取及抛错正向保留。

## 3. R2：异常属性访问防护尚未完整（P2，同一诊断函数内收尾）

位置：worker classifyLocalError约352行及buildReadDiagnostics约383行。

safeErrorCode已保护code/errCode getter，但另两处仍可抛出：

- name缺失时，classifyLocalError直接读取error.message；message getter抛错使诊断构造失败。
- buildReadDiagnostics直接读取error.requestId；requestId getter抛错亦使诊断构造失败。

两例离线直接调用都确认抛错。此为损坏异常对象的合成边界样本，不声称真实SDK已返回该对象，不声称发生泄漏或错误放行。影响是诊断本身可能失败，丢失此次新增的分类事实。

最小修复：诊断无需读取message，删去这项依赖；requestId访问采用已有同等try保护。读取失败时固定UNKNOWN/OTHER/null，不递归展开原异常，不扩成通用异常框架。对象name不认识时应归UNKNOWN，避免把未知SDK异常称为NOT_AN_ERROR；后者可限于null/非对象输入。

补相称反例即可：message、requestId访问抛错时诊断不抛、不输出原文；真正Error/TypeError和原正向不回归。
